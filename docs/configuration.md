# Configuration

The tunables and the feature flags. Setup steps are in [running-locally.md](running-locally.md).

## Configuration

All tunable parameters are a `Settings` Pydantic model in [`src/config.py`](../src/config.py) with validators. Non-secret values are set in committed [`config.toml`](../config.toml); secrets come from `.env` / GitHub Secrets. Precedence: **env var → `.env` → `config.toml` → the code defaults below** (so any field can be overridden ad-hoc via an env var). The `Default` column is the in-code fallback when a field is absent everywhere; `config.toml` ships the actual production values.

The fallback gets the request only on a provider failure of the main adapter, once its own retries are spent — a 429 or 5xx, a timeout, a network or connection error. An empty or invalid JSON answer does not fail over (the provider did answer): it ends in the graph's neutral fallback as before. A 4xx other than 429 (bad request, bad key) is re-raised too, because the second provider would get the same broken request. The fallback's request is a paid call: it counts under `llm` in the cycle telemetry, so the FIN-12 ceiling and the cycle cost see it, and its tokens reach the same ledger with the fallback's provider and model. It runs only for a symbol already past the volatility gate. In the Slow Loop the fallback's request goes through the job's weekly allowance (FIN-30, `BudgetedLLMPort` with the job's shared `PaidCallAllowance`) and spends it like the main request: with the allowance spent the failover does not start and the main adapter's error propagates as before. Without a fallback the allocations stay at one call per job. A prediction made by the fallback carries the quality flag `llm_failover` in `data_quality_flags`, and its recipe names the provider and model that answered (the v2 receipt's `llm_provider` / `llm_model` / `recipe_version` and the `recipe_version` column), so it falls into its own recipe segment of the track record. ## Feature flags

**Optional alpha-data sources** (category "Data"): seven extra signals — SEC EDGAR insider flow, AlphaVantage earnings calendar, Finnhub options/IV, Reddit social velocity, FRED yield-curve, Finnhub analyst consensus, and regime-tagged RAG (vector memory). Each is a port + adapter with a **Null fallback** and is **off by default in code** (`insider_flow_enabled`, `earnings_calendar_enabled`, `options_flow_enabled`, `social_velocity_enabled`, `yield_curve_enabled`, `analyst_consensus_enabled`, `vector_memory_enabled`) — so a source makes **zero network calls** until its flag is on (and its key supplied where needed). Production `config.toml` turns on insider flow, social velocity, the yield curve and analyst consensus; the earnings calendar, options flow and vector memory stay off. Enabled per-symbol signals are aggregated into an "Alpha Signals" report section; `vector_memory_enabled` needs migration `017`.

The FRED yield curve is no longer render-only. When **both** `yield_curve_enabled` and `regime_aware_enabled` are on, an inverted 10Y-2Y spread is cast as one `ELEVATED` **vote** into `RegimeDetector`. It is a vote, not a veto: `RegimeDetector` needs two `ELEVATED` votes to declare `RISK_OFF`, so an inversion on its own only moves the regime to `NEUTRAL`. That is deliberate — inversions can persist for months, and a veto would pin the agent in risk-off for all of it. The net FinOps effect is a saving: `RISK_OFF` raises the volatility threshold, so fewer cycles ever reach the paid ports.

`regime_hysteresis_enabled` and `regime_exit_confirmations` (**require migration `033`**) add hysteresis to the market regime. `RegimeDetector.classify()` is stateless, so a signal oscillating around a boundary used to switch the volatility-threshold multiplier every cycle: noise passing for a signal. With the flag on, `main_agent._resolve_regime` reads the newest row of the `regime_history` table (`cycle_at`, `raw_regime`, `regime`, `streak`) and passes the raw regime through `apply_hysteresis` (`src/domain/regime.py`): entering `RISK_OFF` is immediate, while leaving it needs `regime_exit_confirmations` (default `2`) **consecutive** raw readings outside `RISK_OFF`. `NEUTRAL` and `RISK_ON` count alike, since both loosen the gate the same way, and the regime after the exit is the latest raw reading; a raw `RISK_OFF` resets the count, and moves between `NEUTRAL` and `RISK_ON` are not delayed. Each cycle with a regime (regime aware on and a Risk Watch report) writes one row with the raw regime, the effective regime and the count. The asymmetry is FinOps-safe: `RISK_OFF` only raises the threshold, and the effective regime is `RISK_OFF` whenever the raw one is, so hysteresis can only keep the threshold higher for longer, never lower it. The first cycle without history uses the raw regime, as before. A failed read (for example before the migration) is logged and the cycle uses the raw regime, exactly as with the flag off, and writes no row, so a missing read cannot reset a running count; a failed write is logged and the next cycle reads the older state, which can only delay the exit. `prediction_logs.regime` is not the source of the previous regime: it is written only on a saved prediction, and a cycle where no symbol passed the gate saves none. **A confirmation is one Fast Loop run, not one day**: on the cron schedule two runs are a few hours apart, but with manual dispatches the exit can take as long as the next two runs, days or weeks; a retried run counts as a run too. Both fields are part of `config_hash`, because they change the effective threshold of the gate. The flag ships **off**: before the migration the table does not exist, so the read and the write would fail every cycle.

`regime_tagging_enabled` (uses the `prediction_logs.regime` column of migration `017`) separates tagging from filtering. Before, the regime of a prediction was written only with `vector_memory_enabled`, so with vector memory off the column stayed `NULL` even though `regime_aware_enabled` was on, and there was no history to split the hit rate by regime. Now every saved prediction carries the canonical regime key (`canonical_regime_key` of the cycle's regime label, `UNKNOWN` when the cycle has no regime) whenever the tag is on, while the RAG filter on analogues of the same regime stays behind `vector_memory_enabled`; vector memory still tags as before. The field has no value by default (`None`): `main_agent` then follows `regime_aware_enabled`, which production `config.toml` turns on, so production tags every prediction without a new key. An explicit `true` or `false` wins. This is a deliberate exception to the rule that a new write ships behind a flag that is off: migration `017` was confirmed applied in production (state read on 2026-10-18), so the key cannot return `PGRST204`. A deployment that has `regime_aware_enabled` on but has not applied `017` must set `regime_tagging_enabled = false`, otherwise the whole prediction write fails. Zero calls, zero cost, and the field is outside `config_hash` (a write-only switch; the forecast is the same with the tag or without it).

The earnings calendar works the same way. With `earnings_calendar_enabled = true`, the next quarterly report is fetched **before** the graph runs and its proximity raises the volatility threshold (`IMMINENT` ≤ 2 days → ×1.5, `NEAR` ≤ 7 days → ×1.15, otherwise ×1.0). A 12-hour prediction taken the day before earnings is a coin flip, so the agent tightens the gate instead of burning tokens on analysis the report will invalidate — cutting spend and cleaning up the hit rate at once. The earnings and regime multipliers **compound**, and both are guaranteed `>= 1.0`, so the gate can only ever tighten. The event is fetched once per symbol and injected into the alpha-signals enrichment, so the gate adds **zero** paid API calls. With the flag off, no earnings port is touched at all.

`calibrated_confidence_enabled` closes the calibration loop. The repo already computed a reliability curve and ECE but only *displayed* them: when the 80–90% confidence bucket historically hit 55%, the ranking still trusted the raw 85%. With the flag on, `strength = confidence x |delta|` is computed on the confidence **corrected by that bucket's historical hit rate**, shrunk toward the raw value when the sample is small (`weight = count / (count + 10)`). Calibration therefore reorders the "Najsilniejsze sygnaly" ranking rather than merely labelling it, and each signal card shows the raw and the calibrated confidence next to each other with the bucket's sample size (`85% → 58% po kalibracji (n kubełka: 40)`). It is render-only: nothing is persisted, and in particular the `confidence_calibration` column from migration `016` (an LLM judge's post-hoc score) is never overwritten. The flag is independent of `calibration_curve_enabled` on purpose — one draws the Track Record section, the other changes the ranking.

`messenger_digest_enabled` fixes a real, silent failure. `TelegramNotifier` and `SlackNotifier` used to receive the **full** plain-text report, which routinely exceeds Telegram's 4096-character limit: the API answers `400` and the push disappears. Worse, the per-subscriber fan-out branch skipped `notifier.send_report` entirely, so push never fired once anyone was subscribed. With the flag on, push channels leave the email `CompositeNotifier` and instead receive a 5-line digest (cycle headline counts plus a closed-prediction scorecard) ending with a one-line investment disclaimer, hard-capped at 1500 characters with the disclaimer's length reserved before the clamp and sent **once** per cycle over the full results, independent of the fan-out. Zero cost — the Telegram Bot API and Slack webhooks are free. With the flag off the legacy composite is preserved bit-for-bit.

`model_scorecard_enabled` (migration `019`) surfaces the repo's strongest honesty signal, which users never saw: the walk-forward gate that refuses to ship a model worse than the naive baseline. Each Slow Loop run records one row **per symbol** (that symbol's own walk-forward evaluation, which never writes weights) plus one row with `symbol = 'ALL'` for the shared model, the only one that can ship weights; without the `symbol` column the rows would be indistinguishable. The report reads the **latest run only** (`latest_run_indices`: a gap of more than 2 hours between rows starts an earlier run, so the 30-day read window no longer merges weekly runs). Its main verdict, "accepted N, rejected M, skipped K", comes from the shared model's `ALL` row, because that is the only model that can ship weights; the per-symbol evaluations follow on a separate line, "gate passed N, failed M, skipped K" (`evaluated_passed_gate` / `evaluated_failed_gate` / anything else), instead of being counted as skipped next to the shared model. A run without an `ALL` row (history from before the shared model) still aggregates all its rows into one verdict. Then comes the RMSE against baseline of the newest shipped candidate in that run (or of the newest candidate with metrics when none shipped), labelled with its symbol and sample count, plus directional hit rate, fold count, and a `STALE` badge past 21 days. A manual re-run on the same day still merges with the scheduled run. A run where every candidate was rejected renders as exactly that; it is deliberate, uncomfortable truth rather than a bug. When the Fast Loop has no trained model loaded (cold start), the section says so instead of claiming the report runs on a proven earlier model. The section always carries `METRIC_NOTE`, which states that the metrics describe the *candidate on walk-forward folds* while the shipped model is refit on all data — without it a trust section would itself be dishonest. Writes are best-effort: a missing migration cannot break training.

`model_scorecard_baselines_enabled` (**requires migration `028`**) adds the gate's two newer baselines to each scorecard row: `drift_baseline_rmse` (the mean target of each fold's training part, predicted as a constant) and `llm_baseline_rmse` (`llm_trend_signal` times the mean absolute target of the fold's training part). The walk-forward gate has to beat the strongest of these and the zero-return `baseline_rmse` by the same 2% relative margin whether or not the flag is on; the flag only decides whether the two values are persisted. With them, the model card prints all three baselines and names the strongest; rows written before the migration or with the flag off render exactly as before. The flag ships **off**: before the migration the new keys return `PGRST204`, and because the scorecard write is best-effort the whole row would be lost without breaking training.

`cycle_diff_enabled` adds a "🔄 Zmiany nastawienia" section: the council flipping BUY→SELL on a symbol, a sentiment jump past 0.2, or a consensus drop past 0.25, all measured against the previous stored cycle. It needs no migration — the verdicts have been sitting in the `council_verdict` JSONB since `005`. Two guards make it trustworthy rather than dramatic. Comparisons older than 48 hours degrade to `STALE_COMPARISON` and render with the age spelled out ("porownanie z cyklu sprzed N dni") — the Fast Loop cron is commented out, so "yesterday" is often last week. And a symbol with no *fresh* verdict (filtered out by the volatility gate) is skipped entirely, so an old flip cannot resurface cycle after cycle. Zero cost: a Supabase read of data already paid for.

`receipts_enabled` (migration `020`) persists the evidence chain behind each prediction into a `decision_receipts` JSONB column: the RAG analogues actually used (now carrying their `id` and `similarity`, which the code used to discard), the SHAP-lite feature attributions, the **effective** volatility threshold after regime and earnings multipliers, and a `schema_version` from day one. Until now those artefacts were computed, rendered into one email and thrown away, so a prediction that turned out wrong could not be audited. The flag is a **precondition for graceful degradation, not a preference**: writing a new key before the migration exists returns `PGRST204` and kills the entire prediction write — the same gate `vector_memory_enabled` uses for its column. Zero cost — the data was already paid for this cycle. The MVP deliberately leaves provenance badges out (`AgentState` does not carry them; WIA-66 will add them to `schema_version: 2` as an optional `provenance` key without another bump). Since WIA-20 the receipt is written at `schema_version: 2` whenever the cycle has a prediction recipe (see `recipe_version_enabled` below): every v1 key keeps its meaning, and the flat recipe fields plus `recipe_version` are added. JSONB needs no migration for the new keys, so v2 receipts start with `receipts_enabled` alone. The reader `read_decision_receipt` (`src/application/decision_receipt.py`) accepts v1 and v2, tolerates any missing optional key and returns `None` for an unknown version instead of guessing.

`feature_set_version_enabled` and `feature_set_filter_enabled` (both **require migration `027`**) separate the two meanings of `news_volume_24h`. Since commit `3738ef2` the Alpha Vantage feed is bounded to the last 24 hours; older rows counted relevant articles among the 50 latest of any age, and the feature kept its name. `FEATURE_SET_VERSION` in `src/application/ml_features.py` is the current version (`3`; `1` = the unbounded feed, `2` = the 24-hour window over the merged feed of the whole watchlist, `3` = the lazy per-symbol feed of FIN-04, where `news_volume_24h` counts only the up to 50 articles of the symbol's own request). With `feature_set_version_enabled` the Fast Loop stamps `prediction_logs.feature_set_version` on every prediction; with `feature_set_filter_enabled` the Slow Loop reads only rows of the current version from `ml_feature_store` (rows of version `1` and rows with an unknown, `NULL`, version drop out). Migration `027` backfills version `1` only where it is certain, for rows timestamped before the commit (2026-10-18 21:47:22 UTC); later rows without a stamp stay `NULL`, because the moment the new code reached production is not recorded in the database. The filter cuts the training history, so until enough rows of the current version settle the shared model is skipped: the result carries `status = skipped`, `n_samples` and `feature_set_version`, the Slow Loop logs a warning, and the scorecard row keeps `n_samples`. Both flags ship **off**: writing the key or filtering on the column before the migration returns `PGRST204` (the whole prediction write fails) or `400` (training fails). Turn the stamp on right after the migration, so current-version rows start to accumulate; turning the filter on is the moment the model stops learning from old-meaning rows.

`recipe_version_enabled` (**requires migration `030`**) stamps `prediction_logs.recipe_version` on every prediction: the sha256 of the prediction recipe, so the track record can be split by recipe instead of mixing prompts, models and council line-ups. `main_agent.build_prediction_recipe` computes the recipe **once per cycle** and injects it through one field, `AgentGraphDeps.recipe`. Its parts are the provider and model of the main LLM (with `model_routing_enabled`: provider `routing`, model `openai:<cheap>|<provider>:<frontier>`), the council provider and model, `prompt_sha256` (the source of the prompt template modules `prompts.py`, `council_prompts.py`, `_prompt_safety.py`, not the rendered prompt, which differs per symbol), `personas_sha256` (file names and bytes of `data/council_personas/*.json`), `config_hash`, `model_version` (`cold_start` without a weights file, otherwise the sha256 of the `.ubj`) and `universe_version` (the sha256 of the sorted set of `symbols` + `crypto_symbols`; order and duplicates do not matter, so adding or removing a ticker starts a new segment instead of passing for a change in accuracy). `config_hash` (`Settings.config_hash()`) hashes the sorted settings that shape the forecast. `src/config.py` splits every `Settings` field into exactly one of three lists, and a test fails when a field is in none or in two: `SECRET_SETTINGS_FIELDS` (API keys, tokens, database credentials, e-mail addresses, push targets, the SEC contact header; another test fails when a field with a secret-looking name is missing from it), `NON_RECIPE_SETTINGS_FIELDS` (presentation and delivery such as `display_timezone`, the notification, push, subscription, web-digest and public-scorecard switches and output paths; report sections computed after the prediction such as VaR, stress test, track record, calibrated ranking, cycle diff and `track_record_days`; the paper-PnL cost assumptions `paper_cost_bps` and `crypto_paper_cost_bps`; write-only switches such as `db_writes_enabled`, `receipts_enabled`, `feature_set_version_enabled`, `recipe_version_enabled`, `regime_tagging_enabled`, `feature_snapshots_enabled`, `interval_coverage_enabled`, `gate_delta_enabled`, `experiment_arms_enabled`, `model_scorecard_baselines_enabled` and attestation; other jobs and training: shock watch, deadman, calibration judge and `feature_set_filter_enabled`, whose effect reaches predictions only through new weights, which `model_version` already records) and `RECIPE_SETTINGS_FIELDS` (thresholds, models, providers, symbols, data sources and every switch on the prediction path, `tool_use_*` included, and the `experiments` definitions, whose arms change prompts). The first two lists are cut out before serialisation; a field in neither stays in the hash. When it is unclear whether a field changes the forecast, it stays in the recipe, because splitting one recipe into two segments is safer than merging two recipes into one: `symbol_throttle_seconds` and `symbol_concurrency` (concurrency above 1 turns contagion off, and the throttle keeps the council clear of rate limits), `risk_symbols`, `risk_symbol_types` and `nbp_enabled` (they feed the market regime that can tighten the gate), `reflection_min_age_hours` and `reflection_max_age_hours` (which mistakes reach the prompt), and `ml_model_path` and `council_personas_dir` (their contents are hashed separately). The commit and the run (`git_sha`, `run_id` from `RunContext`) go into the v2 receipt for audit but not into `recipe_version`, so one recipe across many runs stays one segment. Two side effects to know: the prompt hash changes on cosmetic edits of those modules (a comment, a docstring), and `config_hash` changes with any field of `RECIPE_SETTINGS_FIELDS`, including the cautious ones listed above. With `receipts_enabled` the same recipe fields land in the v2 receipt even while this flag is off. Rows written before the migration or with the flag off keep `recipe_version = NULL`; the migration has no backfill, because the recipe of old rows cannot be rebuilt from the database. `uv run python main_tools.py evaluate --by-recipe` adds the directional hit rate per recipe version (rows without a version form the `unversioned` segment); it also needs the migration. `--by-universe` does the same per universe version, read from the v2 receipt (`decision_receipts->>universe_version`), so it needs no new migration; rows without a v2 receipt are `unversioned`. Universe versions of rows written before the v2 receipt are not reconstructed: the universe lives in `config.toml` only since 2026-06-03, and before that production read the unversioned `vars.SYMBOLS` repository variable. The flag ships **off**: writing the key before the migration returns `PGRST204` and the whole prediction write fails.

`feature_snapshots_enabled` (**requires migration `031`**) writes one point-in-time feature vector per symbol and cycle to the `feature_snapshots` table (`symbol`, `as_of`, `feature_set_version`, `features` JSONB, `gated`), from both terminal nodes of the graph, next to the price snapshot, so an **ignored** cycle gets a row too. The exception is a re-baseline cycle after a pause (a reference price older than 96 h, `SkipReason.STALE_REFERENCE`): its `snapshot_delta` is many days of drift, not a cycle move, so it saves only the new price snapshot and no vector. Until now the training data (`ml_feature_store`, built from `prediction_logs`) held only the cycles that passed the volatility gate: the model learned from the days with a large move, and the samples per symbol took months to collect. The free features (`FREE_SNAPSHOT_FEATURES` in `src/application/ml_features.py`) are written in every cycle and come only from data already in the cycle state, with **zero new external calls, free ones included**: the price and the previous snapshot price, the change against that snapshot (`snapshot_delta`, the one that drives the gate, not the model's `price_delta` against the previous prediction) and its absolute value, the effective threshold after the regime and earnings multipliers, the canonical regime key and both multipliers, the Alpha Fusion score, the asset type and the valuation verdict from the fundamentals cache. A missing source is written as `null`, never as `0.0`, so silence does not pass for a neutral market. A cycle that passed the gate (`gated = true`) adds the paid features: the `ML_FEATURE_COLUMNS` vector exactly as the model received it, the LLM `confidence_score` and the `data_quality_flags` (training can drop the "SIDEWAYS 50%" placeholder written after an LLM failure). No realised volatility over a price window is stored, because the state does not carry one and reading the history would be a new call. The label is **not** stored: the return is joined later from `price_snapshots` by `(symbol, as_of)`. The rows are idempotent per symbol and UTC hour (generated `as_of_hour`, upsert like `price_snapshots`), `feature_set_version` is `FEATURE_SET_VERSION`, and a failed write is logged without stopping the cycle. Training from these vectors, a second model on the free features and the gated vs non-gated selection report are not built yet; history has no stored vectors, so that training starts from zero rows. The flag ships **off**: before the migration the table does not exist and every cycle would log a failed write. It is outside `config_hash` (a write-only switch; the forecast is the same with it on or off).

`interval_coverage_enabled` (**requires migration `032`**) stores the 80% interval of each prediction and measures it. The interval itself needs no flag and no migration: every cycle that passes the volatility gate computes it in `predict_node` and the email shows it under the expected move ("80% przedział: −2.1% … +2.4% (n=57)", in the HTML and the plain-text email). `src/domain/conformal.py` holds the method. The calibration window is the settled predictions of the same asset class (STOCK, ETF, CRYPTO) from the last 90 days, read once per cycle with `RepositoryPort.get_settled_moves` (a free Supabase read of columns that already exist, zero paid calls), oldest first, capped at the 250 most recent. Settled predictions, not all price snapshots, because only a cycle past the gate gets an interval: calibrating on the same selection of large-move days keeps quiet days from narrowing it. With trained weights the interval is split conformal around the model's return: ŷ ± the finite-sample quantile `ceil((n+1)(1−α))`-th smallest of the window's `|y − ŷ|`, where `ŷ` is the return the stored target implied; on cold start the predictor is 0 and the bounds are the empirical return quantiles of the window, `floor((n+1)α/2)`-th and `ceil((n+1)(1−α/2))`-th smallest, so the interval can be skewed. α = 0.2 (80%). Adaptive conformal inference (ACI, step γ = 0.005) replays the window in time order: each point gets the interval built from the points before it, and a miss lowers α_t (`α_{t+1} = α_t + γ(α − err_t)`), so a run of misses after a volatility shift widens the interval; when α_t falls below what the window can support, the widest finite interval (the window's extreme) is used. With fewer than 20 points in the class the email says "za mało historii (n/20)" instead of a number. Points settled by this cycle's own `reflect` arrive in the next cycle's window. **The coverage guarantee assumes exchangeability of the window and the new prediction, and markets do not satisfy it**: volatility clusters and regimes change, so the nominal 80% is a target, not a promise; ACI mitigates a shift in the distribution but guarantees nothing. That is why the flag exists: it writes `interval_low` and `interval_high` (prices, the same scale as `predicted_target_price`) on every saved prediction with an available interval, and the Track Record compares the realised coverage of settled intervals with the nominal 80% ("Pokrycie przedziałów 80%: zrealizowane 74% (37/50) vs nominalne 80%"). The flag ships **off**: writing the keys before the migration returns `PGRST204` and the whole prediction write fails, and reading the columns returns `400`. It is outside `config_hash`: the interval describes the uncertainty of the forecast, it does not change the trend, the target or the recommendation.

`gate_delta_enabled` (**requires migration `034`**) stores on every saved prediction the price change that opened the volatility gate, `prediction_logs.gate_delta`: the fraction (`0.031` = +3.1%) against the price snapshot of the previous cycle, the same value the gate checked and the LLM saw in its prompt. A cold start without a previous snapshot writes no value. The offline echo test reads it (`uv run python main_tools.py evaluate --echo`, see [running-locally](running-locally.md)): if the LLM trend mostly repeats the sign of that move, a free rule gives the same call at no cost. The migration backfills the history from `price_snapshots`: for each prediction, the newest snapshot of the same symbol taken **strictly before** the prediction, because the gate compared against the latest snapshot at the start of the cycle and the cycle's own snapshot is written after the prediction. It is an approximation: a snapshot written between the start of the cycle and the prediction (an overlapping manual run) would be taken instead, the stored current price is rounded to 4 decimals, and a prediction without an earlier snapshot, or with a snapshot price of 0, stays `NULL`. The flag ships **off**: writing the key before the migration returns `PGRST204` and the whole prediction write fails. It is outside `config_hash`: the delta is recorded, it does not change the forecast. The echo result is printed only by `evaluate`, never in the email or the weekly recap.

`experiment_arms_enabled` (**requires migration `037`**) stores the arms of the experiments active in the cycle on every saved prediction, `prediction_logs.experiment_arms` (`{"EXP-02": "blind"}`); a cycle without an active experiment writes no value, so the column stays `NULL`. The same arms already reach the v2 decision receipt as the optional key `experiment_arms` with `receipts_enabled`, which needs no migration, so `evaluate --experiment` works before `037`: it prints "kolumna experiment_arms niedostępna — uruchom migrację 037; ramiona z kwitu decyzyjnego" and reads the receipt. The migration backfills the column from that receipt key. The flag ships **off**: writing the key before the migration returns `PGRST204` and the whole prediction write fails. It is outside `config_hash`: it only records the arm. See [Experiments](#experiments).

`settled_at_windows_enabled` (**requires migration `029`**) counts the "closed in the window" reads by the moment a prediction was settled instead of the moment it was made. Migration `029` adds `prediction_logs.settled_at`; a trigger stamps it with the database time when `actual_price_after_12h` first goes from `NULL` to a value, and scoring a settled row again does not move it. Before, both windows filtered on `timestamp`: a Friday prediction settled on Monday was already older than 24 hours, so it missed the email's closed-predictions section, and the Sunday recap still saw it open while a week later it was outside the 7-day window. With the flag on, the email lists the predictions settled since the current cycle started, under the heading "Zamknięte predykcje (rozliczone w tym cyklu)", so a settlement shows up in the digest of the cycle that made it; the preheader count, the lead's hit/miss labels and the push digest scorecard read the same rows. The weekly recap reads the predictions settled in the last 7 days. Rows settled before the migration get an approximate `settled_at`: the first price snapshot of the symbol at the settlement price taken at least an hour after the prediction, because the settling cycle writes its snapshot at the price it settled with. Without such a snapshot the backfill falls back to the prediction's own `timestamp`, which is only a lower bound; those rows have `settled_at = timestamp`. The flag ships **off**: before the migration, filtering on the column returns `400`, so the email would lose the section and the recap would be skipped. With the flag off, both reads, the heading and the 24-hour window are exactly as before.

`shock_alerts_enabled` (migration `021`) adds a **fourth entry point**, [`main_watch.py`](../main_watch.py), designed for an hourly cron that runs **24/7 rather than only during NYSE hours** — BTC and ETH trade around the clock. **Status: that cron runs** (resumed on 2026-10-23 after a pause from 2026-10-16); it does not depend on the Fast Loop. Since ALR-02 the watch no longer needs Fast Loop snapshots to see a move: it first reads the **day's change from the same free quote** (`DailyChangePort`: Finnhub `dp`, the move since the previous close, for stocks; CoinGecko's 24-hour change for crypto) and falls back to the Fast Loop snapshot only when that reading is missing, fails, or is not from the run's UTC day. A reading from another UTC day never alerts — on Saturday Finnhub still reports Friday's `dp` with Friday's timestamp `t`, and alerting on it would repeat Friday's alert under a new `alert_date`. Crypto has one more guard: CoinGecko's 24-hour change still contains a move for a day after it happened, so a crypto symbol whose previous alert (`shock_alerts.created_at`) is less than 24 hours old gets no alert from the daily change — otherwise a move alerted at 22:00 UTC would alert again after midnight under the next `alert_date`; stocks keep the UTC-day rule. A fresh reading decides the symbol on its own (no snapshot read, no price fetch), so one run sends at most one alert per symbol, and the push says which reference it used ("od poprzedniego zamknięcia", "w ciągu ostatnich 24 h" or "od ostatniego snapshotu ceny"). The workflow guard (`tests/test_shock_watch_env_wiring.py`) allows the watch cron without the Fast Loop cron as long as `main_watch.py` wires that daily-change source. It answers the one thing a once-daily digest cannot: an -8% move on BTC at 14:00 should not wait until tomorrow morning. Cost is **zero paid API calls** — free price sources (Finnhub / CoinGecko), a Supabase read, and free push channels; no LLM, no Alpha Vantage, no embeddings. Two hard contracts protect the rest of the system. The watch **never calls `save_price_snapshot`**: overwriting the snapshot hourly would make the Fast Loop measure its delta against an hour-old price instead of a cycle-old one, quietly shutting the volatility gate. And a **one-alert-per-symbol-per-day debounce** — enforced both by the domain predicate and by `UNIQUE(symbol, alert_date)` — keeps a chaotic market from training you to ignore the channel. On the snapshot fallback, a price snapshot older than 30 hours suppresses the alert entirely, because a stale reference point manufactures false alarms. The age is checked **before** the current price is fetched, and a run in which no symbol had a fresh daily change and every snapshot is stale logs a `Shock watch ślepy` WARNING instead of reporting a healthy-looking "0 alerts".

`liveness_fast_loop_max_gap_h` / `liveness_slow_loop_max_gap_h` drive the deadman, [`main_deadman.py`](../main_deadman.py) (daily cron, zero paid calls). It reads the newest `price_snapshots` row (Fast Loop) and `model_scorecards` row (Slow Loop, written per symbol and for the shared `ALL` model even when training is skipped) and mails through Resend when a job has been silent longer than its gap in hours. `0` means the job is deliberately paused and not checked — production sets the Fast Loop to `26` (an alert after two NYSE trading days without a cycle; it was `0` while the cron was paused) and the Slow Loop to `192` (a week plus a day of GitHub cron slack). Without it, a dead Slow Loop looked exactly like a quiet week. The Fast Loop is counted in NYSE trading days (NIEZ-11, the session calendar in `src/domain/market_calendar.py`), because an hourly gap would fire after every weekend and holiday for a job that runs once per trading day: each trading day has a deadline at 00:00 ET plus `liveness_fast_loop_max_gap_h`, and the Fast Loop is overdue once the latest passed deadline has no `price_snapshots` row written since 00:00 ET of that day. Weekends and NYSE holidays have no deadline. With a gap of `26` the deadline of a trading day is 02:00 ET the next day, so one skipped run is tolerated when the next cycle arrives and two missed trading days raise the alert; a gap below the deadman's check time (09:17 UTC, 04:17 ET in winter) reports a missed run the same morning. The value stays `0` while the Fast Loop is paused; set it when the schedule is resumed. The Slow Loop keeps the hourly rule.

`options_flow_enabled` now does more than fill a table cell. With it on, the options port is fetched inside `_predict_node` — naturally **behind the volatility gate**, so a quiet cycle never pays for it — and the model's predicted move is compared against the move the options market implies (`implied_move_12h`, sqrt-time scaled). The report shows a **qualitative label** (`MODEL_AHEAD` / `MARKET_AHEAD` / `ALIGNED`), not a two-decimal sigma, and `edge_sigma` is persisted (migration `025`) so the hypothesis can be falsified later: does the `edge > 1.5σ` subset actually beat the rest? Two methodological caveats are stated in the module docstring rather than hidden: `implied_vol` is a chain-wide average, not the front-month at-the-money, and sqrt-time over calendar hours **overstates** the move across a weekend. The signal is informational and deliberately carries no decision-making role until validated on closed predictions. With the flag off, no options port exists and the cycle is byte-identical.

`alpha_fusion_enabled` (migration `022`) closes the repo's largest wasted investment. Five alpha sources were fetched, classified against domain thresholds, and then rendered **only into a table**: insiders could be buying by the million and neither the LLM prediction nor the seven XGBoost features would know. Fusion is a weighted sum of the *existing* domain classifications, renormalised over whichever sources are actually present, so a symbol with one available source is not silently penalised. A social snapshot **without sentiment** counts as absent, not as present-neutral: Reddit search returns mention counts only, so that vote could never carry a direction and would merely drag the other sources towards zero with its 0.20 weight. The Reddit adapter also returns no snapshot when its week search fills the whole 100-post page — the count is then a ceiling, and the understated baseline would report a false `SURGING`. The score reaches both the LLM prompt — **with its per-source breakdown**, so the composite stays auditable rather than becoming a black box — and `ml_feature_store` as an eighth feature. Enrichment had to move **before** the graph to make that possible; it previously ran after, which is precisely why the signals never reached anything. The paid-call count is unchanged: `enrich` already ran once per symbol, just later. In the view the column is `COALESCE(alpha_fusion_score, 0.0)` so `dropna` cannot cut the historical rows out of training (a train/serve skew the migration test freezes). Whether the hand-picked weights are signal or noise is decided by the walk-forward "beat the baseline" gate, not by intuition — which is why the flag is off by default in code. Production `config.toml` turns it on.

`attestation_enabled` (migration `024`) is built to make the track record **cryptographically checkable**. At prediction time a SHA-256 commitment over the canonicalised prediction plus a random salt is written to `prediction_logs` and the **hash alone** is appended to a public JSONL file — until the salt is revealed the hash discloses nothing. Once the prediction settles, a **sweep** reveals every matured commitment (salt and plaintext), and `revealed_at` is stamped only *after* a successful publish, so a miss can never be marked-revealed-but-never-published. The sweep is deliberate rather than a reveal-on-settle hook: predictions for symbols later removed from `config.toml` would otherwise never be revealed, and to a sceptic that looks exactly like hiding losses. **Be honest about what this proves:** git commit dates are forgeable. The claim is *tamper-evidence under branch protection*, not an unforgeable timestamp. Canonicalisation is frozen by golden tests and carries a `schema_version` from the first commit, because a canonicalisation bug breaks verification of history with no way to repair it retroactively. `portfolio_positions_enabled` (migration `023`) replaces a fiction. `stress_test` and `portfolio_pnl` computed on **equal weights**: someone holding 40% in NVDA received a VaR calculated as though they held 2.3% of each of 43 tickers. A `positions` table now feeds a `Portfolio` aggregate with real weights (renormalised over the symbols that actually have a current price), unrealised P/L per position, and the exposure of each stock sector from `sectors` (a sector, not a measured correlation cluster) — your three largest positions in one sector are 61% of capital. Until `sectors` filled `peer_groups`, the groups were empty, so neither the warning nor the sizing exposure ever fired. Amounts in PLN come from NBP rates passed to the renderer as **values** (`ReportContext.portfolio_fx`, see `fx_rates_cache_enabled` below), never by injecting a port into the renderer. A **STALE badge is a requirement, not decoration**: the positions table is maintained by hand, and a stale portfolio produces a *false* P/L, which is worse than no section at all. A Supabase error degrades to no section rather than to wrong numbers. A position the cycle could not price (for example a ticker in `symbols_unsupported_price` such as `XDWD.DE`) is never dropped silently: the section lists it under the table as "Bez wyceny w tym cyklu: XDWD.DE, IUSN.DE (≈ X% kosztu)", with its share of the total **cost** basis (`Portfolio.unpriced_symbols` / `unpriced_cost_share`), and the totals are labelled "bez pozycji niewycenionych", because the weights of the priced positions are renormalised without it. A position in a symbol outside the watchlist (`symbols` + `crypto_symbols`) and outside `symbols_unsupported_price` gets a price from the free quote endpoint only (`build_market_port`: Finnhub `/quote` or CoinGecko), fetched sequentially while the report is built and passed as `ReportContext.held_prices`. It never writes a `price_snapshots` row, never enters the graph and never triggers an LLM, Alpha Vantage or embedding call; adding the symbol to `symbols` instead would pay for a full analysis on every move past the volatility gate. A failed quote leaves the position unpriced. Phase 2 is now in: `suggest_band` knows the existing exposure. Suggesting a "full 4-5% position" to someone already holding 40% of their capital in that symbol was advice computed on an empty portfolio. Both `current_weight` and the exposure of the symbol's **sector** can only ever *narrow* the band — three positions in one sector are one position wearing three hats. Monotonicity is the contract: an empty portfolio is absence of information, never a buy signal, so exposure never upgrades a weak signal. Both arguments default to `None`, preserving the pre-phase-2 behaviour exactly. Portfolio risk is the third input. With `portfolio_var_enabled` on and real positions loaded, `main_agent` measures the positions actually held (`PortfolioRiskUseCase.position_risk`): the free `price_snapshots` history of the held symbols only, weighted by each position's market value at its latest snapshot and renormalised over the held symbols that have history. `suggest_band` applies it after the exposure, and each signal is its own step: a 1-day VaR95 of at least 3% (`VAR_TIGHTEN_THRESHOLD`, from 60 returns as in the radar) lowers the band one step, a current drawdown of the portfolio at least 15% below its peak in the 90-day window (`DEEP_DRAWDOWN_THRESHOLD`) forces the starter band, and held hedges that do not move against the rest of the portfolio (hedge effectiveness below 0.3, from 20 paired returns) lower it one step. A hedge is a held instrument typed `INVERSE_EQUITY` or `VOLATILITY` in `risk_symbol_types` (`EQUITY_HEDGE_TYPES`, `src/domain/hedge.py`); a held GLD, EPOL or TBT is an investment, not a hedge of the stock book, and never lowers the band. Like exposure, risk can only narrow the band. With the flag off or without positions the band is unchanged; the radar's VaR, computed on equal watchlist weights, never sizes anything. The global hit rate stays the track-record input. The flag stays outside `config_hash`: the band is rendered after the prediction and changes no stored forecast.

`positions_currency_enabled` (**requires migration `035`**) gives each position its currency and its real purchase date. Migration `035` adds `positions.currency` (ISO 4217, `NOT NULL DEFAULT 'USD'`, three capital letters enforced by a check) and `positions.purchase_date` (`DATE`, `NULL` = unknown). It backfills the currency of the rows that exist when the column is added from the ticker suffix: `.DE`, `.AS`, `.PA`, `.MI`, `.MC` → `EUR`, `.L` → `GBP`, anything else → `USD`. London quotes are often in pence (GBX) and some `.L` ETFs trade in USD; the migration converts nothing, so correct such a row with the import below. A rerun of the migration does not overwrite a currency set later. Existing rows keep `purchase_date = NULL`: `as_of` is the date the table was last updated, not a purchase date. With the flag on, `SupabasePositionsAdapter` reads both columns (a row without them reads as USD with an unknown date, so turning the flag on early does not fail) and stops using `as_of` as the purchase date; with it off the adapter keeps the old mapping (USD, `as_of` date). The flag also lets `uv run python main_tools.py import-positions --csv <file> --apply` write the two columns (see [running-locally](running-locally.md)); off, the import writes only `symbol`, `quantity`, `avg_cost` and `as_of` and refuses a file with a non-USD currency or a purchase date, because writing it would silently drop them. The flag ships **off**: writing the new keys before the migration returns `PGRST204`. It is outside `config_hash`: the currency changes the report, not the forecast.

The 💼 section's P/L in złoty (PORT-11) values the cost at the NBP rate of the purchase date and the current value at the current rate, then splits the result into the instrument and the currency effect: `P/L zł` = quantity × current price × current rate − quantity × purchase price × purchase-date rate, of which `w tym kurs` = quantity × purchase price × (current rate − purchase-date rate), and the instrument part = quantity × (current price − purchase price) × current rate; the two add up to the P/L. Buying 10 shares at 100 USD with USD/PLN at 4,00 and holding them at 100 USD with USD/PLN at 4,40 is +400 zł, all of it currency. This is an economic result at the NBP rate of the purchase date, not a tax base: Polish income tax (PIT, art. 11a) uses the NBP rate of the last business day before the transaction. Each position uses the rates of its own currency (`Portfolio.pln_pnl`, `src/domain/portfolio.py`); a PLN position has no currency effect. With `nbp_enabled`, `main_agent` collects the rates while the report is built (`collect_pln_rates`, `src/application/portfolio_fx.py`): the current rate of each foreign currency for today in Warsaw and the rate of each (currency, purchase date) pair, from the NBP table A endpoint `/api/exchangerates/rates/a/{code}/{date}/`. A day without a table (weekend, holiday, before the table is published around noon) returns 404 and the adapter steps back day by day to the previous business day, at most 10 days (`MAX_LOOKBACK_DAYS`); any other error gives no rate and stops further NBP calls for the rest of the cycle, because with NBP down every call is a timeout with retries and dozens of purchase dates would exceed the job's time limit. These calls are free (NBP needs no key), outside the graph and the volatility gate. A position without a purchase date (every position before migration `035` and `positions_currency_enabled`, because `as_of` is not a purchase date) says `kurs z dnia zakupu nieznany` in the `w tym kurs` cell and `—` in `P/L zł`, instead of a P/L computed with the current rate on both sides, which would hide the currency effect; a missing NBP rate for the purchase date says `brak kursu NBP z dnia zakupu`, a missing current rate `brak kursu XXX/PLN`. The totals line names the current rates it used (`W PLN (kursy NBP: EUR 4,2710 · USD 3,6820)`), sums the value of every position with a current rate and the P/L and its currency part of the complete positions only, and lists the others (`bez P/L w zł: AMD, NVDA`). When the rate collection fails, the section falls back to the current USD/PLN and EUR/PLN of Risk Watch without purchase-date rates. Position amounts are shown in the position's currency; when the priced positions hold different currencies the native totals line says so instead of adding dollars to euros. The whole portfolio is measured in one currency, złoty, whenever rates are known: the weights in the 💼 section and in the lead (`AAPL (50% portfela)`), the sector exposure of the concentration warning and of the sizing band, the symbol weight the sizing band sees, the unpriced positions' share of the cost and the change since the previous email all use `Portfolio.pln_prices` (price × current NBP rate of the position's currency) instead of adding dollars to euros; `main_agent` passes the same rates to `PortfolioRiskUseCase.position_risk`, so the VaR, drawdown and hedge weights of the sizing band are in złoty too. A position whose currency has no rate (or a symbol held in two currencies) drops out of all of them and the section says so under the table: `Bez kursu NBP: VUSA.L — poza wagami i sumami w zł`; it is never treated as USD. Returns stay in the quote currency, so the currency move is in the P/L split but not in the VaR. Without any rate (`nbp_enabled` off) the old native amounts remain, which is only right for a single-currency portfolio. GBX risk: migration `035` maps `.L` tickers to `GBP`, but London quotes are often in pence; if the price source returns pence for a position stored as `GBP`, every złoty amount and weight of that position is 100 times too large, so check `.L` positions and set their currency explicitly with the import. Other subscribers (`subscriptions_enabled`) never receive the rates, like the rest of the portfolio. `fx_rates_cache_enabled` (**requires migration `036`**) adds a read-through cache of past-day rates in the `fx_rates` table (key `currency`, `on_date`; `effective_date` is the NBP table the rate came from), so a purchase-date rate is fetched from NBP once. Only days before today in Warsaw are cached, because today's rate before publication is yesterday's. A cache read or write error is logged and the rate comes straight from NBP. The flag ships **off**: before the migration the table does not exist. Both flags are outside `config_hash`.

`portfolio_var_enabled`, `stress_test_enabled` and `hedge_effectiveness_enabled` add VaR/CVaR, a beta-based stress test and hedge effectiveness to the 🎯 Portfolio Radar and Risk Watch sections, all computed from free `price_snapshots` history (zero paid calls). With real positions, `portfolio_var_enabled` also lets the risk of the held portfolio narrow the sizing band (see above). Series of different symbols are paired by **UTC day** (`align_by_utc_day`, `src/domain/correlation.py`): snapshots written in one cycle differ by seconds, so the exact-timestamp intersection used to be empty and the radar, VaR, stress test and hedges silently disappeared. When a day has several snapshots the latest one wins, and only days present in every series are kept. An hourly bucket would split one cycle across two hours. Minimum samples (`src/domain/risk_sample.py`) keep a handful of points from posing as risk statistics: VaR/CVaR needs `MIN_VAR_OBSERVATIONS = 60` daily returns, and correlations, clusters and the stress-test betas need `MIN_PAIRED_RETURNS = 20` paired returns. Below that the statistic is not computed and the section says "za mało historii (n/60)" (or `n/20`) in both the HTML and the plain-text email instead of going blank or printing a VaR that is just the worst day of the sample. The radar reads a 90-day window (`PRICE_HISTORY_DAYS`), roughly 63 sessions, so VaR can appear at all; `get_price_history` reads it page by page, because PostgREST silently caps a SELECT at about 1000 rows; until the loop has collected that history (or it is backfilled) the section honestly reports the gap.

`public_scorecard_enabled` renders the one artefact that can earn a stranger's trust: a landing page carrying **aggregates only** — number of settled predictions, the directional hit rate, Brier score, ECE, the reliability curve as a div-sparkline, and the equity curve. The numbers are computed so that they mean something:

- **One definition of hit rate.** The headline is the *directional* hit rate from `directional_hit_rate` (`src/domain/equity_curve.py`): SIDEWAYS calls place no bet and stay out of the denominator; their count gets its own card. With no directional calls the card shows "—" instead of borrowing the equity curve's win rate.
- **Uncertainty.** Next to the rate: a 95% Wilson interval (`src/domain/statistics.py`) computed on the **effective sample size** `n_eff = n / (1 + (m̄ − 1)·ICC)` (`src/domain/significance.py`). Predictions of one cycle (UTC day of `prediction_logs.timestamp`) move together, so 412 calls can be worth ~61 independent ones; the page prints "n=412, n_eff≈61". With at least 20 cycles a cycle-level block bootstrap adds a second interval; below that the page says the bootstrap was skipped, and below `n_eff = 5` it says the interval is very wide.
- **Naive baselines.** "Always BULLISH / BEARISH / SIDEWAYS" hit rates computed on the **same** directional predictions (after the volatility gate, not on every market day) — `naive_baselines` in `src/domain/track_record.py`.
- **Significance.** An exact one-sided binomial test (normal approximation above n = 1000) against the stronger of the two directional baselines, run on `n_eff`, with a Polish verdict such as "nieodróżnialne od rzutu monetą (p=0.41, n=37, n_eff≈12)". `benjamini_hochberg` (FDR, q = 0.10) is available in the same module for tables of many comparisons.
- **Probability scores.** Brier score, the climatological Brier (always forecasting the base rate), the Brier Skill Score, log loss and the Murphy decomposition (reliability, resolution, uncertainty) lead the calibration block (`probability_scores` in `src/domain/calibration_curve.py`). ECE stays as a secondary number, because a constant "55%" forecast at a 55% hit rate has ECE = 0 and no skill at all. Each reliability bucket shows its `n`.
- **Equity curve.** One point per cycle, equal weight per prediction within a cycle, SIDEWAYS held as cash (`paper_portfolio_curve`), net of the one-way trading cost charged on each change of a symbol's position (`src/domain/trading_costs.py`); the heading says "paper-PnL (koszt 10 bps)" with the decimal point, and the assumptions name the crypto cost. Next to it the page compares the agent with two buy&hold benchmarks that pay the same cost (WIA-21, `src/domain/benchmark.py`): the **basket** (every predicted symbol held long in the same windows, equal weight, entry cost only) and **IVV** (held long in the prediction windows, one point per agent cycle), as "agent +1.2% · koszyk +3.4% · S&P 500 +2.1%", plus the excess return over the basket and the **market-relative hit rate**: a directional call is a hit when its sign matches the sign of the symbol's return minus IVV's return in the same window, so an always-BULLISH agent in a bull market no longer scores ~55% for free; predictions of IVV itself stay in both curves but out of this hit rate, since their excess return over IVV is zero by definition. The sparkline gets a second row for the basket. The basket is an aggregate and the page names the index "S&P 500" instead of its ticker, so no watchlist symbol reaches the page — IVV is on the watchlist, so the invariant holds without exception; the private email says "IVV". **Timestamp convention:** IVV is read from the free `price_snapshots` (no paid call) and its window uses the same cycle snapshots as the prediction: the start is the IVV snapshot of the same cycle (same UTC day, the one nearest to the prediction's `timestamp`, since IVV may be written minutes before or after the symbol), the end is the first IVV snapshot at least `reflection_min_age_hours` later, which is the cycle in which `reflect_node` settles the prediction. The 05:30 UTC snapshot is the previous session's close, so both sides measure close(D−1) → close(D); calendar trading dates are never used. A missing IVV snapshot in a prediction's cycle drops that prediction from the market-relative hit rate; a cycle with no IVV window at all makes the IVV curve "brak danych benchmarku" rather than a curve with a hole. If IVV misses the settlement cycle, its window runs to the next IVV snapshot. The read covers `track_record_days + 1` days, because the start snapshot of the oldest cycle can be written just before the prediction window's cutoff. The old curve compounded parallel trades serially on 100% of capital; the page marks the methodology change of 2026-10-18.
- **Survivorship.** The methodology section says that the watchlist was hand-picked (2026-06) with knowledge of the companies' earlier rallies, so a long bias on it is not skill, and points at the naive "always up" baseline on the same predictions. The sentence names no symbol, so the anti-PII invariant holds.
- **Window.** The page states its window and generation date — "Okno: ostatnie 30 dni (2026-09-18 – 2026-10-18)" — from `track_record_days`.

Rows written by the LLM fallback (`data_quality_flags` contains `llm_analysis_failed`, a placeholder "SIDEWAYS 50%") are excluded from every track-record read, so they reach neither the hit rate nor the calibration. `web_digest_enabled` could never do this: it publishes the *full private digest*, watchlist symbols and all. A guard in [`tests/test_workflow_env_wiring.py`](../tests/test_workflow_env_wiring.py) fails while `web_digest_enabled` is on next to any `actions/deploy-pages` step or `git add` of `public/` in any workflow, and accepts a Pages artifact only when its `path` is the scorecard's directory (`dirname(public_scorecard_path)`), never `public/` or the digest's directory. The scorecard leaks nothing — a hard anti-PII test asserts the absence of email addresses, amounts and ticker symbols from the rendered page, using input that deliberately contains "NVDA" and an address. It runs through a **second** `FileWebPublisher` instance on its own path; reusing the digest's instance would have one overwrite the other. Metrics are computed independently of `equity_curve_enabled` and `calibration_curve_enabled`, because those gate sections of a private email, not a public proof. The page carries a **methodology** section: an embarrassing hit rate during a weak stretch is the point, not a bug — verifiable humility beats promises. **Status: implemented and unit-tested, not yet published.** The page is rendered to the runner's local disk only; no workflow deploys it, so `config.toml` ships the flag **off**. GitHub Pages deployment will need `pages: write` and `id-token: write`, which return to the workflow together with the deploy step.

The report also **prints its own bill**. One meter per cycle (`CycleTelemetry`, [`src/application/cycle_telemetry.py`](../src/application/cycle_telemetry.py)) counts the paid calls of the Fast Loop graph per pricing source, and the digest carries a "koszt cyklu" section: how many paid calls fired, broken down by source, and an **estimated** dollar figure. The sources are `llm` (the prediction call and the mistake diagnosis in `reflect_node`), `council_llm` (every persona, revision and chairman request, counted at the council's LLM port by `MeteredLLMPort`), `sentiment` and `news` (one each per symbol past the gate) and `embedding` (every real `embed` request). The word *estimated* is load-bearing — the unit prices in `UNIT_COST_USD` ([`src/domain/finops.py`](../src/domain/finops.py)) are an order-of-magnitude model per call, not an invoice, and the module says so; `council_llm` costs ~$0.0025 per persona or chairman call. The most interesting case renders explicitly rather than self-suppressing: a cycle where the volatility gate filtered every symbol reports **zero paid calls**, which is the entire point of the FinOps architecture.

The meter does not see every paid request. A tool-use prediction counts as one `llm` call although the loop can make up to `tool_use_max_rounds + 1` requests; `sentiment` and `news` count symbols past the gate, and so does the Alpha Vantage feed since FIN-04 (one request per symbol past the gate, plus key-rotation retries); calls made outside the graph, such as the Alpha Vantage earnings calendar and the alpha enrichment sources, are not metered. Digests sent before the council was metered per request counted a council run as one `council_llm` call priced at $0.02: a plain 7-persona run (8 calls × $0.0025) costs the same dollar figure, but the call count was understated eightfold, and debate rounds (15 calls) and late or failed requests were not priced, so council costs before and after that change do not compare one to one.

**The bill from tokens (FIN-13).** The LLM and embedding adapters (Anthropic and OpenAI, the council's adapter, both tool-use loops and the embeddings) report the token counts of every successful request to a `UsageSink` port, the in-memory `UsageLedger` of the run ([`src/application/usage_ledger.py`](../src/application/usage_ledger.py)); they know nothing about Supabase or prices. Anthropic gives `input_tokens`, `output_tokens`, `cache_read_input_tokens` and `cache_creation_input_tokens`; OpenAI's `prompt_tokens` includes the cached tokens (`prompt_tokens_details.cached_tokens`), so the adapter reports the uncached part as input and the cached part as cache read; embeddings report `prompt_tokens`. A request whose answer turns out empty or invalid is still reported, because it was billed; a response without usage reports nothing and raises nothing, and a cache hit of the embedding adapter is not a request. Who pays is added by the caller: the graph wraps every paid call in `usage_scope(source, node, symbol)` (the reflect diagnosis and the prediction under `llm`, the council under `council_llm`, the RAG and save-time embeddings under `embedding`), `MeteredLLMPort` sets the source of the council and of the Slow Loop jobs, and the council copies the caller's context into its persona threads. The domain prices each request (`price_usage` in [`src/domain/finops.py`](../src/domain/finops.py), from `llm_pricing`). In the "koszt cyklu" section a source whose every request has a price shows the cost from tokens ("2 wywołania z tokenów = $0,0123") and the others keep the unit estimate, marked "(szacunek)"; the header says when the total mixes the two and names the price date ("cennik z 20.10.2026"). A source with one unpriced request falls back as a whole, since a partial sum would understate it. A tool-use prediction is still one `llm` call in the count, but its token cost covers every round. Without token data (the price list empty, or no request reported) the section is exactly the estimate described above. Local stub runs (FIN-35) report nothing and hide the section as before. With `cost_ledger_enabled` the same ledger is written to `llm_calls` after the run.

Manual dispatches beyond the schedule are cycles outside the count, as in the Alpha Vantage budget. For `config.toml` on 2026-10-20 (42 eligible symbols, 7 personas, debate and tool use off, ceiling `100`, `symbol_concurrency = 4`, one cycle a day) the ceiling leaves the 84 `llm` calls, the 42 sentiment and news calls and the 84 embeddings as they are and cuts the council from 336 to 99 + 4 × 8 = 131 requests: 1.2112 USD a cycle, 6.06 USD a week, so `config.toml` sets the budget to `7.0`, the worst case rounded up to a whole dollar.

`weekly_recap_enabled` costs exactly **one LLM call per week** — not per symbol, not per cycle, enforced by a test — and, like the calibration judge, it runs outside the volatility gate under the Slow Loop's weekly ceiling `slow_loop_max_paid_llm_calls_per_week` (FIN-30), where it has the first share. The Slow Loop already ran every Sunday and sent the user nothing. It now composes a story: prediction of the week (the directional hit closest to its price target; a week with no directional hit shows the miss closest to target instead, titled "Najbliżej celu (kierunek chybiony)"), miss of the week (the mirror rule: the directional miss farthest from its target; a week with no directional miss shows the hit farthest from target instead, titled "Najdalej od celu (kierunek trafiony)") with the lesson `reflect_node` drew from it, the council's **vindicated dissenter** ("Soros was right while everyone said BUY"), and the week-over-week ECE delta. Each hero shows its direction verdict (✅ / ❌) and its price-target error (`1 − accuracy_score`, as a share of the entry price); `accuracy_score` measures closeness to the target, not directional accuracy, so neither the email nor the narrative prompt calls it "trafność". The direction verdict, which also drives hero selection and the recap's ECE, is the `is_trend_correct` that `reflect_node` stored (with the ±2.5% SIDEWAYS band for crypto), the same value the daily email uses; only a row without it is re-scored from its prices. That re-scoring and the "vindicated dissenter" check (did the market go UP, DOWN or stay FLAT) use the asset-class band `reflect_node` uses: ±2.5% for symbols listed in `crypto_symbols`, ±0.5% for everything else, so a +1.5% day on BTC counts as FLAT and vindicates a HOLD dissenter. A hard sample-size rule lives in the domain: **below five closed predictions no recap is built and no email goes out**, because a thin week would otherwise manufacture drama out of noise. If the LLM call fails the deterministic recap is still sent, without the narrative. A failure to *build* the LLM adapter (for example a missing SDK or `ANTHROPIC_API_KEY`) falls back the same way: the step gets an adapter that fails on every call, so the recap still goes out without the narrative and the calibration judge still stores its arithmetic. Insight text reaches the prompt through `fence_untrusted`, since `correction_insights` derives indirectly from news headlines.

**Repository variables:** none. All non-secret config lives in committed [`config.toml`](../config.toml), read directly by `Settings` — so there is nothing to map in the workflow `env:` and no `vars.*` drift to guard. The workflow injects only the secrets above; the split (secrets mapped, non-secret config kept out) is guarded by [`tests/test_workflow_env_wiring.py`](../tests/test_workflow_env_wiring.py).

## Experiments

`experiments` (EXP-05) defines A/B experiments that run inside the Fast Loop. Questions such as "does RAG help" or "is a blind council better" are causal; a before/after comparison mixes the change with the market, while a random assignment per symbol and day answers them on the same period and the same stocks. Each experiment is a block of dotted keys in [`config.toml`](../config.toml):

```toml
experiments.EXP-02.hypothesis = "..."
experiments.EXP-02.arms = ["sighted", "blind"]
experiments.EXP-02.start = 2026-11-02
experiments.EXP-02.end = 2027-01-29
experiments.EXP-02.primary_metric = "council_hit_rate"
experiments.EXP-02.enabled = false
```

- **Assignment.** `assign_arm(experiment_id, symbol, cycle_date, arms)` in [`src/domain/experiment.py`](../src/domain/experiment.py) takes the sha256 of `id|symbol|YYYY-MM-DD` modulo the number of arms, where the date is the UTC day of the cycle start. It is deterministic, reproducible and stateless: a re-run of the same day lands in the same arm, and nothing is stored to decide it.
- **Active** means `enabled` and the cycle day inside `[start, end]`, both days included. An inactive experiment has no effect at all: the cycle runs exactly as it would without it, and nothing is recorded.
- **Arms.** The first arm is the control: the status quo, the behaviour production has without the experiment. The other arms are treatments the code knows, each changing one part of a prompt: `blind` (council prompt) and `no_memory` (prediction prompt). The settings refuse to start on an unknown arm name, a treatment as the first arm, a primary metric that does not belong to the experiment's prompt part, a window that ends before it starts, or an unknown key in the block: an arm without an effect would be an A/A test passing for an experiment.
- **One experiment per prompt part.** Two **enabled** experiments that change the same prompt part with overlapping windows stop the start. The check looks at the windows, not at today's date, so a configuration that is fine today and conflicting next week fails when it is deployed rather than on the day the second window opens. This was chosen over orthogonal hashes for the same part: two treatments on one prompt interact, and with a small n per arm the interaction cannot be told apart from the main effect. Experiments on different parts may run together. Their assignments are independent because the experiment id is part of the hash key (a factorial design), so each comparison stays balanced over the other experiment's arms.
- **Metrics.** Prediction prompt: `hit_rate` (directional hit rate of the LLM trend, SIDEWAYS places no bet) and `brier` (Brier score of `confidence_score` against `is_trend_correct`, on every settled call). Council prompt: `council_llm_agreement` (the final recommendation read as a trend, BUY → BULLISH, SELL → BEARISH, HOLD → SIDEWAYS, equals the LLM trend), `council_hit_rate` (BUY and SELL against the realized move) and `council_brier` (`consensus_strength` against whether the recommendation hit; HOLD hits inside the ±0.5% band).
- **Recording.** The arms of the active experiments go into the v2 decision receipt as the optional key `experiment_arms` (with `receipts_enabled`, no migration; the receipt reader tolerates its absence) and, with `experiment_arms_enabled`, into `prediction_logs.experiment_arms` (migration `037`).
- **Cost.** Experiments add no paid calls. The volatility gate is unchanged, and the arms only change the prompts of calls that run anyway.
- **Recipe.** `experiments` is in `RECIPE_SETTINGS_FIELDS`: enabling, disabling or editing an experiment (its hypothesis text included) changes `config_hash` and therefore `recipe_version`. Both arms of one cycle share that recipe; the recorded arm tells them apart.
- **Evaluation.** `uv run python main_tools.py evaluate --experiment EXP-02 --days 90` compares the arms (see [running-locally](running-locally.md)). It reads the control arm and the metrics from the definition, so keep a finished experiment in `config.toml` with `enabled = false`.

Defined experiments (both enabled in production from 2026-10-26, the first cycle after the Fast Loop resumed, to 2027-01-29):

- **EXP-02, blind council** (`arms = ["sighted", "blind"]`, primary metric `council_hit_rate`). The personas see the main LLM's verdict ("Trend wg głównego analityka agenta: … (pewność: …)") before they decide, so seven "independent" votes may be seven echoes of one. In the `blind` arm that line is left out of both the round-1 prompt and the debate revision prompt (`CouncilInput.blind`); everything else, the ML target included, stays. Both arms make the same council calls, so the experiment costs nothing extra. It compares the council's agreement with the LLM, the hit rate of `final_recommendation` and the Brier score of `consensus_strength`; persona redundancy is not measured yet (it arrives with WIA-45). The council fires only above `council_volatility_threshold`, so it takes weeks of cycles.
- **EXP-03, memory A/B** (`arms = ["memory", "no_memory"]`, primary metric `hit_rate`). We pay for mistake diagnoses (`analyze_mistake`) and embeddings on the assumption that lessons and analogs improve the next predictions, and nobody has measured it. The `no_memory` arm leaves the lessons from `reflect` (`reflection_context`) and the RAG analogs (`similar_context`) out of the prediction prompt (`get_prediction_prompt(include_memory=False)` also drops the instruction that refers to them). The arm the entry calls "control" in the hypothesis sense is `no_memory`; in the configuration the first arm, `memory`, is the status quo that runs whenever the experiment is inactive. The `no_memory` arm runs no RAG query, but it still embeds the news summary at save time, exactly like the status quo (owner's decision, 2026-10-20): each cycle makes one embedding call in both arms, and the arm's predictions join the analog corpus, so the experiment leaves no gap in the memory that later cycles retrieve from. Settling the previous prediction in `reflect` (and its gated diagnosis) runs in both arms. It compares the directional hit rate and the Brier score of `confidence_score`. RAG retrieval runs whenever the embedding adapter exists, which `main_agent` always builds; `vector_memory_enabled` only adds the regime filter. So the arm drops both lessons and analogs, and on days when retrieval finds no analog it measures the lessons alone.
