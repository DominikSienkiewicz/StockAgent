# Configuration

The tunables and the feature flags. Setup steps are in [running-locally.md](running-locally.md).

## Configuration

All tunable parameters are a `Settings` Pydantic model in [`src/config.py`](../src/config.py) with validators. Non-secret values are set in committed [`config.toml`](../config.toml); secrets come from `.env` / GitHub Secrets. Precedence: **env var → `.env` → `config.toml` → the code defaults below** (so any field can be overridden ad-hoc via an env var). The `Default` column is the in-code fallback when a field is absent everywhere; `config.toml` ships the actual production values.

An unknown key in `config.toml` stops the start with a `ValueError` that names it (TEST-03), so a typo such as `weekly_recap_enable` cannot silently leave a flag at its code default. Only that file is strict: environment variables and `.env` also carry keys of other tools (`SONAR_TOKEN`, `GH_TOKEN`) and unknown names there are ignored.

The fallback gets the request only on a provider failure of the main adapter, once its own retries are spent — a 429 or 5xx, a timeout, a network or connection error. An empty or invalid JSON answer does not fail over (the provider did answer): it ends in the graph's neutral fallback as before. A 4xx other than 429 (bad request, bad key) is re-raised too, because the second provider would get the same broken request. The prediction and the mistake diagnosis fail over; the council, tool use and embeddings do not, and the FIN-35 stub run has no failover. The fallback's request is a paid call: it counts under `llm` in the cycle telemetry, so the FIN-12 ceiling and the cycle cost see it, and its tokens reach the same ledger with the fallback's provider and model. It runs only for a symbol already past the volatility gate. In the Slow Loop the fallback's request goes through the job's weekly allowance (FIN-30, `BudgetedLLMPort` with the job's shared `PaidCallAllowance`) and spends it like the main request: with the allowance spent the failover does not start and the main adapter's error propagates as before. When the fallback is available (`llm_fallback_provider` set and its key present, on a paid run), each Slow Loop job with a paid LLM call asks `slow_loop_paid_budget` for one more call — the recap 2, the calibration judge 2 — and only a fallback request after a main failure spends it; the weekly ceiling stays hard and trims in the usual priority order, so a tight ceiling can still leave a job with the single call of its main request. Without a fallback the allocations stay at one call per job. A prediction made by the fallback carries the quality flag `llm_failover` in `data_quality_flags`, and its recipe names the provider and model that answered (the v2 receipt's `llm_provider` / `llm_model` / `recipe_version` and the `recipe_version` column), so it falls into its own recipe segment of the track record. **Column preflight (FIN-05).** Many flags below write a `prediction_logs` column that exists only after its migration. Before the first symbol, a Fast Loop run that writes to the database (`db_writes_enabled`) selects, with `limit 0`, every column the save node can write under the current flags (`required_prediction_columns` in `src/application/agent_graph.py`). A missing column (Postgres `42703`) stops the cycle with exit code 1 and an `ERROR` naming the columns and the **DB Migrate** workflow, before any paid call — otherwise every symbol past the gate would pay for an analysis whose save fails. Any other error of that check (network, timeout) is a `WARNING` and the cycle runs on.

## Feature flags

The paragraphs below say what a flag does, when to turn it on and what it requires (migration, secret, order of switching on). The reasons, the history and the design details are in the [Flag rationale](decisions.md#flag-rationale) of the decision log, linked from each paragraph; the defaults, the migration and the status of every flag are in the table above.

**A flag does not outrun its migration (NIEZ-30).** A flag turned on before its migration used to end in `PGRST204` (a write to a column the table does not have) and lose the whole prediction write. At start the Fast Loop and the Slow Loop now call `public.schema_version()` (migration `071`), which returns the highest migration number recorded by the Supabase CLI. Every flag that is on and whose migration is newer — the **Migration** column of the table above, kept in `FLAG_REQUIRED_MIGRATION` in [`src/domain/feature_requirements.py`](../src/domain/feature_requirements.py) (the later one when a flag names two) — is switched off for that run, with a `WARNING` in the log and one `WARNING` quota alert in the next email banner (the Slow Loop saves it to `quota_alerts`). The setting in `config.toml` is untouched: the first run after the migration turns the flag on by itself. When the number cannot be read — `071` not applied yet, the database not answering, or an empty registry because migrations were pasted by hand — every flag stays on (the owner chose fail-open), the log gets one `WARNING` and the run's step summary a **Schema probe** note; there is no email alert, because that is missing information, not a proven mismatch. A raw network error while asking is not caught and fails the start like any other first request. Shock Watch does not ask. [`tests/test_feature_requirements_wiring.py`](../tests/test_feature_requirements_wiring.py) fails when the map and the table disagree.

**Optional alpha-data sources** (category "Data"): seven extra signals — SEC EDGAR insider flow, AlphaVantage earnings calendar, Finnhub options/IV, Reddit social velocity, FRED yield-curve, Finnhub analyst consensus, and regime-tagged RAG (vector memory). Each is a port + adapter with a **Null fallback** and is **off by default in code** (`insider_flow_enabled`, `earnings_calendar_enabled`, `options_flow_enabled`, `social_velocity_enabled`, `yield_curve_enabled`, `analyst_consensus_enabled`, `vector_memory_enabled`) — so a source makes **zero network calls** until its flag is on (and its key supplied where needed). Production `config.toml` turns on the yield curve and analyst consensus; insider flow, social velocity, the earnings calendar, options flow and vector memory stay off. Enabled per-symbol signals are aggregated into an "Alpha Signals" report section; `vector_memory_enabled` needs migration `017`.

**Insider flow and social velocity are off** (since 2026-10-24) because both sources refuse the Fast Loop: from at least 2026-07-27 every run got `403` on every symbol from both, so their Alpha Signals cells were always empty and the fusion score never had an insider vote. Both flags are part of `config_hash`, so turning them off starts a new track-record segment; turning them off before the first weekday cycle on the new database (2026-10-26) keeps that cost at almost nothing. Why and history: [Flag rationale](decisions.md#flag-edgar-reddit).

- **SEC EDGAR** (`insider_flow_enabled`): a lasting IP block (`403 Forbidden`, "Request Rate Threshold Exceeded"), not the brief throttle. The adapter now follows SEC's fair-access rules (one pacer for all threads, requests at least 0.12 s apart, the ticker map once per cycle, the first `403` ends EDGAR for the rest of the cycle), but only SEC can lift the block. To re-enable, email `webmaster@sec.gov` with the "Reference ID" shown on the 403 page, then set `insider_flow_enabled = true` and start one manual Fast Loop run to confirm. Switching to a new contact address (`edgar_user_agent`) to get past the block would be circumvention, not a fix.
- **Reddit** (`social_velocity_enabled`): every anonymous `search.json` request from a GitHub Actions runner answers `403 Client Error: Blocked`. The only compliant fix is a registered OAuth app with client credentials, a new credentialed integration that is not built. The adapter stops after the first `403` of a cycle. Little is lost meanwhile: a search returns mention counts without sentiment, so the social snapshot never votes in the Alpha Fusion Score.

**Insider flow covers stocks only** (`has_insider_filings` in `src/domain/insider_flow.py`, the same boundary as fundamentals and valuation): `AlphaEnrichmentUseCase` never asks the insider port about a crypto or ETF symbol, which also saves about two SEC requests per ETF per cycle.

The FRED yield curve is no longer render-only. When **both** `yield_curve_enabled` and `regime_aware_enabled` are on, an inverted 10Y-2Y spread is cast as one `ELEVATED` **vote** into `RegimeDetector`. It is a vote, not a veto: two `ELEVATED` votes make `RISK_OFF`, so an inversion on its own only moves the regime to `NEUTRAL`. `RISK_OFF` raises the volatility threshold, so the net FinOps effect is a saving. Why and history: [Flag rationale](decisions.md#flag-yield-curve).

`macro_series_enabled` (no migration; the same free `fred_api_key` as the yield curve) reads five market state variables from FRED **once per cycle** (DAT-22, `MacroSeriesPort`): `VIXCLS` over the last year, the high-yield option-adjusted spread `BAMLH0A0HYM2` over the last three weeks, and the latest observation within two weeks of `VXNCLS`, `T10Y2Y` and the weekly `NFCI`. Every value keeps the day it was **observed**, not the day it was fetched (FRED publishes with a lag). With `regime_aware_enabled` two regime votes join the yield-curve vote: the VIX percentile over the year (at least 60 observations) votes `ELEVATED` from the 75th percentile and `CRITICAL` above the 90th, and the 5-session change of the high-yield spread votes `ELEVATED` from +0.25 pp and `CRITICAL` from +0.50 pp; a `CRITICAL` vote means `RISK_OFF`, a single `ELEVATED` vote only `NEUTRAL`, and votes can only raise the volatility threshold. With `market_features_enabled` the features `vix_level`, `vix_percentile_1y`, `vxn_level`, `hy_oas`, `hy_oas_change_5d`, `term_spread_10y2y`, `nfci` and `macro_observed_on` join every feature vector of the cycle. A failed series is logged without its key and left out; all five failing gives no snapshot, no votes and `null` features. The values are not cached in the database, so history is not kept between cycles. Part of `config_hash` (its votes can change the regime, which tightens the gate and reaches the prompt as the regime label); ships **off**. Why and history: [Flag rationale](decisions.md#flag-macro-series).

`regime_hysteresis_enabled` and `regime_exit_confirmations` (**require migration `033`**) add hysteresis to the market regime. With the flag on, entering `RISK_OFF` is immediate, while leaving it needs `regime_exit_confirmations` (default `2`) **consecutive** raw readings outside `RISK_OFF` (`NEUTRAL` and `RISK_ON` count alike), so a signal oscillating around a boundary no longer switches the threshold multiplier every cycle. `main_agent._resolve_regime` reads the newest row of `regime_history` and every cycle with a regime (regime aware on and a Risk Watch report) writes one row with the raw regime, the effective regime and the count; a failed read (for example before the migration) uses the raw regime, exactly as with the flag off, and writes no row. Hysteresis can only keep the threshold higher for longer, never lower it. **A confirmation is one Fast Loop run, not one day**: on the cron schedule two runs are a few hours apart, but with manual dispatches the exit can take days or weeks. Both fields are part of `config_hash`. The flag ships **off**: before the migration the table does not exist, so the read and the write would fail every cycle. Why and history: [Flag rationale](decisions.md#flag-regime).

**Regime in the email header (ALR-05).** With `regime_aware_enabled` the HTML and plain-text header carry one line under the start time, e.g. "Reżim: RISK_OFF · próg ×1,5 (2,0% → 3,0%) · powód: 2 głosy ELEVATED": the effective regime (after hysteresis), the threshold multiplier, the stock threshold before and after it, and the reason from `RegimeDetector.reason`. Without the flag or without a Risk Watch report there is no line. **A regime change leads the email**: when the effective regime enters or leaves RISK_OFF compared with the previous cycle, the lead gets an item ranked right below a CRITICAL quota alert (the subject inherits it when no such alert exists). The previous regime comes only from the hysteresis state, so the item needs `regime_hysteresis_enabled` (**requires migration `033`**); a switch between NEUTRAL and RISK_ON is no lead item.

`regime_tagging_enabled` (uses the `prediction_logs.regime` column of migration `017`) separates tagging from filtering: every saved prediction carries the canonical regime key (`UNKNOWN` when the cycle has no regime) whenever the tag is on, while the RAG filter on analogues of the same regime stays behind `vector_memory_enabled`. The field has no value by default (`None`): `main_agent` then follows `regime_aware_enabled`, which production `config.toml` turns on; an explicit `true` or `false` wins. **A deployment that has `regime_aware_enabled` on but has not applied `017` must set `regime_tagging_enabled = false`**, otherwise the whole prediction write fails (`PGRST204`). Zero calls, zero cost; outside `config_hash`.

With `earnings_calendar_enabled = true` the next quarterly report is fetched **before** the graph runs and its proximity raises the volatility threshold (`IMMINENT` ≤ 2 days → ×1.5, `NEAR` ≤ 7 days → ×1.15, otherwise ×1.0). The earnings and regime multipliers **compound** and are both `>= 1.0`, so the gate can only tighten. One domain rule, `effective_threshold` in [`src/domain/asset.py`](../src/domain/asset.py) (FIN-08), sets the threshold of every gate (main gate, paid mistake diagnosis in `reflect_node`, council, tool use; crypto has no separate tool-use threshold). With the flag off no earnings port is touched. Since FIN-09 the adapter asks Alpha Vantage `EARNINGS_CALENDAR` **once per run, without a symbol**, before the volatility gate; it rotates over every key of `ALPHA_VANTAGE_API_KEYS` on a soft limit, and when every key is limited the run has no earnings dates and a `WARNING` quota alert (`Alpha Vantage earnings`) says so. Tickers with a dot are not in the CSV. `earnings_cache_enabled` (FIN-11, **requires migration `053`**) moves the fetch to the Slow Loop: the weekly run refreshes the `earnings_cache` table (one report date per stock symbol, ETFs and crypto skipped) and the Fast Loop reads only that table, so the FIN-32 daily budget counts one request per symbol again. An entry is valid for `EARNINGS_CACHE_TTL_HOURS` (144 h, Monday to Friday after the Sunday refresh); a report announced after the refresh is missed until the next one; a symbol without a cached entry gets no earnings multiplier. `calibrated_confidence_enabled` makes the "Najsilniejsze sygnaly" ranking use `strength = confidence x |delta|` on the confidence **corrected by its bucket's historical hit rate**, shrunk toward the raw value on a small sample (`weight = count / (count + 10)`); each signal card shows the raw and the calibrated confidence with the bucket's sample size (`85% → 58% po kalibracji (n kubełka: 40)`). The buckets come from directional predictions only (WIA-39, `src/application/signal_calibration.py`). When the confidence carries no ranking information — the AUC of the directional confidences against their hits is below `0.55` on an `n_eff` (by UTC day) of at least `50` (WIA-38, `confidence_reorders_ranking` in `src/domain/calibration_curve.py`) — the ranking stays on the raw confidence and the cycle logs a `WARNING` with both numbers; a smaller sample keeps the calibration. `evaluate --discrimination` prints the same AUC for the LLM and for the council's consensus strength. Render-only: nothing is persisted, and in particular the `confidence_calibration` column from migration `016` is never overwritten. Independent of `calibration_curve_enabled` on purpose — one draws the Track Record section, the other changes the ranking. Why and history: [Flag rationale](decisions.md#flag-calibrated-confidence).

`isotonic_calibration_enabled` (no migration; effective only with `calibrated_confidence_enabled`) replaces the bucket shrinkage with an isotonic map when that map wins out of sample (ML-28). `fit_isotonic` in `src/domain/isotonic_calibration.py` fits a non-decreasing map with pool-adjacent-violators, and `select_isotonic_calibrator` fits both the map and the buckets on the directional settlements from 60 to 30 days ago and scores them with the Brier score on the last 30 days next to the raw confidence; the map enters the ranking only when its Brier is lower than both, and each window needs at least 30 samples (`MIN_ISOTONIC_SAMPLES`), otherwise the buckets stay. `isotonic_class_calibration_enabled` (no migration; effective only with `isotonic_calibration_enabled`) runs the same rule separately for crypto (`crypto_symbols`) and for the rest (stocks and ETFs), from the same read, which now carries the `symbol` (ML-54). `select_class_isotonic_calibrators` in `src/domain/isotonic_calibration.py` gives a class its own decision when it has at least 30 samples in each window (`MIN_CLASS_ISOTONIC_SAMPLES`): the class map when it wins out of sample in that class, otherwise the buckets. `messenger_digest_enabled` fixes a silent failure: Telegram and Slack used to receive the **full** plain-text report, which routinely exceeds Telegram's 4096-character limit (the API answers `400` and the push disappears), and the per-subscriber fan-out never fired push at all. `model_scorecard_enabled` (migration `019`) surfaces the walk-forward gate that refuses to ship a model worse than the naive baselines. The gate is necessary, not sufficient (DOC-06; [how it works](how-it-works.md), step 10). Each Slow Loop run records one row **per symbol** (that symbol's own evaluation, which never writes weights) plus one row with `symbol = 'ALL'` for the shared model, the only one that can ship weights. The report reads the **latest run only** (a gap of more than 2 hours between rows starts an earlier run) over a 42-day window (`MODEL_SCORECARD_WINDOW_DAYS`, ML-15), so the `STALE` badge (past 21 days) stays visible. The main verdict ("accepted N, rejected M, skipped K") comes from the `ALL` row; the per-symbol evaluations follow on a separate line; then come the RMSE against the baseline of the newest shipped candidate (or the newest with metrics), directional hit rate and fold count. A run where every candidate was rejected renders as exactly that, and at cold start the section says no model is loaded. The section always carries `METRIC_NOTE`: the metrics describe the candidate on walk-forward folds while the shipped model is refit on all data. Writes are best-effort: a missing migration cannot break training. Why and history: [Flag rationale](decisions.md#flag-model-scorecard).

`settled_at_windows_enabled` (**requires migration `029`**) counts the "closed in the window" reads by the moment a prediction was settled instead of the moment it was made. With the flag on, the email lists the predictions settled since the current cycle started, under "Zamknięte predykcje (rozliczone w tym cyklu)", and the preheader count, the lead's hit/miss labels and the push digest scorecard read the same rows; the weekly recap reads the predictions settled in the last 7 days. Rows settled before the migration get an approximate `settled_at` (the first price snapshot of the symbol at the settlement price taken at least an hour after the prediction; without one, the prediction's own `timestamp`, a lower bound). Ships **off**: before the migration, filtering on the column returns `400`, so the email would lose the section and the recap would be skipped. With the flag off, both reads, the heading and the 24-hour window are exactly as before. Why and history: [Flag rationale](decisions.md#flag-settled-at-windows).

`shock_alerts_enabled` (migration `021`) adds a **fourth entry point**, [`main_watch.py`](../main_watch.py), for an hourly cron that runs **24/7 rather than only during NYSE hours** (BTC and ETH trade around the clock): an -8% move on BTC at 14:00 should not wait until tomorrow morning. The cron runs (resumed on 2026-10-23) and does not depend on the Fast Loop. Since ALR-02 the watch reads the **day's change from the same free quote** (`DailyChangePort`: Finnhub `dp` for stocks, CoinGecko's 24-hour change for crypto) and falls back to the Fast Loop snapshot only when that reading is missing, fails, or is not from the run's UTC day; a reading from another UTC day never alerts, and a crypto symbol whose previous alert is less than 24 hours old gets no alert from the daily change. A fresh reading decides the symbol on its own, so one run sends at most one alert per symbol, and the push says which reference it used. On the snapshot fallback a price snapshot older than 30 hours suppresses the alert (checked before the current price is fetched), and a run in which no symbol had a fresh daily change and every snapshot is stale logs a `Shock watch ślepy` WARNING instead of reporting a healthy-looking "0 alerts". Zero paid calls (free price sources, a Supabase read, free push channels). Two hard contracts protect the rest of the system: the watch **never calls `save_price_snapshot`** (an hourly overwrite would make the Fast Loop measure its delta against an hour-old price and quietly shut the volatility gate), and a **one-alert-per-symbol-per-day debounce**, enforced by the domain predicate and `UNIQUE(symbol, alert_date)`. Delivery is **at-least-once** (ALR-14): the push goes out first and the `shock_alerts` row is written after a successful send, so a database failure never swallows an alert, and two overlapping runs or a failed write can push the same alert twice (`UNIQUE` rejects the second row, not the second push). The comment in migration `021` describes the opposite order; the migration is applied and is not edited, so this paragraph and `main_watch.py` are the contract. The workflow guard (`tests/test_shock_watch_env_wiring.py`) allows the watch cron without the Fast Loop cron as long as `main_watch.py` wires the daily-change source. Why and history: [Flag rationale](decisions.md#flag-shock-watch).

`quiet_hours_enabled`, `quiet_hours_start` and `quiet_hours_end` (ALR-09) mute the watch's pushes at night instead of dropping them. The watch is built for an hourly 24/7 cron, so a crypto shock at 03:00 would otherwise wake the reader; suppressing it would lose the information. When the run's moment falls in the window `[start, end)` in `display_timezone` (the window may cross midnight, `22:00`–`07:00` by default; equal bounds mean no quiet hours), `main_watch` sends the push with `silent=True`: Telegram gets `disable_notification`, so the message arrives without a sound; a Slack incoming webhook has no such option, and the adapter adds no @-mention in the first place, so the Slack text is unchanged; e-mail ignores the flag. Only the shock watch asks for silence: operational CRITICAL alerts (`AlertNotifier`) never pass it, so quiet hours do not apply to them. `ReportNotifierPort.send_report` takes `silent` as a keyword with the default `False`, so every other caller sends exactly as before. The fields only change delivery and stay outside `config_hash`. The code default is off; `config.toml` turns the window on.

`price_level_alerts_enabled` and `price_alerts` (ALR-11, **requires migration `057`**) add user-set price levels to the watch: "tell me when NVDA rises through 150". `price_alerts` is the starting list in `config.toml`, one inline table per level, `{ symbol = "NVDA", level = 150, direction = "ABOVE", note = "realizacja części zysku" }` (`direction` is `ABOVE` or `BELOW`, `level` must be positive, `note` is optional, an unknown key or direction stops the start). Every watch run adds the missing levels to the `price_level_alerts` table with `ON CONFLICT DO NOTHING` on `(symbol, level, direction)`, so a level that already fired is not revived; the list ships empty. The run reads the active alerts, takes one free quote per symbol (Finnhub or CoinGecko, symbols in `symbols_unsupported_price` are skipped) and fires on a **crossing**, not on the position of the price: the previous reading must lie on the other side of the level (`src/domain/price_levels.py`). The previous reading lives in the alert (`last_seen_price`), because the watch never writes `price_snapshots`; the first reading after a level is added is only the reference. A hit sends the push ("🎯 NVDA przebiła 150 (Twoja notatka: realizacja części zysku)", "🎯 NVDA spadła do 150" for `BELOW`, silent in the quiet hours) and then disables the alert (`active = false`, `triggered_at`); without a push channel the hit waits untouched for the next run. Zero paid calls. The flag ships **off**: before the migration the table does not exist, and with the flag off the watch neither reads nor writes it.

**Shock-alert context (ALR-08).** A bare "NVDA -6.2%" push does not say whether the move touches you or whether the model saw it coming, so the watch adds up to three lines between the move and the footer, all from free reads: your position in the symbol (its share of the portfolio at the current free quotes and its return since purchase, from the `positions` table behind `portfolio_positions_enabled`; a portfolio older than the 7-day freshness rule is marked with its date, and a share computed without a quote for every holding says it covers the priced part only. A portfolio that holds several currencies is valued in zlotys at today's NBP rates (`nbp_enabled`; only the current rate of each foreign currency is asked for), because amounts in USD and PLN do not add up; with no NBP rate for the currency of the position the share is left out rather than guessed, and a failing rate read never stops the alert. A portfolio in one currency needs no rates), the latest council verdict from `get_previous_verdict` with its age in calendar days of `display_timezone` ("Rada wczoraj: KUP, zgoda 72%", "Rada 8 dni temu: …"), and the reasoning of the latest prediction from `RepositoryPort.get_latest_prediction` (price, time and `reasoning_text` of the newest `prediction_logs` row), cut to 240 characters. Every read is best-effort: a failure costs a `WARNING` and one line less, never the alert. The portfolio is read once per run, on the first alert, and the extra quotes go only to held symbols; the watch still writes nothing but the `shock_alerts` row.

`liveness_fast_loop_max_gap_h` / `liveness_slow_loop_max_gap_h` drive the deadman, [`main_deadman.py`](../main_deadman.py) (daily cron, zero paid calls). It reads the newest `price_snapshots` row (Fast Loop) and `model_scorecards` row (Slow Loop, written per symbol and for the shared `ALL` model even when training is skipped) and mails through Resend when a job has been silent longer than its gap in hours. `0` means the job is deliberately paused and not checked — production sets the Fast Loop to `26` (an alert after two NYSE trading days without a cycle; it was `0` while the cron was paused) and the Slow Loop to `192` (a week plus a day of GitHub cron slack). Without it, a dead Slow Loop looked exactly like a quiet week. The Fast Loop is counted in NYSE trading days (NIEZ-11, the session calendar in `src/domain/market_calendar.py`), because an hourly gap would fire after every weekend and holiday for a job that runs once per trading day: each trading day has a deadline at 00:00 ET plus `liveness_fast_loop_max_gap_h`, and the Fast Loop is overdue once the latest passed deadline has no `price_snapshots` row written since 00:00 ET of that day. Weekends and NYSE holidays have no deadline. With a gap of `26` the deadline of a trading day is 02:00 ET the next day, so one skipped run is tolerated when the next cycle arrives and two missed trading days raise the alert; a gap below the deadman's check time (09:17 UTC, 04:17 ET in winter) reports a missed run the same morning. The value stays `0` while the Fast Loop is paused; set it when the schedule is resumed. The Slow Loop keeps the hourly rule.

`options_flow_enabled` now does more than fill a table cell. With it on, the options port is fetched inside `_predict_node` — naturally **behind the volatility gate**, so a quiet cycle never pays for it — and the model's predicted move is compared against the move the options market implies (`implied_move_12h`, sqrt-time scaled to a 24-hour horizon: one cycle on a weekday, so a Friday prediction that runs to Monday's cycle is understated). The report shows a **qualitative label** (`MODEL_AHEAD` / `MARKET_AHEAD` / `ALIGNED`), not a two-decimal sigma, and `edge_sigma` is persisted (migration `025`) so the hypothesis can be falsified later: does the `edge > 1.5σ` subset actually beat the rest? Two methodological caveats are stated in the module docstring rather than hidden: `implied_vol` is a chain-wide average, not the front-month at-the-money, and sqrt-time over calendar hours **overstates** the move across a weekend. The signal is informational and deliberately carries no decision-making role until validated on closed predictions. With the flag off, no options port exists and the cycle is byte-identical.

**`options_flow_enabled` stays off (DAT-24).** Finnhub's option chain is a premium endpoint: a free key answers 403, so with the flag on every cycle would spend about 39 requests behind the gate on a signal that never appears. The implied edge has no decision-making role until `edge_sigma` has passed its falsification test, so paying for it first buys little. The decision is to approximate it for free and to buy the plan only if that shows an effect: the realized volatility of the symbol's own price snapshots (not built yet), the Deribit DVOL index for BTC and ETH (`deribit_dvol_enabled` below, built, off until the test and the Deribit terms review), and the VIX scaled by the symbol's beta for stocks (not built yet; the VIX itself is read with `macro_series_enabled`). A Finnhub premium plan is reconsidered only after one of them gives a positive `edge_sigma` result.

`edge_calendar_horizon_enabled` (WIA-28, no migration) replaces that fixed 24-hour horizon for stocks and ETFs with the calendar hours to the same ET time on the next NYSE trading day (`hours_to_next_trading_day` in `src/domain/market_calendar.py`): 24 h on a weekday, 72 h from a Friday, 48 h before a mid-week holiday, 96 h before a long weekend, 71 or 73 h across a daylight-saving change. Crypto trades every day and keeps 24 h. The calendar knows no unscheduled closures. A longer horizon means a larger implied move and so a smaller `edge_sigma`, which changes a signal `evaluate` segments by, so the flag is part of the recipe (`config_hash`) and ships **off** until the EXP-02/03 experiments end (2027-01-29).

`deribit_dvol_enabled` (DAT-18) gives the same edge a free source for crypto, since Finnhub's option chain is a premium endpoint. With it on, the graph's options port becomes a router: `BTC` and `ETH` go to the public Deribit volatility index (`get_volatility_index_data`, no key, the close of the newest hourly candle, 55.0 → `implied_vol = 0.55`), and stocks go to Finnhub when `options_flow_enabled` is on, otherwise nowhere. DVOL is a 30-day implied volatility, not the front-month at the money — the same class of approximation as the chain-wide average — and crypto trades around the clock, so sqrt-time over calendar hours is right there. DVOL feeds only the implied edge (`edge_sigma`, migration `025`); it never reaches Alpha Fusion, where an options source without a put/call ratio would be a neutral vote diluting the others. Outside `config_hash` (a stored measurement, not the prediction). **Turn it on only after the `edge_sigma > 1.5σ` hypothesis has a falsification test (WIA-75)** and the Deribit terms of use are reviewed; until then it ships off.

`alpha_fusion_enabled` (migration `022`) feeds the alpha sources into the prediction instead of only into a table. Fusion is a weighted sum of the *existing* domain classifications, renormalised over whichever sources are present, so a symbol with one available source is not silently penalised; a social snapshot **without sentiment** counts as absent (Reddit search returns mention counts only), and the Reddit adapter returns no snapshot when its week search fills the whole 100-post page. The score reaches the LLM prompt **with its per-source breakdown** and `ml_feature_store`, where it is a **candidate** feature, not a model feature: it is not in `ML_FEATURE_COLUMNS` ([`src/application/ml_features.py`](../src/application/ml_features.py)), so the XGBoost model neither trains nor predicts on it. Enrichment runs **before** the graph (it used to run after); the paid-call count is unchanged. In the view the column is `COALESCE(alpha_fusion_score, 0.0)` so that, once the score is promoted, `dropna` cannot cut the historical rows out of training (a train/serve skew the migration test freezes). Whether the hand-picked weights are signal or noise is not settled — promoting the score needs an A/B comparison first (EXP-19) — which is why the flag is off by default in code; production `config.toml` turns it on. Why and history: [Flag rationale](decisions.md#flag-alpha-fusion).

`attestation_enabled` (**requires migrations `024` and `043`**) makes the track record **cryptographically checkable** (R-16 and D-4 in the [decision log](decisions.md)). At prediction time a SHA-256 commitment over the canonicalised prediction plus a random salt is written to `prediction_logs` and the **hash alone** is appended to a public JSONL file. The hash is published only after the prediction row is saved (WIA-01), and the canonical plaintext is kept in `commitment_payload` (`TEXT`, migration `043`, WIA-70), so anyone checks SHA-256(`payload` + `salt`) byte for byte. A second save of the same symbol in the same UTC hour reuses the row's salt when the prediction is the same; when it differs, the overwritten commitment is revealed at once with `"status": "superseded"`. Once a prediction settles, a **sweep** reveals every matured commitment (salt and plaintext), whatever its age and whether or not its symbol is still on the watchlist; `revealed_at` is stamped only once the reveal is *durable* (WIA-15): the sweep after the report only appends to `reveals.jsonl`, and the next Fast Loop run stamps exactly the rows whose `commitment_hash` is in the `reveals.jsonl` it checked out of `attestation-log`. Before each cycle with the flag on, `attestation_columns_available()` checks that the three commitment columns exist; without them the cycle runs without attestation and logs a `WARNING`, instead of losing every prediction write to `PGRST204`.

**One Merkle root per cycle (WIA-60).** The commitments of a cycle are the leaves of one RFC 9162 §2.1 tree (`tree: "rfc9162-sha256"`). After the symbol pass, also when the pass raised, the Fast Loop appends **one** line per cycle to `commitments.jsonl` (`cycle_id`, `committed_at`, `root`, `n_leaves`, `leaves`, `schema_version`, `tree`), also for a cycle with no prediction; a reveal carries `inclusion` (`cycle_id`, `root`, `leaf_index`, `tree_size`, `proof`) or `"status": "incomplete_cycle"` when its cycle's root never reached the ledger. Canonicalisation is frozen by golden tests and carries a `schema_version` from the first commit; new commitments use schema `2`, which also binds the declared confidence, the horizon (12 hours), the council's `final_recommendation` and `consensus_strength`, the `recipe_version` and the hash of the evaluation protocol (WIA-41), with fractions as four-decimal strings and prices as the four-decimal text of their `DECIMAL(14,4)` columns (WIA-02); schema `1` stays frozen for verifying older commitments. Zero cost — local hashing.

**What this proves is bounded:** git commit dates are forgeable, so the claim is *tamper-evidence under branch protection*, not an unforgeable timestamp. The predictions of 2026-07-10 to 2026-08-17 cannot be attested at all (WIA-27): the record is verifiable only from the first push of the ledger onwards, and earlier rows stay in the database and in the email's Track Record as unattested history. How to check a ledger: [Verify it yourself](#verify-it-yourself).

**The ledger and its wiring.** The durable home is the orphan branch `attestation-log` (WIA-14). The Fast Loop checks it out into the directory of `attestation_commitments_path` and `attestation_reveals_path` before the agent runs; a separate job, `publish-attestation-ledger`, is the only one with `contents: write` and holds no API key: it commits the new lines with `[skip ci]`, runs `git pull --rebase` with up to five retries and pushes to `attestation-log` and nowhere else, never to `main`, and it runs after a failed agent job too. A flag on without the branch fails the Fast Loop in its first step, before any paid call. Guards in [`tests/test_workflow_env_wiring.py`](../tests/test_workflow_env_wiring.py) check the wiring and fail the flag if it is switched on without a `git add` of both ledger files and a `git push` in the agent's job or a job that waits for it. `config.toml` ships the flag **off** until the owner creates and protects the branch (step 9 of the [resume checklist](resume-checklist.md)). Why and history: [Flag rationale](decisions.md#flag-attestation).

**Anchoring cycle roots in Rekor (WIA-73).** `attestation_rekor_enabled` (needs `attestation_enabled`, database writes and `id-token: write` on the agent job) logs every cycle root with at least one prediction in the public [Sigstore Rekor](https://docs.sigstore.dev/logging/overview/) transparency log before the line is appended to `commitments.jsonl`. `RekorAttestationPublisher` ([`src/infrastructure/adapters/rekor_publisher.py`](../src/infrastructure/adapters/rekor_publisher.py)) wraps the file publisher, so the graph keeps one `attestation_publisher`. It signs the 32 bytes of the root keyless, as the official `sigstore-python` client does: the job's GitHub Actions OIDC token with audience `sigstore`, an ephemeral P-256 key that lives for one call, and a short-lived Fulcio certificate requested with a CSR, whose SAN names the workflow (`https://github.com/<owner>/<repo>/.github/workflows/fast_loop_12h.yml@<ref>`). It then posts a `hashedrekord` entry (SHA-256 of the root bytes, `root_artifact_sha256` in `src/domain/attestation.py`, frozen by a golden test) to `rekor.sigstore.dev`, and the line carries Rekor's answer in its `rekor` field: `uuid`, `logIndex`, `integratedTime`, the entry `body` (with the certificate) and the inclusion proof with its checkpoint. No line field enters a hash. A cycle with no prediction (its root is the hash of nothing, the same for every empty cycle), old single lines and reveals skip Rekor. A failed token, Fulcio or Rekor call logs a `WARNING` naming the cycle and the line goes out without `rekor`; the cycle runs on. Zero paid calls (three free requests per cycle); entries are public forever. What it adds to the git ledger: Rekor's `integratedTime` is an independent upper bound on when the root, and every prediction under it, existed, and the certificate ties it to the public workflow rather than to someone's laptop. How to check it: [Verify it yourself](#verify-it-yourself).

**Turning Rekor on** is the owner's security decision, because the OIDC token lets whoever runs code in the job sign as the workflow: (1) `attestation_enabled` is on and the ledger is pushed (step 9 of the [resume checklist](resume-checklist.md)); (2) the `run-market-agent` job of [`fast_loop_12h.yml`](../.github/workflows/fast_loop_12h.yml) gets its own `permissions:` block with `contents: read` and `id-token: write` — the job that also holds the API keys, which is why no workflow grants it today; (3) `attestation_rekor_enabled = true` in `config.toml`. Without step 2 every cycle with predictions would log `WARNING Rekor: … job bez id-token: write …` and the ledger would have no anchor, so a guard in [`tests/test_workflow_env_wiring.py`](../tests/test_workflow_env_wiring.py) (`test_rekor_flag_needs_oidc_on_every_agent_job`) fails the flag while a job that runs `main_agent.py` lacks `id-token: write`. Step 2 also collides with the Pages guard of the same file, which allows `id-token` only in the `deploy-scorecard` job: switching Rekor on means amending that guard to accept it on the agent job too. Why and history: [Flag rationale](decisions.md#flag-attestation-rekor).

`portfolio_positions_enabled` (migration `023`) replaces equal-weight risk with the real portfolio: a `positions` table feeds a `Portfolio` aggregate with real weights (renormalised over the symbols that have a current price), unrealised P/L per position, and the exposure of each stock sector from `sectors`. Amounts in PLN come from NBP rates passed to the renderer as **values** (`ReportContext.portfolio_fx`). A **STALE badge is a requirement**: the table is maintained by hand and a stale portfolio produces a *false* P/L; a Supabase error degrades to no section. A position the cycle could not price (for example a ticker in `symbols_unsupported_price` such as `XDWD.DE`) is listed under the table ("Bez wyceny w tym cyklu: …") with its share of the total **cost** basis, and the totals are labelled "bez pozycji niewycenionych". A position in a symbol outside `symbols` + `crypto_symbols` and `symbols_unsupported_price` gets a price from the free quote endpoint only (`build_market_port`), fetched sequentially while the report is built (`ReportContext.held_prices`); it never writes a `price_snapshots` row, never enters the graph and never triggers an LLM, Alpha Vantage or embedding call. Phase 2: `suggest_band` knows the existing exposure — `current_weight` and the exposure of the symbol's sector can only *narrow* the band, an empty portfolio is never a buy signal. Portfolio risk is the third input: with `portfolio_var_enabled` on and real positions loaded, `PortfolioRiskUseCase.position_risk` measures the positions actually held from the free `price_snapshots` history; a 1-day VaR95 of at least 3% (`VAR_TIGHTEN_THRESHOLD`, from 60 returns) lowers the band one step, a drawdown of at least 15% below the 90-day peak (`DEEP_DRAWDOWN_THRESHOLD`) forces the starter band, and held hedges (typed `INVERSE_EQUITY` or `VOLATILITY` in `risk_symbol_types`, `EQUITY_HEDGE_TYPES`) with effectiveness below 0.3 (from 20 paired returns) lower it one step. With the flag off or without positions the band is unchanged. Outside `config_hash`: the band is rendered after the prediction. Why and history: [Flag rationale](decisions.md#flag-portfolio).

**Position currency and purchase date (migration `035`, no flag since PORT-23).** Each position carries its currency (`positions.currency`, ISO 4217, `NOT NULL DEFAULT 'USD'`) and its real purchase date (`positions.purchase_date`, `DATE`, `NULL` = unknown). The migration backfills the currency from the ticker suffix (`.DE`, `.AS`, `.PA`, `.MI`, `.MC` → `EUR`, `.L` → `GBP`, anything else → `USD`) and converts nothing; existing rows keep `purchase_date = NULL`, because `as_of` is not a purchase date. London quotes are often in pence (GBX) and some `.L` ETFs trade in USD: correct such a row with the import. `uv run python main_tools.py import-positions --csv <file> --apply` always writes both columns (see [running-locally](running-locally.md)) and returns `PGRST204` when the migration has not been applied. Production has had the migration since 2026-10-23. The currency changes the report, not the forecast.

**The P/L in złoty (PORT-11).** The 💼 section values the cost at the NBP rate of the purchase date and the current value at the current rate, then splits the result into the instrument and the currency effect (`w tym kurs`); the two add up to the P/L. It is an economic result at the NBP rate of the purchase date, not a tax base (PIT art. 11a uses the last business day before the transaction). With `nbp_enabled`, `main_agent` collects the rates while the report is built (`collect_pln_rates`, `src/application/portfolio_fx.py`) from the NBP table A endpoint, free and outside the graph and the volatility gate: a day without a table steps back day by day to the previous business day, at most 10 days (`MAX_LOOKBACK_DAYS`), and any other error stops further NBP calls for the rest of the cycle. A position without a purchase date says `kurs z dnia zakupu nieznany` and `—` in `P/L zł`; a missing rate says `brak kursu NBP z dnia zakupu` or `brak kursu XXX/PLN`; the totals line names the rates used and lists the positions left out (`bez P/L w zł: AMD, NVDA`). When the collection fails, the section falls back to the current USD/PLN and EUR/PLN of Risk Watch without purchase-date rates. Whenever rates are known the whole portfolio is measured in złoty (the weights, the sector exposure, the concentration warning, the sizing band, the VaR, drawdown and hedge weights, all via `Portfolio.pln_prices`); a position whose currency has no rate drops out of all of them and the section says so. Returns stay in the quote currency, so the currency move is in the P/L split but not in the VaR. Without any rate (`nbp_enabled` off) the native amounts remain, which is only right for a single-currency portfolio. GBX risk: if the price source returns pence for a `.L` position stored as `GBP`, every złoty amount and weight of that position is 100 times too large, so check `.L` positions and set their currency explicitly with the import. Other subscribers (`subscriptions_enabled`) never receive the rates. `fx_rates_cache_enabled` (**requires migration `036`**) adds a read-through cache of past-day rates in the `fx_rates` table (key `currency`, `on_date`), so a purchase-date rate is fetched from NBP once; only days before today in Warsaw are cached, and a cache error falls back to NBP. It ships **off**: before the migration the table does not exist. Both flags are outside `config_hash`.

`portfolio_var_enabled`, `stress_test_enabled` and `hedge_effectiveness_enabled` add VaR/CVaR, a beta-based stress test and hedge effectiveness to the 🎯 Portfolio Radar and Risk Watch sections, all from free `price_snapshots` history (zero paid calls); with real positions, `portfolio_var_enabled` also lets the risk of the held portfolio narrow the sizing band. Series of different symbols are paired by **UTC day** (`align_by_utc_day`, `src/domain/correlation.py`; the latest snapshot of a day wins, only days present in every series are kept). Minimum samples (`src/domain/risk_sample.py`): VaR/CVaR needs `MIN_VAR_OBSERVATIONS = 60` daily returns, correlations, clusters and the stress-test betas need `MIN_PAIRED_RETURNS = 20` paired returns; below that the section says "za mało historii (n/60)" (or `n/20`) in both the HTML and the plain-text email. The radar reads a 90-day window (`PRICE_HISTORY_DAYS`, roughly 63 sessions) page by page, because PostgREST silently caps a SELECT at about 1000 rows; until the loop has collected that history (or it is backfilled) the section reports the gap.

`public_scorecard_enabled` renders the one artefact meant to earn a stranger's trust: a landing page with **aggregates only** — settled predictions, the directional hit rate, Brier score, ECE, the reliability curve and the equity curve — and its machine-readable twin `scorecard.json`. The numbers are computed so that they mean something:

- **One definition of hit rate**: the *directional* hit rate (`directional_hit_rate`, `src/domain/equity_curve.py`); SIDEWAYS calls place no bet and stay out of the denominator.
- **Uncertainty**: a 95% Wilson interval on the effective sample size `n_eff = n / (1 + (m̄ − 1)·ICC)` (`src/domain/significance.py`) and, with at least 20 cycles, a cycle-level block bootstrap.
- **Naive baselines** ("always BULLISH / BEARISH / SIDEWAYS") on the same directional predictions (`naive_baselines`, `src/domain/track_record.py`), and an exact one-sided binomial test against the stronger of the two directional baselines, run on `n_eff`. `benjamini_hochberg` (FDR, q = 0.10) corrects the `evaluate --by` segments and the email's council ranking (WIA-22).
- **Required sample (DOC-16)**: about 617 settled directional predictions, in `n_eff`, to tell a 55% hit rate from a coin flip with a one-sided test at α = 0.05 and 80% power (`required_n`); with a window, the date the sample would suffice at the window's pace (`sample_reached_on`).
- **Probability scores**: Brier score, the climatological Brier, the Brier Skill Score, log loss and the Murphy decomposition (`probability_scores` in `src/domain/calibration_curve.py`); ECE on 10 equal-count buckets with a cycle-bootstrap interval and the bias-corrected `debiased_ece`.
- **Equity curve** (`paper_portfolio_curve`): one point per cycle, equal weight per prediction within a cycle, SIDEWAYS held as cash, net of the one-way trading cost (`src/domain/trading_costs.py`), next to two buy&hold benchmarks that pay the same cost (the basket and IVV, WIA-21, `src/domain/benchmark.py`) and the market-relative hit rate (a directional call is a hit when its sign matches the sign of the symbol's return minus IVV's return in the same window; predictions of IVV itself stay out of it). The page names the index "S&P 500" instead of its ticker, so no watchlist symbol reaches the page; the private email says "IVV". The page marks the methodology change of 2026-10-18 (the old curve compounded parallel trades serially on 100% of capital). **Timestamp convention:** IVV is read from the free `price_snapshots` (no paid call) and its window uses the same cycle snapshots as the prediction: the start is the IVV snapshot of the same cycle (same UTC day, the one nearest to the prediction's `timestamp`), the end is the first IVV snapshot at least `reflection_min_age_hours` later, which is the cycle in which `reflect_node` settles the prediction; the 05:30 UTC snapshot is the previous session's close, so both sides measure close(D−1) → close(D) and calendar trading dates are never used. A missing IVV snapshot in a prediction's cycle drops that prediction from the market-relative hit rate; a cycle with no IVV window at all makes the IVV curve "brak danych benchmarku"; if IVV misses the settlement cycle, its window runs to the next IVV snapshot. The read covers `track_record_days + 1` days.
- **Survivorship and window**: the methodology section says the watchlist was hand-picked (2026-06) with knowledge of the companies' earlier rallies, and the page states its window ("Okno: ostatnie 30 dni …", from `track_record_days`).

Rows written by the LLM fallback (`data_quality_flags` contains `llm_analysis_failed`) are excluded from every track-record read. The methodology section ends with the evaluation protocol (WIA-42): the version and adoption date of [`evaluation_protocol.toml`](../evaluation_protocol.toml), the horizon, the hit rule, the baselines, the metrics, α, the window and the protocol's sha256, the same hash every v2 commitment carries; `tests/test_evaluation_protocol.py` fails when a value in the file stops matching the domain constants it describes. `scorecard.json` is rendered from exactly the input of the page (WIA-81); its contract is [`docs/schemas/scorecard.schema.json`](schemas/scorecard.schema.json) (JSON Schema 2020-12, `additionalProperties: false`), and a change of meaning or shape bumps `schema_version` together with the schema.

**Privacy.** Aggregates only: a hard anti-PII test asserts that no email address, amount or ticker symbol reaches the page or the JSON. The private email never goes this way; it goes to the private archive of `digest_archive_enabled` (MAIL-24, a signed link valid for 7 days). Metrics are computed independently of `equity_curve_enabled` and `calibration_curve_enabled`, because those gate sections of a private email, not a public proof.

**Publishing.** The page and `scorecard.json` are written through `FileWebPublisher` (`public_scorecard_path`) and `WebPublisherPort.publish_asset`. `main_scorecard.py` (WIA-52) renders the same page from the data already in the database, with no paid call, charging the paper-PnL costs of `config.toml`; `--days N` overrides `track_record_days`; an empty window writes no page, so Pages keeps the last one it served; with the flag off it logs and exits 0; a database read error or a failed write exits 1. [`scorecard_pages.yml`](../.github/workflows/scorecard_pages.yml) runs it on `workflow_dispatch` (input `days`; the weekly cron stays commented out during the pause) and deploys only `dirname(public_scorecard_path)` — never `public/`, which also holds the attestation log, because a deploy replaces the whole site — with `actions/deploy-pages` in a separate job holding the only `pages: write` and `id-token: write`. The Fast Loop does the same with the page its cycle writes (WIA-16, job `deploy-scorecard`); both deploy jobs share the `pages` concurrency group, and [`tests/test_workflow_env_wiring.py`](../tests/test_workflow_env_wiring.py) checks the contract. `config.toml` ships the flag **off** until Pages is set up (Settings → Pages → Source: GitHub Actions); the order is in the [resume checklist](resume-checklist.md). Why and history: [Flag rationale](decisions.md#flag-public-scorecard).

The report also **prints its own bill**. One meter per cycle (`CycleTelemetry`, [`src/application/cycle_telemetry.py`](../src/application/cycle_telemetry.py)) counts the paid calls of the Fast Loop graph per pricing source, and the digest carries a "koszt cyklu" section: how many paid calls fired, broken down by source, and an **estimated** dollar figure. The sources are `llm` (the prediction call and the mistake diagnosis in `reflect_node`), `council_llm` (every persona, revision and chairman request, counted at the council's LLM port by `MeteredLLMPort`), `sentiment` and `news` (one each per symbol past the gate) and `embedding` (every real `embed` request). The word *estimated* is load-bearing — the unit prices in `UNIT_COST_USD` ([`src/domain/finops.py`](../src/domain/finops.py)) are an order-of-magnitude model per call, not an invoice, and the module says so; `council_llm` costs ~$0.0025 per persona or chairman call. The most interesting case renders explicitly rather than self-suppressing: a cycle where the volatility gate filtered every symbol reports **zero paid calls**, which is the entire point of the FinOps architecture.

The meter does not see every paid request. A tool-use prediction counts as one `llm` call although the loop can make up to `tool_use_max_rounds + 1` requests; `sentiment` and `news` count symbols past the gate, and so does the Alpha Vantage feed since FIN-04 (one request per symbol past the gate, plus key-rotation retries); calls made outside the graph, such as the Alpha Vantage earnings calendar and the alpha enrichment sources, are not metered. Digests sent before the council was metered per request counted a council run as one `council_llm` call priced at $0.02: a plain 7-persona run (8 calls × $0.0025) costs the same dollar figure, but the call count was understated eightfold, and debate rounds (15 calls) and late or failed requests were not priced, so council costs before and after that change do not compare one to one.

**The bill from tokens (FIN-13).** The LLM and embedding adapters (Anthropic and OpenAI, the council's adapter, both tool-use loops and the embeddings) report the token counts of every successful request to a `UsageSink` port, the in-memory `UsageLedger` of the run ([`src/application/usage_ledger.py`](../src/application/usage_ledger.py)); they know nothing about Supabase or prices. Anthropic gives `input_tokens`, `output_tokens`, `cache_read_input_tokens` and `cache_creation_input_tokens`; OpenAI's `prompt_tokens` includes the cached tokens (`prompt_tokens_details.cached_tokens`), so the adapter reports the uncached part as input and the cached part as cache read; embeddings report `prompt_tokens`. A request whose answer turns out empty or invalid is still reported, because it was billed; a response without usage reports nothing and raises nothing, and a cache hit of the embedding adapter is not a request. Who pays is added by the caller: the graph wraps every paid call in `usage_scope(source, node, symbol)` (the reflect diagnosis and the prediction under `llm`, the council under `council_llm`, the RAG and save-time embeddings under `embedding`), `MeteredLLMPort` sets the source of the council and of the Slow Loop jobs, and the council copies the caller's context into its persona threads. The domain prices each request (`price_usage` in [`src/domain/finops.py`](../src/domain/finops.py), from `llm_pricing`). In the "koszt cyklu" section a source whose every request has a price shows the cost from tokens ("2 wywołania z tokenów = $0,0123") and the others keep the unit estimate, marked "(szacunek)"; the header says when the total mixes the two and names the price date ("cennik z 20.10.2026"). A source with one unpriced request falls back as a whole, since a partial sum would understate it. A tool-use prediction is still one `llm` call in the count, but its token cost covers every round. Without token data (the price list empty, or no request reported) the section is exactly the estimate described above. Local stub runs (FIN-35) report nothing and hide the section as before. With `cost_ledger_enabled` the same ledger is written to `llm_calls` after the run.

### Verify it yourself

Once `attestation_enabled` is on and the first predictions have settled, anyone can check the commit-reveal log from a clone of the repository, with no key, no database and no network after the first command (WIA-26):

```bash
git clone --depth 1 --branch attestation-log https://github.com/DominikSienkiewicz/StockAgent.git /tmp/attestation-log
uv run python main_tools.py verify-attestation --commitments /tmp/attestation-log/commitments.jsonl --reveals /tmp/attestation-log/reveals.jsonl
echo "exit code: $?"
```

The second command prints a line per problem and ends with one verdict line, `OK: all N reveals reproduce their published commitments` or `FAIL: …`; the exit code is `0` for OK and `1` for FAIL (`2` when a file cannot be read). For every reveal it recomputes SHA-256(`payload` + `salt`) and compares it with the hash published in `commitments.jsonl` (`src.domain.attestation.verify_canonical`), and it checks that the symbol, trend and prices in the reveal row match the hashed payload, so a column edited after the fact fails too. A reveal whose hash was never published, a salt or payload that was changed, an unreadable line and a commitment line without a hash all give `FAIL`. Commitments that are not revealed yet are only counted (`N not revealed yet`): a prediction may simply not have settled, but a count that keeps growing is the thing to watch. Lines written before WIA-25 (symbol and hash only) and reveals from before migration `043` (no `payload`, rebuilt from their columns with schema `1`) are still read. Since WIA-60 a cycle writes one **cycle root line** instead of a line per prediction; the verifier rebuilds each root from its `leaves` (a root or an `n_leaves` that does not match them, or two different roots for one `cycle_id`, give `FAIL`), counts the leaves as published commitments, and checks each reveal's `inclusion` proof against the root the ledger published for that cycle, so a reveal can be checked against the root alone. A reveal marked `incomplete_cycle` (its cycle's root never reached the ledger) is listed as `incomplete cycle` and keeps the verdict at `FAIL`: it is public, but it proves nothing. Old single lines and cycle roots verify side by side in one ledger.

Since WIA-73 a cycle root line that carries a `rekor` field must also be confirmed by that Rekor entry, checked from the ledger alone ([`src/tools/verify_rekor.py`](../src/tools/verify_rekor.py)): the entry logs the SHA-256 of the root's 32 bytes and its signature verifies over them with the certificate's key; the entry body is a leaf of the log's RFC 9162 tree under the inclusion proof's `rootHash`, and the checkpoint names the same tree size and root; Rekor's `integratedTime` lies between 5 minutes before and 15 minutes after the line's `committed_at` and inside the certificate's validity; and the certificate's SAN names the workflow `https://github.com/DominikSienkiewicz/StockAgent/.github/workflows/fast_loop_12h.yml@<ref>`, issued for `https://token.actions.githubusercontent.com` (`--rekor-repository owner/name` and `--rekor-workflow .github/workflows/<file>` name another one, for a fork). Any mismatch gives `FAIL`; a root line without `rekor` does not (the flag may have been off, or that cycle's Rekor call failed), and the report counts the anchored roots (`Cycle roots logged in Rekor: N`). Offline, the verifier does not check the certificate chain up to the Fulcio root or Rekor's signature on the checkpoint, which need Sigstore's trust root: a green result says the entry is consistent and names the right workflow. To confirm that the public log really holds it, look its `uuid` up with `rekor-cli get --uuid <uuid>` or on [search.sigstore.dev](https://search.sigstore.dev), which show the same body and `integratedTime`.

What a green result proves is bounded, as in the status above: every revealed prediction is exactly the one that was hashed into a published commitment, and the history of `attestation-log` shows whether a line was ever removed or rewritten (`git -C /tmp/attestation-log log --stat`). Without a Rekor entry it does not prove when a commitment was made, because git commit dates are forgeable; with one, Rekor's `integratedTime` bounds it. It says nothing about predictions that were never committed. The verifiable track record starts at the first push of the ledger (WIA-27).

## Experiments

`experiments` (EXP-05) defines A/B experiments that run inside the Fast Loop. Questions such as "does RAG help" or "is a blind council better" are causal; a before/after comparison mixes the change with the market, while a random assignment per symbol and day answers them on the same period and the same stocks. Each experiment is a block of dotted keys in [`config.toml`](../config.toml):

```toml
experiments.EXP-02.hypothesis = "..."
experiments.EXP-02.arms = ["sighted", "blind"]
experiments.EXP-02.start = 2026-11-02
experiments.EXP-02.end = 2027-01-29
experiments.EXP-02.primary_metric = "council_hit_rate"
experiments.EXP-02.enabled = false
```

- **Assignment.** `assign_arm(experiment_id, symbol, cycle_date, arms)` in [`src/domain/experiment.py`](../src/domain/experiment.py) takes the sha256 of `id|symbol|YYYY-MM-DD` modulo the number of arms, where the date is the UTC day of the cycle start. It is deterministic, reproducible and stateless: a re-run of the same day lands in the same arm, and nothing is stored to decide it.
- **Active** means `enabled` and the cycle day inside `[start, end]`, both days included. An inactive experiment has no effect at all: the cycle runs exactly as it would without it, and nothing is recorded.
- **Arms.** The first arm is the control: the status quo, the behaviour production has without the experiment. The other arms are treatments the code knows, each changing one part of a prompt: `blind` (council prompt) and `no_memory` (prediction prompt). The settings refuse to start on an unknown arm name, a treatment as the first arm, a primary metric that does not belong to the experiment's prompt part, a window that ends before it starts, or an unknown key in the block: an arm without an effect would be an A/A test passing for an experiment.
- **One experiment per prompt part.** Two **enabled** experiments that change the same prompt part with overlapping windows stop the start. The check looks at the windows, not at today's date, so a configuration that is fine today and conflicting next week fails when it is deployed rather than on the day the second window opens. This was chosen over orthogonal hashes for the same part: two treatments on one prompt interact, and with a small n per arm the interaction cannot be told apart from the main effect. Experiments on different parts may run together. Their assignments are independent because the experiment id is part of the hash key (a factorial design), so each comparison stays balanced over the other experiment's arms.
- **Metrics.** Prediction prompt: `hit_rate` (directional hit rate of the LLM trend, SIDEWAYS places no bet) and `brier` (Brier score of `confidence_score` against `is_trend_correct`, on every settled call). Council prompt: `council_llm_agreement` (the final recommendation read as a trend, BUY → BULLISH, SELL → BEARISH, HOLD → SIDEWAYS, equals the LLM trend), `council_hit_rate` (BUY and SELL against the realized move) and `council_brier` (`consensus_strength` against whether the recommendation hit; HOLD hits inside the ±0.5% band).
- **Recording.** The arms of the active experiments go into the v2 decision receipt as the optional key `experiment_arms` (with `receipts_enabled`, no migration; the receipt reader tolerates its absence) and, with `experiment_arms_enabled`, into `prediction_logs.experiment_arms` (migration `037`).
- **Cost.** Experiments add no paid calls. The volatility gate is unchanged, and the arms only change the prompts of calls that run anyway.
- **Recipe.** `experiments` is in `RECIPE_SETTINGS_FIELDS`: enabling, disabling or editing an experiment (its hypothesis text included) changes `config_hash` and therefore `recipe_version`. Both arms of one cycle share that recipe; the recorded arm tells them apart.
- **Evaluation.** `uv run python main_tools.py evaluate --experiment EXP-02 --days 90` compares the arms (see [running-locally](running-locally.md)). It reads the control arm and the metrics from the definition, so keep a finished experiment in `config.toml` with `enabled = false`.

Defined experiments (both enabled in production from 2026-10-26, the first cycle after the Fast Loop resumed, to 2027-01-29):

- **EXP-02, blind council** (`arms = ["sighted", "blind"]`, primary metric `council_hit_rate`). The personas see the main LLM's verdict ("Trend wg głównego analityka agenta: … (pewność: …)") before they decide, so seven "independent" votes may be seven echoes of one. In the `blind` arm that line is left out of both the round-1 prompt and the debate revision prompt (`CouncilInput.blind`); everything else, the ML target included, stays. Both arms make the same council calls, so the experiment costs nothing extra. It compares the council's agreement with the LLM, the hit rate of `final_recommendation` and the Brier score of `consensus_strength`; persona redundancy is not measured yet (it arrives with WIA-45). The council fires only above `council_volatility_threshold`, so it takes weeks of cycles.
- **EXP-03, memory A/B** (`arms = ["memory", "no_memory"]`, primary metric `hit_rate`). We pay for mistake diagnoses (`analyze_mistake`) and embeddings on the assumption that lessons and analogs improve the next predictions, and nobody has measured it. The `no_memory` arm leaves the lessons from `reflect` (`reflection_context`) and the RAG analogs (`similar_context`) out of the prediction prompt (`get_prediction_prompt(include_memory=False)` also drops the instruction that refers to them). The arm the entry calls "control" in the hypothesis sense is `no_memory`; in the configuration the first arm, `memory`, is the status quo that runs whenever the experiment is inactive. The `no_memory` arm runs no RAG query, but it still embeds the news summary at save time, exactly like the status quo (owner's decision, 2026-10-20): each cycle makes one embedding call in both arms, and the arm's predictions join the analog corpus, so the experiment leaves no gap in the memory that later cycles retrieve from. Settling the previous prediction in `reflect` (and its gated diagnosis) runs in both arms. It compares the directional hit rate and the Brier score of `confidence_score`. RAG retrieval runs whenever the embedding adapter exists, which `main_agent` always builds; `vector_memory_enabled` only adds the regime filter. So the arm drops both lessons and analogs, and on days when retrieval finds no analog it measures the lessons alone.
