# Decision log

The decisions behind the code that a reader cannot recover from the code alone: what was
chosen, what it replaced, what it costs, and the commit and the test that hold it in place.
Each entry is short on purpose (an ADR-lite). Two kinds of identifier appear in the code, in
[`config.toml`](../config.toml) and in the other documents:

- **`R-N`** is a shipped roadmap item, a feature with a number. The table below is the only
  place that defines the numbers, and
  [`tests/test_decision_log.py`](../tests/test_decision_log.py) fails when a file mentions an
  `R-N` that the table lacks.
- **`D-N`** is a decision, written out in the second part.

Every `R-N` and `D-N` entry carries commit hashes, and the test checks that each one exists in
the history. After the decisions comes the [flag rationale](#flag-rationale): the reasons
behind the feature flags, which [configuration](configuration.md#feature-flags) links to. What
the repository does not record is not claimed here either: where a number or a reason could not
be recovered, the entry says nothing about it. For incidents and the guard that closed each
class of them, see the [engineering log](engineering-log.md).

## Decisions

### D-1 · The model learns the return, not the price level

**Date** 2026-06-20 · **Status** in force · **Commits** `bae5111`, `5da4808`, `82b1fd9`, `eff54d7`

The first XGBoost target was the absolute price. `bae5111` replaced it with `target_return` of
the `ml_feature_store` view (migration `012`, breaking: the old weights were deleted and the
model retrained), made the baseline the zero return, and computed `price_delta` once, in the
view, so that training and serving read the same number. A return can be compared across
symbols and against a "no change" baseline; a price level is in the units of its own symbol.

From 2026-10-18 one shared model is fitted on the pooled predictions of all symbols over
dimensionless features, which also fixed the per-symbol weights file that each run
overwrote. Weights ship only when the candidate beats the strongest of three baselines (no
change, mean drift, the LLM direction alone) by a 2% relative margin on at least 60
out-of-sample points; otherwise the leg runs on the no-change baseline and the report and the
council prompt label it cold-start rather than presenting it as a forecast.

*Costs:* weights ship rarely, and with a short history never. *Replaced:* the absolute price
target of each symbol.

**Guards** [`tests/application/test_train_model_use_case.py`](../tests/application/test_train_model_use_case.py) `TestRun::test_trains_model_with_correct_features_and_target` · [`tests/infrastructure/test_xgboost_adapter.py`](../tests/infrastructure/test_xgboost_adapter.py) `TestTrain::test_baseline_rmse_is_zero_return_persistence` · [`tests/application/test_agent_graph.py`](../tests/application/test_agent_graph.py) `TestColdStartBaseline::test_cold_start_is_flagged_in_final_state`

### D-2 · The volatility gate is a rule of the domain

**Date** 2026-05-13 (first commit), hardened 2026-06-20 and 2026-10-21 · **Status** in force · **Commits** `3e4a37f`, `bae5111`, `9e41b51`, `25479b8`

Every paid call (LLM, Alpha Vantage, embeddings) sits behind one question: did the price move
enough to be worth analysing. The answer is `Asset.evaluate_volatility` and the threshold
composition `effective_threshold` in `src/domain/asset.py`, computed on a fraction, never a
percent. The market-regime and earnings multipliers compound but are at least 1.0, so the gate
can only tighten. The graph executes the decision and never reimplements it; FIN-08 moved the
composition of the threshold for every gate (analysis, council, tool use, diagnosis) into the
domain as well.

Two exceptions exist and both are explicit and budgeted: the Slow Loop (weekly recap, diagnoses)
calls the LLM outside the gate under `slow_loop_max_paid_llm_calls_per_week`, and a ceiling on
paid calls per cycle cuts the council of the symbols past it.

*Costs:* a quiet market yields no analysis, no prediction and no settlement for most symbols
on most days, which lengthens the time to a meaningful track record.

**Guards** [`tests/application/test_agent_graph.py`](../tests/application/test_agent_graph.py) `TestVolatilityGateIsSystemic::test_no_optional_paid_port_touched_when_gated` · [`tests/domain/test_asset.py`](../tests/domain/test_asset.py) `TestAssetEvaluateVolatility::test_gates_on_fraction_not_percent`, `TestEffectiveThreshold::test_a_multiplier_below_one_never_loosens_the_gate` · [`tests/test_config.py`](../tests/test_config.py) `test_zero_volatility_threshold_rejected`

### D-3 · The council verdict is computed from the votes, not asked from a model

**Date** 2026-06-20 · **Status** in force · **Commits** `bae5111`, `9f2562a`

The council is a set of personas, each a vote with a confidence. The recommendation and the
strength of the consensus used to come from a chairman model; when that call failed, an
invented HOLD with 0.5 overwrote seven real votes. `derive_consensus` in `src/domain/council.py`
now computes both from the actual opinions: each recommendation collects the mass
`confidence × persona weight`, the largest mass wins, a tie goes BUY over SELL over HOLD, and
no opinions mean HOLD with strength 0. A persona whose call failed is not a vote (`9f2562a`).

*Costs:* the council cannot "overrule" its own votes with a synthesis. *Gains:* the verdict is
reproducible from the stored votes, so flips between cycles (R-8), persona weights (R-21) and
leave-one-out ablations are recomputed from data instead of trusted.

**Guards** [`tests/domain/test_council.py`](../tests/domain/test_council.py) `TestDeriveConsensus::test_three_buy_one_sell_three_hold_deterministic`, `TestDeriveConsensus::test_unanimous_buy_high_strength`

### D-4 · Commit-reveal attestation, with a claim that stays small

**Date** 2026-07-10, claim narrowed 2026-10-16, ledger 2026-10-24 · **Status** in force · **Commits** `7c37fe1`, `562fe73`, `5f005aa`, `60f95fb`

A track record is only believable if the predictions could not be tuned after the move. At
prediction time a SHA-256 commitment over the canonicalised prediction and a random salt is
written; at settlement the plaintext and the salt are revealed, and anyone can recompute the
hash. The canonicalisation is frozen from day one by golden tests, because a change would
break the verification of the whole history and cannot be repaired afterwards.

The claim is deliberately small: Git commit dates can be forged, so this is tamper-evidence
under branch protection, not a timestamp. On 2026-10-16 the owner chose to switch the
attestation and the public scorecard off and to make the documents say so until something is
actually published (`562fe73` removed claims that nothing backed). The append-only ledger on
the `attestation-log` branch (WIA-14) and the rule that `revealed_at` is stamped only from that
ledger (WIA-15) followed. `attestation_enabled` stays off until the owner has protected the
branch and enabled Pages, as the [resume checklist](resume-checklist.md) lists.

*Costs:* nothing is verifiable by a stranger until the owner switches it on. *Rejected:* an
external timestamping service for now (OpenTimestamps stays an optional later stage).

**Guards** [`tests/domain/test_attestation.py`](../tests/domain/test_attestation.py) `test_golden_hash_v2`, `test_commit_golden_flat` · [`tests/test_readme_claims.py`](../tests/test_readme_claims.py) `test_readme_links_attestation_docstring`

### D-5 · Charts are inline HTML

**Date** 2026-07-10 · **Status** in force · **Commits** `2f0ffe9`

The three charts of the email were `<img>` tags that pointed at `quickchart.io`. Gmail and
Outlook block remote images by default, so the middle of the report was holes, and every send
handed the portfolio's deltas and sentiment scores to a third party inside the URL. The charts
are table and `div` bars in the body of the message now, built with the technique of the
tested sparkline, and each bar keeps a minimum width and prints its value, so a −0.5% bar can
never look like −8%. The functions that returned a URL were renamed to return HTML.

*Costs:* a chart is less expressive than a rendered image. *Gains:* no external host, no data
in a URL, and the email renders the same with images blocked.

**Guards** [`tests/application/test_report_charts.py`](../tests/application/test_report_charts.py) `TestBuildChartUrl::test_returns_inline_html_not_url` · [`tests/application/test_report_builder.py`](../tests/application/test_report_builder.py) `TestDeltaChart::test_renders_inline_bars_not_a_remote_image`

### D-7 · `config.toml` is the one place for non-secret configuration

**Date** 2026-06-03, tightened 2026-10-21 · **Status** in force · **Commits** `1a68875`, `e71a1fe`, `781fda0`, `c83ee77`

`1a68875` moved the configuration out of variables into a file. The committed `config.toml`
now holds everything that is not a secret: symbols, thresholds, flags, models,
budgets and the experiment definitions. `.env` and the repository secrets hold only secrets
and the two environment switches `DB_WRITES_ENABLED` and `PAID_CALLS_ENABLED`. The order of
precedence is environment, `.env`, `config.toml`, then the defaults in code, and a key in
`config.toml` that `Settings` does not know is a startup error, so a typo cannot silently do
nothing. A test builds the Fast Loop from the production file, and another fails when
non-secret configuration leaks into a workflow.

*Costs:* the file is public, so an address in it is public (the SEC contact there is an alias
for that reason). *Gains:* one versioned, reviewed, validated source, and a diff that shows
what changed between two runs.

**Date** 2026-10-24, confirmed 2026-10-25 · **Status** in force · **Commits** `c2e00b5`, `5a315c8`, `95dc8cf`, `a3d7ac8`, `d769137`, `2ee4ae5`, `dd116f4`, `a8b59a8`

### D-10 · Provider failures have a taxonomy, and broad handlers only go down

**Date** 2026-10-24 · **Status** in force · **Commits** `806bb00`, `dd69f93`, `5b65b4b`

`src/application/errors.py` defines `PortError` and four classes under it: `ProviderUnavailable`,
`QuotaExhausted`, `MalformedPayload` and `NotFound`. An adapter translates the exception of its
provider into one of them and keeps the provider's type as a base class, so an old
`except requests.RequestException` still works while the graph and the entry points catch the
taxonomy. The type of a translated error is logged with its origin, for example
`ProviderUnavailable[HTTPError]`. New code does not write `except Exception`; a test counts the
broad handlers in `src` and the entry points, and its baseline may only be lowered: when a
change really needs a new best-effort handler, another one is narrowed in the same change.

*Costs:* each adapter needs a translation. *Gains:* a quota, an outage and a garbage answer are
told apart in the logs, the telemetry and the degradation paths, and a programmer's error stops
passing for a missing signal.

**Guards** [`tests/test_exception_ratchet.py`](../tests/test_exception_ratchet.py) `test_broad_except_count_does_not_grow`

### D-11 · The email is a registry of sections

**Date** 2026-10-24 · **Status** in force · **Commits** `0509d91`, `608f3a8`, `25b9554`

The email used to be one function with a slot per section. It is now the tuple

*Costs:* a new section touches four places. *Gains:* the order of the mail is data, a field that

checked against the registry.

## Flag rationale

Why each feature flag exists, what it replaced, what it costs and how its design was settled:
the reasons, the history and the design details that the short description in
[configuration](configuration.md#feature-flags) leaves out. These are reference entries, not
numbered decisions: they carry no `D-N`, and a commit or a test is cited inline where it matters.
What a flag does, when to turn it on and what it requires (the migration, the secret, the order
of switching on) stays in configuration, which links to the entry here; the defaults, the
migrations and the status of every flag are in its [flag table](configuration.md#flag-reference).

<a id="flag-edgar-reddit"></a>

### `insider_flow_enabled` and `social_velocity_enabled`: why both are off

**Insider flow and social velocity are off because both sources refuse the Fast Loop** (since 2026-10-24). From at least 2026-07-27, the oldest run whose logs GitHub still keeps, every run got `403` on every symbol from both sources, so the Alpha Signals cells for insiders and social were always empty, and the fusion score never had an insider vote.

- **SEC EDGAR** (`insider_flow_enabled`) answers `403 Forbidden` with SEC's "Request Rate Threshold Exceeded" page on the *first* request of a run, from GitHub Actions and from a residential IP alike. The `User-Agent` carries a contact address (`edgar_user_agent`) as [SEC's fair-access rules](https://www.sec.gov/os/accessing-edgar-data) require, and the failing runs sent at most five requests a second, so this is a lasting block, not the brief throttle that lifts after 10 minutes below the limit. SEC says it may block IP addresses that submit excessive requests, and the adapter used to break the limit: no pacing, the 1 MB `company_tickers.json` downloaded again for every symbol, and up to 22 requests per symbol across `symbol_concurrency` threads. The adapter now complies: one pacer shared by all threads spaces requests at least 0.12 s apart (about 8 a second), the ticker map is downloaded once per cycle, and the first `403` ends EDGAR for the rest of the cycle with one warning instead of a traceback per symbol, because further requests would only keep the block alive. Only SEC can lift the block. To re-enable, email `webmaster@sec.gov` with the "Reference ID" shown on the 403 page, then set `insider_flow_enabled = true` and start one manual Fast Loop run to confirm. The same block keeps `corporate_events_enabled` (DAT-17, 8-K filings in the prompt) off; it also waits for the end of EXP-02/03. Switching to a new contact address to get past the block would be circumvention, not a fix.
- **Reddit** (`social_velocity_enabled`) answers every anonymous `search.json` request from a GitHub Actions runner with `403 Client Error: Blocked`. Reddit's API rules require OAuth for programmatic clients, and third-party reports say Reddit closed unauthenticated JSON in 2026. The only compliant fix is a registered OAuth app with client credentials, which is a new credentialed integration and is not built. The adapter now stops after the first `403` of a cycle as well. Little is lost meanwhile: a search returns mention counts without sentiment, so the social snapshot never votes in the Alpha Fusion Score (see below).

**Insider flow covers stocks only** (`has_insider_filings` in `src/domain/insider_flow.py`, the same boundary as fundamentals and valuation). Crypto has no SEC insiders, and in SEC's ticker map `BTC` or `ETH` can name an exchange-traded trust, which would hand a crypto row someone else's Form 4 flow. ETFs are open-end funds that file no Form 4, so EDGAR could only return an empty window, and an empty window votes neutral with the largest fusion weight (0.35), pulling every ETF's score towards zero. `AlphaEnrichmentUseCase` therefore never asks the insider port about a crypto or ETF symbol, which also saves about two SEC requests per ETF per cycle.

Both flags are part of `config_hash`, so turning them off starts a new track-record segment; turning them off before the first weekday cycle on the new database (2026-10-26) keeps that cost at almost nothing.

### `digest_quiet_policy`: a short email on a quiet day, not no email

**A full 40–70 KB email on a day without a signal teaches the reader that the email usually says nothing** (MAIL-35, decision 2026-10-23, option b). On such a day `compact_when_quiet` sends five lines instead: the largest move against its threshold, the gate thresholds and the portfolio (or watchlist) state, with the full footer. The footer stays whole because the data sources' terms require the attributions and the notice on every email that shows their data ([data sources and terms](how-it-works.md#data-sources-and-terms)).

**Quiet is defined narrowly** so that the short email never hides news: an empty lead, no settlement, no watch shock, no symbol past the gate (an analysed one has a prediction, a budget-cut one a move worth seeing), no failed symbol and not the onboarding cycle. A failed read of the settlements is not quiet either: the full email warns about it.

**No email at all (`skip_when_quiet`) is not offered yet.** Without the weekly heartbeat of MAIL-28, a silent inbox cannot be told apart from a broken pipeline, so `Settings` accepts only `always` and `compact_when_quiet`; the domain keeps the third policy for when the heartbeat ships.

<a id="flag-yield-curve"></a>

### `yield_curve_enabled`: a vote, not a veto

The FRED yield curve is no longer render-only. When **both** `yield_curve_enabled` and `regime_aware_enabled` are on, an inverted 10Y-2Y spread is cast as one `ELEVATED` **vote** into `RegimeDetector`. It is a vote, not a veto: `RegimeDetector` needs two `ELEVATED` votes to declare `RISK_OFF`, so an inversion on its own only moves the regime to `NEUTRAL`. That is deliberate — inversions can persist for months, and a veto would pin the agent in risk-off for all of it. The net FinOps effect is a saving: `RISK_OFF` raises the volatility threshold, so fewer cycles ever reach the paid ports.

<a id="flag-macro-series"></a>

### `macro_series_enabled`: market state variables from FRED

`macro_series_enabled` (no migration; the same free `fred_api_key` as the yield curve) reads five market state variables from FRED **once per cycle** (DAT-22, `MacroSeriesPort`, `FredClient.fetch_macro_series`): `VIXCLS` over the last year, the high-yield option-adjusted spread `BAMLH0A0HYM2` over the last three weeks, and the latest observation within two weeks of `VXNCLS`, `T10Y2Y` and the weekly `NFCI`. Every window ends on the cycle's day (`observation_end`), and every value keeps the day it was **observed**, not the day it was fetched: FRED publishes with a lag (`VIXCLS` is the previous session) and `NFCI` is weekly. `src/domain/macro_series.py` turns them into two regime votes and into features. The regime used to rest on the daily price change of proxy ETFs with 1% and 3% thresholds, which for VIXY (in contango) is noise; the level of the VIX and of credit spreads are steadier state variables. With `regime_aware_enabled` the VIX percentile over the year (the share of the year's observations at or below the latest, with at least 60 observations) votes `ELEVATED` from the 75th percentile and `CRITICAL` above the 90th, and the 5-session change of the high-yield spread votes `ELEVATED` from +0.25 pp and `CRITICAL` from +0.50 pp. They join the yield-curve vote in `RegimeDetector`, so a `CRITICAL` vote means `RISK_OFF` and a single `ELEVATED` vote only `NEUTRAL`; votes can only raise the volatility threshold, never lower it. With `market_features_enabled` the features `vix_level`, `vix_percentile_1y`, `vxn_level`, `hy_oas`, `hy_oas_change_5d`, `term_spread_10y2y`, `nfci` and `macro_observed_on` (series → ISO observation day) join every feature vector of the cycle. A failed series is logged without its key and left out; all five failing gives no snapshot, no votes and `null` features. The values are not cached in the database: the `macro_series` table from the audit entry needs a migration this change did not get, so history is not kept between cycles. The flag is part of `config_hash`, because its votes can change the regime, which tightens the gate and reaches the prompt as the regime label. It ships **off**.

<a id="flag-regime"></a>

### `regime_hysteresis_enabled`, the regime in the header and `regime_tagging_enabled`

`regime_hysteresis_enabled` and `regime_exit_confirmations` (**require migration `033`**) add hysteresis to the market regime. `RegimeDetector.classify()` is stateless, so a signal oscillating around a boundary used to switch the volatility-threshold multiplier every cycle: noise passing for a signal. With the flag on, `main_agent._resolve_regime` reads the newest row of the `regime_history` table (`cycle_at`, `raw_regime`, `regime`, `streak`) and passes the raw regime through `apply_hysteresis` (`src/domain/regime.py`): entering `RISK_OFF` is immediate, while leaving it needs `regime_exit_confirmations` (default `2`) **consecutive** raw readings outside `RISK_OFF`. `NEUTRAL` and `RISK_ON` count alike, since both loosen the gate the same way, and the regime after the exit is the latest raw reading; a raw `RISK_OFF` resets the count, and moves between `NEUTRAL` and `RISK_ON` are not delayed. Each cycle with a regime (regime aware on and a Risk Watch report) writes one row with the raw regime, the effective regime and the count. The asymmetry is FinOps-safe: `RISK_OFF` only raises the threshold, and the effective regime is `RISK_OFF` whenever the raw one is, so hysteresis can only keep the threshold higher for longer, never lower it. The first cycle without history uses the raw regime, as before. A failed read (for example before the migration) is logged and the cycle uses the raw regime, exactly as with the flag off, and writes no row, so a missing read cannot reset a running count; a failed write is logged and the next cycle reads the older state, which can only delay the exit. `prediction_logs.regime` is not the source of the previous regime: it is written only on a saved prediction, and a cycle where no symbol passed the gate saves none. **A confirmation is one Fast Loop run, not one day**: on the cron schedule two runs are a few hours apart, but with manual dispatches the exit can take as long as the next two runs, days or weeks; a retried run counts as a run too. Both fields are part of `config_hash`, because they change the effective threshold of the gate. The flag ships **off**: before the migration the table does not exist, so the read and the write would fail every cycle.

**Regime in the email header (ALR-05).** With `regime_aware_enabled` the regime changes the gate of every cycle, yet it used to reach only the logs, so a reader saw fewer predictions without knowing why. `main_agent._resolve_regime` now also hands the cycle's regime to the report (`on_banner`, `ReportContext.regime`, `src/application/report_regime.py`), and the HTML and plain-text header carry one line under the start time, e.g. "Reżim: RISK_OFF · próg ×1,5 (2,0% → 3,0%) · powód: 2 głosy ELEVATED": the effective regime (after hysteresis), the threshold multiplier, the stock threshold `volatility_threshold` before and after it, and the reason from `RegimeDetector.reason` ("brak danych makro", "alert CRITICAL", the number of ELEVATED votes, "wszystkie sygnały NORMAL", or "histereza: trzymam RISK_OFF (surowy odczyt …)" while hysteresis holds the regime). Without the flag or without a Risk Watch report there is no line. **A regime change leads the email** (ALR-05, step 2): when the effective regime enters RISK_OFF ("🌧️ Rynek przeszedł w RISK_OFF, analiza rzadsza") or leaves it ("🌤️ Rynek wyszedł z RISK_OFF (NEUTRAL), analiza częstsza") compared with the previous cycle, the lead gets an item ranked right below a CRITICAL quota alert, and the subject inherits it when no such alert exists. The previous regime comes only from the hysteresis state, so the item needs `regime_hysteresis_enabled` (**requires migration `033`**): without it the raw regime could flip every day. A switch between NEUTRAL and RISK_ON keeps the multiplier at 1.0 and is no lead item.

`regime_tagging_enabled` (uses the `prediction_logs.regime` column of migration `017`) separates tagging from filtering. Before, the regime of a prediction was written only with `vector_memory_enabled`, so with vector memory off the column stayed `NULL` even though `regime_aware_enabled` was on, and there was no history to split the hit rate by regime. Now every saved prediction carries the canonical regime key (`canonical_regime_key` of the cycle's regime label, `UNKNOWN` when the cycle has no regime) whenever the tag is on, while the RAG filter on analogues of the same regime stays behind `vector_memory_enabled`; vector memory still tags as before. The field has no value by default (`None`): `main_agent` then follows `regime_aware_enabled`, which production `config.toml` turns on, so production tags every prediction without a new key. An explicit `true` or `false` wins. This is a deliberate exception to the rule that a new write ships behind a flag that is off: migration `017` was confirmed applied in production (state read on 2026-10-18), so the key cannot return `PGRST204`. A deployment that has `regime_aware_enabled` on but has not applied `017` must set `regime_tagging_enabled = false`, otherwise the whole prediction write fails. Zero calls, zero cost, and the field is outside `config_hash` (a write-only switch; the forecast is the same with the tag or without it).

<a id="flag-earnings"></a>

### `earnings_calendar_enabled`, `earnings_cache_enabled` and `finnhub_earnings_calendar_enabled`

The earnings calendar works the same way. With `earnings_calendar_enabled = true`, the next quarterly report is fetched **before** the graph runs and its proximity raises the volatility threshold (`IMMINENT` ≤ 2 days → ×1.5, `NEAR` ≤ 7 days → ×1.15, otherwise ×1.0). A 12-hour prediction taken the day before earnings is a coin flip, so the agent tightens the gate instead of burning tokens on analysis the report will invalidate — cutting spend and cleaning up the hit rate at once. The earnings and regime multipliers **compound**, and both are guaranteed `>= 1.0`, so the gate can only ever tighten. One domain rule, `effective_threshold` in [`src/domain/asset.py`](../src/domain/asset.py) (FIN-08), sets the threshold of every gate — the main gate, the paid mistake diagnosis in `reflect_node`, the council gate and the tool-use gate — so in `RISK_OFF` or before earnings the tool-use loop needs a bigger move too (crypto has no separate tool-use threshold and uses `tool_use_volatility_threshold`). The event is fetched once per symbol and injected into the alpha-signals enrichment, so the gate adds no second paid call. With the flag off, no earnings port is touched at all. Since FIN-09 the adapter asks Alpha Vantage `EARNINGS_CALENDAR` **once per run, without a symbol**: the CSV lists every company reporting in the next three months, the first symbol to ask fetches it (under a lock, since symbols run in parallel) and every symbol reads its nearest report date from memory — one request a cycle instead of one per symbol, before the volatility gate. It rotates over every key of `ALPHA_VANTAGE_API_KEYS` on a soft limit (`Note` waits once on the same key, `Information` moves on); when every key is limited, the run has no earnings dates and a `WARNING` quota alert (`Alpha Vantage earnings`) says so. A failed fetch is not retried by the next symbol. The full CSV is a few hundred KB; tickers with a dot are not in it. `earnings_cache_enabled` (FIN-11, **requires migration `053`**) moves it to the Slow Loop: the weekly run refreshes the `earnings_cache` table (one report date per stock symbol, ETFs and crypto skipped) with every key of `ALPHA_VANTAGE_API_KEYS`, rotating on a soft limit, and the Fast Loop reads only that table — zero Alpha Vantage requests for the calendar, so the FIN-32 daily budget counts one request per symbol again. The cache stores the date, not the day count, so the gate counts `days_until` on the cycle's day; an entry is valid for `EARNINGS_CACHE_TTL_HOURS` (144 h, Monday to Friday after the Sunday refresh). A report announced after the refresh is missed until the next one. A symbol without a cached entry gets no earnings multiplier. Outside `config_hash` (owner decision FIN-11: the cache changes where the same report date comes from, not the prediction recipe, so switching it does not cut the track record into segments); ships **off** until the migration.

`finnhub_earnings_calendar_enabled` (DAT-20) adds the Monday section `📅 Ten tydzień` to the email: the watchlist stocks (ETFs and crypto left out) that report from Monday to Sunday, with the day, the timing against the session (`przed sesją` / `po sesji` / `w trakcie sesji`, left out when Finnhub's `hour` is empty) and the EPS estimate. `FinnhubEarningsCalendarAdapter` asks `GET /calendar/earnings?from&to` once per run **without a symbol** — the answer lists every company in the 30-day window and is filtered to the watchlist — through the shared Finnhub limiter; a failed or empty answer just leaves the section out. Monday is the day in `display_timezone`. With the owner's portfolio (`portfolio_positions_enabled`) the same flag adds a lead tier on every day: a position of at least 10% of the portfolio whose company reports today or tomorrow (`MSFT (24% portfela): wyniki jutro po sesji`), right below a move of your position; that needs the calendar daily, so the report asks once a day with a portfolio, and on Monday the section and the lead share the one answer. The flag is presentation only (outside `config_hash`): the earnings gate keeps its Alpha Vantage source or cache. **Turn it on only after the provider terms review (BEZ-28) and a probe of the free plan** — the free tier may cap the date range or drop fields; the probe is one manual request `curl -s "https://finnhub.io/api/v1/calendar/earnings?from=<monday>&to=<monday+30d>&token=$FINNHUB_API_KEY"` checking that rows for several watchlist stocks come back with `date`, `hour` and `epsEstimate`.

<a id="flag-calibrated-confidence"></a>

### `calibrated_confidence_enabled` and `isotonic_calibration_enabled`

`calibrated_confidence_enabled` closes the calibration loop. The repo already computed a reliability curve and ECE but only *displayed* them: when the 80–90% confidence bucket historically hit 55%, the ranking still trusted the raw 85%. With the flag on, `strength = confidence x |delta|` is computed on the confidence **corrected by that bucket's historical hit rate**, shrunk toward the raw value when the sample is small (`weight = count / (count + 10)`). The buckets come from directional predictions only (WIA-39, `src/application/signal_calibration.py`): a SIDEWAYS call hits for free on a quiet day, so mixing "SIDEWAYS 0.8" into the bucket of "BULLISH 0.8" inflated the hit rate that calibrates a bet on direction. Calibration assumes the confidence carries information: if the LLM always says ~0.7, it only moves every signal to the base rate and the reordering is noise. A domain rule therefore checks the discrimination first (WIA-38, `confidence_reorders_ranking` in `src/domain/calibration_curve.py`): when the AUC of the directional confidences against their hits (Mann–Whitney, ties count ½) is below `0.55` on an `n_eff` (by UTC day) of at least `50`, the ranking stays on the raw confidence, as without history, and the cycle logs a `WARNING` with both numbers. A smaller sample keeps the calibration, because the AUC interval is too wide to decide. `evaluate --discrimination` prints the same AUC for the LLM and for the council's consensus strength, with a cycle-bootstrap interval and the risk–coverage points. Calibration therefore reorders the "Najsilniejsze sygnaly" ranking rather than merely labelling it, and each signal card shows the raw and the calibrated confidence next to each other with the bucket's sample size (`85% → 58% po kalibracji (n kubełka: 40)`). It is render-only: nothing is persisted, and in particular the `confidence_calibration` column from migration `016` (an LLM judge's post-hoc score) is never overwritten. The flag is independent of `calibration_curve_enabled` on purpose — one draws the Track Record section, the other changes the ranking.

`isotonic_calibration_enabled` (no migration; effective only with `calibrated_confidence_enabled`) replaces the bucket shrinkage in the signal ranking with an isotonic map when that map wins out of sample (ML-28). The bucket mapping is not monotone (a 0.8 bucket can end up below a 0.7 one) and was never scored outside the sample it was built on. `fit_isotonic` in `src/domain/isotonic_calibration.py` fits a non-decreasing map from confidence to hit rate with pool-adjacent-violators (ties in confidence pooled first, linear interpolation between knots, the end values outside them), and `select_isotonic_calibrator` fits both the map and the buckets on the directional settlements from 60 to 30 days ago and scores them with the Brier score on the last 30 days next to the raw confidence. The map enters the ranking only when its Brier is lower than both, and it is exactly the map that was scored; each window needs at least 30 samples (`MIN_ISOTONIC_SAMPLES`), otherwise the ranking keeps the buckets. SIDEWAYS predictions stay out, as in the bucket calibration (WIA-39), and when the confidence carries no ranking information (WIA-38) there is no calibration at all. The flag adds one free read of 60 days of settlements to the report; a failed read logs and keeps the buckets. It changes only the ranking order and the calibrated confidence shown next to a signal, not any prediction, so it is outside `config_hash`.

`isotonic_class_calibration_enabled` (ML-54, owner decision 2026-10-25: the global map first, maps per asset class later) splits that map by asset class. Crypto has a different volatility and a different SIDEWAYS band than stocks and ETFs, so one shared map averages two different calibration curves. Each class with at least 30 samples in each window (`MIN_CLASS_ISOTONIC_SAMPLES`, the same minimum as the global map, because the class goes through the same out-of-sample test) gets its own decision: its own map when that map beats the raw confidence and the buckets on the class's last 30 days, otherwise the buckets — the global map was never scored on that class alone. A smaller class keeps the global map, since a stepwise map on a few dozen samples overfits. The calibration read carries the `symbol` for this (column from `001`); the class comes from `crypto_symbols`, the rule that sets the asset class of the cycle's results. Outside `config_hash` for the same reason as the global map.

<a id="flag-messenger-digest"></a>

### `messenger_digest_enabled`: a silent failure fixed

`messenger_digest_enabled` fixes a real, silent failure. `TelegramNotifier` and `SlackNotifier` used to receive the **full** plain-text report, which routinely exceeds Telegram's 4096-character limit: the API answers `400` and the push disappears. Worse, the per-subscriber fan-out branch skipped `notifier.send_report` entirely, so push never fired once anyone was subscribed. With the flag on, push channels leave the email `CompositeNotifier` and instead receive a short digest ending with a one-line investment disclaimer (MAIL-20): the header in local time, up to three lead items of the email (`⚖️ NVDA -4,2%, rada PODZIELONA`, each clipped to 160 characters), the cycle counts, the closed-prediction scorecard and the top three of the email's signal ranking in rank order with the calibrated confidence when there is one (`Sygnały: 1. 📉 NVDA 64% · 2. 📈 AAPL 50% …+5 więcej`; without a ranked signal the line falls back to the trend arrows in cycle order). Telegram gets it with `parse_mode=HTML`: the subject in bold and every other character escaped. The digest carries no portfolio amounts. It is hard-capped at 1500 characters with the disclaimer's length reserved before the clamp and sent **once** per cycle over the full results, independent of the fan-out. Zero cost — the Telegram Bot API and Slack webhooks are free. With the flag off the legacy composite is preserved; Telegram sends that text with `parse_mode=HTML` too, escaped, so it reads the same as before.

<a id="flag-model-scorecard"></a>

### The `model_scorecard_*` flags

`model_scorecard_enabled` (migration `019`) surfaces a check users never saw: the walk-forward gate that refuses to ship a model worse than the naive baselines. The gate is necessary, not sufficient (DOC-06): a candidate that passes it beat the strongest baseline by the 2% margin and the paired loss test on a few hundred correlated out-of-sample points at best, which rules out a model that is clearly worse but does not prove skill ([how it works](how-it-works.md), step 10). Each Slow Loop run records one row **per symbol** (that symbol's own walk-forward evaluation, which never writes weights) plus one row with `symbol = 'ALL'` for the shared model, the only one that can ship weights; without the `symbol` column the rows would be indistinguishable. The report reads the **latest run only** (`latest_run_indices`: a gap of more than 2 hours between rows starts an earlier run, so the read window no longer merges weekly runs). The read window is 42 days, `MODEL_SCORECARD_WINDOW_DAYS = 2 × MODEL_STALE_AFTER_DAYS` in `src/domain/model_scorecard.py` (ML-15), not `track_record_days`: with a 30-day window the card disappeared 30 days after the last run, so its `STALE` badge was visible only on days 22–30. Its main verdict, "accepted N, rejected M, skipped K", comes from the shared model's `ALL` row, because that is the only model that can ship weights; the per-symbol evaluations follow on a separate line, "gate passed N, failed M, skipped K" (`evaluated_passed_gate` / `evaluated_failed_gate` / anything else), instead of being counted as skipped next to the shared model. A run without an `ALL` row (history from before the shared model) still aggregates all its rows into one verdict. Then comes the RMSE against baseline of the newest shipped candidate in that run (or of the newest candidate with metrics when none shipped), labelled with its symbol and sample count, plus directional hit rate, fold count, and a `STALE` badge past 21 days. Without `model_scorecard_run_id_enabled` (below) a manual re-run on the same day still merges with the scheduled run. A run where every candidate was rejected renders as exactly that; it is deliberate, uncomfortable truth rather than a bug. When the Fast Loop has no trained model loaded (cold start), the section says so instead of claiming the report runs on a proven earlier model. The section always carries `METRIC_NOTE`, which states that the metrics describe the *candidate on walk-forward folds* while the shipped model is refit on all data — without it a trust section would itself be dishonest. Writes are best-effort: a missing migration cannot break training.

`model_scorecard_baselines_enabled` (**requires migration `028`**) adds the gate's two newer baselines to each scorecard row: `drift_baseline_rmse` (the mean target of each fold's training part, predicted as a constant) and `llm_baseline_rmse` (`llm_trend_signal` times the mean absolute target of the fold's training part). The walk-forward gate has to beat the strongest of these and the zero-return `baseline_rmse` by the same 2% relative margin whether or not the flag is on; the flag only decides whether the two values are persisted. With them, the model card prints all three baselines and names the strongest; rows written before the migration or with the flag off render exactly as before. The flag ships **off**: before the migration the new keys return `PGRST204`, and because the scorecard write is best-effort the whole row would be lost without breaking training.

`model_scorecard_run_id_enabled` (**requires migration `049`**) stamps every scorecard row of one Slow Loop run with the same `run_id`: `main_trainer.py` draws one `uuid4` per run and passes it to the per-symbol rows and to the shared model's `ALL` row (ML-24). The model card then reads the run of the newest row by its `run_id` (`latest_run_indices_by_id` in `src/domain/model_scorecard.py`), so a manual re-run minutes after the scheduled one is its own run instead of doubling the verdict; when the newest row has no `run_id` (history from before the migration, or the flag off) the 2-hour gap rule of ML-03 applies as before. Old rows keep `run_id = NULL`: the runs they belonged to are not recorded in the database. The flag ships **off**: before the migration the new key returns `PGRST204` and the best-effort scorecard write would lose the whole row. It is outside `config_hash` (a write-only switch).

`model_scorecard_feature_stats_enabled` (**requires migration `052`**) stores the feature distribution of each training run in `model_scorecards.feature_stats` (JSONB, ML-21). `XGBoostAdapter.train()` already returned per-feature `mean` and `std`, but the scorecard write dropped them, so the drift detector existed only in a docstring. Each feature now also carries quantile bins of the whole training sample (`edges`, the inner decile cut points taken from the sample itself, so a discrete feature such as `llm_trend_signal` gets `-1/0/1` instead of interpolated edges, and `fractions`, the share of the sample in each bin) and `psi_recent_30d`: the Population Stability Index of the last 30 days of the sample (counted from its newest row) against its older part, on the bins of the older part (`src/domain/drift.py`). PSI is `null` without row timestamps or when either part has fewer than 20 values. The model card in the email reads it from the row its metrics come from and warns when any feature exceeds `0.25` ("Dryf cech (PSI > 0,25, ostatnie 30 dni próbki vs starsza część): price_delta 0,31"); rows without the column or written with the flag off render as before. **What "serving" means here**: the last 30 days are the logged inputs of settled predictions in `ml_feature_store`, not the live serving stream — a serving-side comparison needs a reader of `feature_snapshots`, which does not exist yet. The flag ships **off**: before the migration the new key returns `PGRST204` and the best-effort scorecard write would lose the whole row. It is outside `config_hash` (a write-only switch); the card reads the column whenever a row has it.

`model_scorecard_weights_sha256_enabled` (**requires migration `060`**) stores the sha256 of the weights file written by the run in `model_scorecards.weights_sha256` (CI-13). The weights travel as the `model-latest` Release asset, overwritten every week, and the Release notes describe only the latest file, so without the hash in the card a run's metrics cannot be tied to the weights that produced them, nor to the `model_version` of the predictions served with them (the sha256 of the same file, WIA-20). `XGBoostAdapter` hashes the bytes of the file it has just written, which is the file the Slow Loop workflow uploads, not a re-serialisation of the model. Rows of runs that wrote no weights (rejected, skipped, per-symbol evaluation) keep `null`. The flag ships **off**: before the migration the new key returns `PGRST204` and the best-effort scorecard write would lose the whole row. It is outside `config_hash` (a write-only switch).

`model_scorecard_provenance_enabled` (**requires migration `064`**) stores the provenance of each training run on its scorecard row (ML-22): `dataset_sha256` (the sha256 of the training rows — UTC timestamp, target and features sorted by name — with the row lines sorted first, so the input order does not change it while any changed value or duplicated row does; missing values and NaN are the same gap), `data_start` / `data_end` (the timestamp range of the sample), `n_per_symbol` (rows per symbol), `training_params` (the XGBoost parameters, with `random_state = 0` now explicit in `DEFAULT_PARAMS`; it was already the library default, so the weights stay byte-identical), `library_version` (`xgboost 3.2.0`), `feature_set_version`, `git_sha` (the commit of the run, `local` outside GitHub Actions) and the label overlap of the sample (ML-25): `label_overlap_measured` rows have a settlement time and a next row of their symbol, and `label_overlap_count` of them settled only after that next row, the cases the fixed 12 h purge of the walk-forward folds does not see (`null` before migration `050` adds `settled_at` to the view). The Slow Loop step summary shows the same pair for the shared model ("Label overlaps (settle after the next row)"), without the flag. Skipped runs carry no provenance. Independently of the flag, every accepted training writes a sidecar next to the weights (`data/models/price_predictor.json`) with the same fields plus the weights sha256, the target unit and the sample size, and the Slow Loop workflow uploads it to the `model-latest` Release with the weights. `uv run python main_tools.py reproduce-training` rebuilds the shared model's sample the way the Slow Loop does (read-only), keeps the rows inside the sidecar's date range, compares their fingerprint with the sidecar, refits with the sidecar's parameters and compares the tree dump with the saved weights; it prints `REPRODUCED` and exits 0, or says which step differs and exits 1 (2 when the sidecar or the weights are missing). A later run sees rows whose labels matured after the training, so reproduction is meant for the weights of the latest run. The flag ships **off**: before the migration the new keys return `PGRST204` and the best-effort scorecard write would lose the whole row. It is outside `config_hash` (a write-only switch).

<a id="flag-receipts"></a>

### `receipts_enabled`: the evidence chain behind a prediction

`receipts_enabled` (migration `020`) persists the evidence chain behind each prediction into a `decision_receipts` JSONB column: the RAG analogues actually used (now carrying their `id` and `similarity`, which the code used to discard), the SHAP-lite feature attributions, the **effective** volatility threshold after regime and earnings multipliers, and a `schema_version` from day one. Until now those artefacts were computed, rendered into one email and thrown away, so a prediction that turned out wrong could not be audited. The flag is a **precondition for graceful degradation, not a preference**: writing a new key before the migration exists returns `PGRST204` and kills the entire prediction write — the same gate `vector_memory_enabled` uses for its column. Zero cost — the data was already paid for this cycle. The MVP deliberately leaves provenance badges out (`AgentState` does not carry them; WIA-66 will add them to `schema_version: 2` as an optional `provenance` key without another bump). Since WIA-20 the receipt is written at `schema_version: 2` whenever the cycle has a prediction recipe (see [`recipe_version_enabled`](#flag-recipe-version)): every v1 key keeps its meaning, and the flat recipe fields plus `recipe_version` are added. JSONB needs no migration for the new keys, so v2 receipts start with `receipts_enabled` alone. The reader `read_decision_receipt` (`src/application/decision_receipt.py`) accepts v1 and v2, tolerates any missing optional key and returns `None` for an unknown version instead of guessing. Since WIA-56 the receipt is also read: `RepositoryPort.get_receipt` / `find_receipts` feed `main_tools.py explain` (see [running-locally.md](running-locally.md)), and the 24-hour settlement read carries `decision_receipts` only while `receipts_enabled` is on, so under a missed prediction the email prints one line from it, `🧾 Kwit: stała na analogach #3f2a1b9c (0,91) przy progu 3,0%`; with the flag off the settlement select leaves the column out and the email has no such line.

### `feature_set_version_enabled` and `feature_set_filter_enabled`

`feature_set_version_enabled` and `feature_set_filter_enabled` (both **require migration `027`**) separate the two meanings of `news_volume_24h`. Since commit `3738ef2` the Alpha Vantage feed is bounded to the last 24 hours; older rows counted relevant articles among the 50 latest of any age, and the feature kept its name. `FEATURE_SET_VERSION` in `src/application/ml_features.py` is the current version (`3`; `1` = the unbounded feed, `2` = the 24-hour window over the merged feed of the whole watchlist, `3` = the lazy per-symbol feed of FIN-04, where `news_volume_24h` counts only the up to 50 articles of the symbol's own request; `4` = version `3` plus the market features in `feature_snapshots`, stamped only with `market_features_enabled`, see [the feature snapshots](#flag-feature-snapshots)). With `feature_set_version_enabled` the Fast Loop stamps `prediction_logs.feature_set_version` on every prediction; with `feature_set_filter_enabled` the Slow Loop reads only rows of the current version from `ml_feature_store` (rows of version `1` and rows with an unknown, `NULL`, version drop out). Migration `027` backfills version `1` only where it is certain, for rows timestamped before the commit (2026-10-18 21:47:22 UTC); later rows without a stamp stay `NULL`, because the moment the new code reached production is not recorded in the database. The filter cuts the training history, so until enough rows of the current version settle the shared model is skipped: the result carries `status = skipped`, `n_samples` and `feature_set_version`, the Slow Loop logs a warning, and the scorecard row keeps `n_samples`. Both flags ship **off**: writing the key or filtering on the column before the migration returns `PGRST204` (the whole prediction write fails) or `400` (training fails). Turn the stamp on right after the migration, so current-version rows start to accumulate; turning the filter on is the moment the model stops learning from old-meaning rows. Turn the filter on only once the current version has at least 75 valid rows in the view (`SELECT count(*) FROM ml_feature_store WHERE feature_set_version = 3 AND price_delta IS NOT NULL AND target_return IS NOT NULL`): with four folds the walk-forward gate needs 75 samples (`MIN_OOS_POINTS = 60` out-of-sample points), so an earlier switch only skips the shared model; until then training mixes the two meanings of `news_volume_24h`. While the Fast Loop is paused no current-version rows settle, so turning the filter on then leaves the shared model with an empty sample (an explicit skip with `n_samples`). `main_backtest.py` follows the same filter (ML-51), so the offline verdict and the training read the same sample.

### `recipe_version_enabled` and the recipe

`recipe_version_enabled` (**requires migration `030`**) stamps `prediction_logs.recipe_version` on every prediction: the sha256 of the prediction recipe, so the track record can be split by recipe instead of mixing prompts, models and council line-ups. `main_agent.build_prediction_recipe` computes the recipe **once per cycle** and injects it through one field, `AgentGraphDeps.recipe`, whenever something records it (`receipts_enabled`, `recipe_version_enabled` or `attestation_enabled`, whose v2 commitment binds `recipe_version`). Its parts are the provider and model of the main LLM (with `model_routing_enabled`: provider `routing`, model `openai:<cheap>|<provider>:<frontier>`), the council provider and model, `prompt_sha256` (the source of the prompt template modules `prompts.py`, `council_prompts.py`, `_prompt_safety.py`, not the rendered prompt, which differs per symbol), `personas_sha256` (file names and bytes of `data/council_personas/*.json`), `config_hash`, `model_version` (`cold_start` without a weights file, otherwise the sha256 of the `.ubj`) and `universe_version` (the sha256 of the sorted set of `symbols` + `crypto_symbols`; order and duplicates do not matter, so adding or removing a ticker starts a new segment instead of passing for a change in accuracy), and `protocol_sha256` (WIA-42: the sha256 of the bytes of [`evaluation_protocol.toml`](../evaluation_protocol.toml), comments included, so a new evaluation protocol starts a new segment and results scored under the old one stay in theirs). `config_hash` (`Settings.config_hash()`) hashes the sorted settings that shape the forecast. `src/config.py` splits every `Settings` field into exactly one of three lists, and a test fails when a field is in none or in two: `SECRET_SETTINGS_FIELDS` (API keys, tokens, database credentials, e-mail addresses, push targets, the SEC contact header; another test fails when a field with a secret-looking name is missing from it), `NON_RECIPE_SETTINGS_FIELDS` (presentation and delivery such as `display_timezone`, the notification, push, subscription, web-digest and public-scorecard switches and output paths; report sections computed after the prediction such as VaR, stress test, track record, calibrated ranking, cycle diff and `track_record_days`; the paper-PnL cost assumptions `paper_cost_bps` and `crypto_paper_cost_bps`; write-only switches such as `db_writes_enabled`, `receipts_enabled`, `feature_set_version_enabled`, `recipe_version_enabled`, `regime_tagging_enabled`, `feature_snapshots_enabled`, `interval_coverage_enabled`, `gate_delta_enabled`, `experiment_arms_enabled`, `model_scorecard_baselines_enabled` and attestation; other jobs and training: shock watch, deadman, calibration judge and `feature_set_filter_enabled`, whose effect reaches predictions only through new weights, which `model_version` already records) and `RECIPE_SETTINGS_FIELDS` (thresholds, models, providers, symbols, data sources and every switch on the prediction path, `tool_use_*` included, and the `experiments` definitions, whose arms change prompts). The first two lists are cut out before serialisation; a field in neither stays in the hash. When it is unclear whether a field changes the forecast, it stays in the recipe, because splitting one recipe into two segments is safer than merging two recipes into one: `symbol_throttle_seconds` and `symbol_concurrency` (concurrency above 1 turns contagion off, and the throttle keeps the council clear of rate limits), `risk_symbols`, `risk_symbol_types` and `nbp_enabled` (they feed the market regime that can tighten the gate), `reflection_min_age_hours` and `reflection_max_age_hours` (which mistakes reach the prompt), and `ml_model_path` and `council_personas_dir` (their contents are hashed separately). The commit and the run (`git_sha`, `run_id` from `RunContext`) go into the v2 receipt for audit but not into `recipe_version`, so one recipe across many runs stays one segment. Two side effects to know: the prompt hash changes on cosmetic edits of those modules (a comment, a docstring), and `config_hash` changes with any field of `RECIPE_SETTINGS_FIELDS`, including the cautious ones listed above. With `receipts_enabled` the same recipe fields land in the v2 receipt even while this flag is off. Rows written before the migration or with the flag off keep `recipe_version = NULL`; the migration has no backfill, because the recipe of old rows cannot be rebuilt from the database. `uv run python main_tools.py evaluate --by-recipe` adds the directional hit rate per recipe version (rows without a version form the `unversioned` segment); it also needs the migration. `--by-universe` does the same per universe version, read from the v2 receipt (`decision_receipts->>universe_version`), so it needs no new migration; rows without a v2 receipt are `unversioned`. Universe versions of rows written before the v2 receipt are not reconstructed: the universe lives in `config.toml` only since 2026-06-03, and before that production read the unversioned `vars.SYMBOLS` repository variable. The flag ships **off**: writing the key before the migration returns `PGRST204` and the whole prediction write fails.

<a id="flag-feature-snapshots"></a>

### `feature_snapshots_enabled` and `market_features_enabled`

`feature_snapshots_enabled` (**requires migration `031`**) writes one point-in-time feature vector per symbol and cycle to the `feature_snapshots` table (`symbol`, `as_of`, `feature_set_version`, `features` JSONB, `gated`), from both terminal nodes of the graph, next to the price snapshot, so an **ignored** cycle gets a row too. The exception is a re-baseline cycle after a pause (a reference price older than 96 h, `SkipReason.STALE_REFERENCE`): its `snapshot_delta` is many days of drift, not a cycle move, so it saves only the new price snapshot and no vector. Until now the training data (`ml_feature_store`, built from `prediction_logs`) held only the cycles that passed the volatility gate: the model learned from the days with a large move, and the samples per symbol took months to collect. The free features (`FREE_SNAPSHOT_FEATURES` in `src/application/ml_features.py`) are written in every cycle and come only from data already in the cycle state, with **zero new external calls, free ones included**: the price and the previous snapshot price, the change against that snapshot (`snapshot_delta`, the one that drives the gate, not the model's `price_delta` against the previous prediction) and its absolute value, the effective threshold after the regime and earnings multipliers, the canonical regime key and both multipliers, the Alpha Fusion score, the asset type and the valuation verdict from the fundamentals cache. A missing source is written as `null`, never as `0.0`, so silence does not pass for a neutral market. A cycle that passed the gate (`gated = true`) adds the paid features: the `ML_FEATURE_COLUMNS` vector exactly as the model received it, the LLM `confidence_score` and the `data_quality_flags` (training can drop the "SIDEWAYS 50%" placeholder written after an LLM failure). Without `market_features_enabled` (below) no realised volatility over a price window is stored, because the state does not carry one and reading the history would be a new call. The label is **not** stored: the return is joined later from `price_snapshots` by `(symbol, as_of)`. The rows are idempotent per symbol and UTC hour (generated `as_of_hour`, upsert like `price_snapshots`), `feature_set_version` is `FEATURE_SET_VERSION` (`4` with `market_features_enabled`), and a failed write is logged without stopping the cycle. The Slow Loop evaluates two models on these vectors (ML-52: a free-feature model on every cycle and an LLM-feature model on gated cycles, see `snapshot_training_enabled`) and reports the gated vs non-gated selection; history has no stored vectors, so that training starts from zero rows. The flag ships **off**: before the migration the table does not exist and every cycle would log a failed write. It is outside `config_hash` (a write-only switch; the forecast is the same with it on or off).

`market_features_enabled` (no new migration; effective only together with `feature_snapshots_enabled`, so it needs migration `031`) adds market features of the cycle to every feature vector and stamps the **feature set version `4`** on both the vector and, with `feature_set_version_enabled`, the prediction (ML-31, ML-32; brief W2 decision: the new features live behind a flag, and only the flag moves the version). Before the graph, `main_agent` calls `AnalyzeMarketUseCase.prepare_market_features` once per cycle: for each symbol of the cycle it reads the quote from the market port and the last 45 days of `price_snapshots` (a free Supabase read), and `price_features` in `src/domain/price_features.py` computes point-in-time features from them. One function serves training and serving: it sees only prices up to `as_of`, groups snapshots into daily closes (the last price of each UTC day) and returns only dimensionless numbers, so a price ×100 gives the same features. The features (`PRICE_FEATURE_NAMES`) are `ret_1`, `ret_5`, `ret_20` (returns over 1, 5 and 20 daily closes), `ret_1_over_vol_20` (the one-day return in units of σ₂₀, the sample standard deviation of the last 20 daily log returns), `log_realized_vol_20` (ln σ₂₀), `vol_ratio_5_20` (σ₅ / σ₂₀), `dist_from_20d_high` (price over the highest of the last 20 closes, minus 1) and `gate_move_z` (the move against the previous snapshot, the one the volatility gate judges, over σ₂₀). Once every symbol of the cycle has its quote, `cross_section_features` in `src/domain/cross_section.py` adds the move against the market (ML-32, `CROSS_SECTION_FEATURE_NAMES`): `ret_1_rank` (the percentile rank of `ret_1` in the cycle's universe, `0` the weakest, `1` the strongest, ties share the average rank), `ret_1_excess_vs_benchmark` (`ret_1` minus the `ret_1` of IVV, the benchmark the report already compares against; `null` without an IVV quote), `ret_1_excess_vs_class_median` (`ret_1` minus the median of its asset class: stocks, ETFs or crypto) and `breadth` (the share of the universe whose `|ret_1|` is at least the base gate threshold of its class, `volatility_threshold` or `crypto_volatility_threshold`, without the regime and earnings multipliers). A −3% day when the whole basket falls 3% is beta, not company news, and these features let the shared model see that. With `macro_series_enabled` ([macro series](#flag-macro-series)) the FRED features of the cycle, the same for every symbol, join them too (DAT-22). The universe is the symbols with a known `ret_1`: a symbol whose quote failed or that has no previous close is left out of the rank, the medians and the breadth, and its own cross-sectional features are `null`. **Missing data is masked, not backfilled**: snapshots exist only for days the loop ran (none since the pause of 2026-08-17), so a window shorter than its length or with a gap of more than 5 calendar days between consecutive closes yields `null`; after a resume the 20-day features need about a month of daily cycles. The quote fetched in this phase is cached for the cycle (`CycleQuoteCache`), so `check_price` reuses it: the number of price requests is unchanged, but every symbol now uses the price from the start of the cycle instead of the moment its turn comes (minutes apart on a sequential, throttled run). A symbol whose quote fails gets `null` features and `check_price` asks again, as before; a failed history read leaves its features `null`. The model's vector (`ML_FEATURE_COLUMNS`, read from `ml_feature_store`) does **not** change — the shared model trains from `feature_snapshots` only with `snapshot_training_enabled` — but with `feature_set_filter_enabled` the Slow Loop and `main_backtest.py` filter on the version of the same flag, so switching it on starts a new training sample. It is outside `config_hash`: the prompt, the model's inputs and the thresholds stay the same, and the effect on the weights is recorded by `model_version`. The flag ships **on** (owner decision of 2026-10-25), so new vectors carry version `4` and the training sample of ML-52 starts to accumulate.

<a id="flag-ml-training"></a>

### `ml_settled_purge_enabled`, `ml_direction_classifier_enabled` and `shadow_predictions_enabled`

`ml_settled_purge_enabled` (needs the `settled_at` column that migration `050` adds to the `ml_feature_store` view; without it the purge stays at 12 h) changes which rows train each walk-forward fold (ML-26). Until now a fold dropped the training rows whose label matures within the fixed 12-hour horizon after the validation start (`purged_train_end`). The real label runs until the settling cycle, a day or more and over a weekend 72 h, so a Friday row settled on Monday could still train a fold validated on Saturday. With the flag, `purge_training_indices` in `src/domain/backtest.py` keeps only the rows whose label ends no later than `PURGE_EMBARGO` before the validation start, where the label end is `settled_at` but never earlier than the row time plus 12 h (`label_end_times`; migration `029` backfilled history with the lower bound `settled_at = timestamp`). The kept rows need not be a prefix: a late settlement drops a row while a later one with a mature label stays. The same purge covers the single-split fallback below 50 rows, the per-symbol evaluations and the models trained from `feature_snapshots`, whose label ends at the price snapshot it was taken from. `PURGE_EMBARGO` is `0`: the folds train only on the past, so the leak an embargo guards against (training rows right after the test block) cannot occur, and the purge itself closes the label leak. The step summary and, with `model_scorecard_provenance_enabled`, the scorecard show how many labels overlap the next row (ML-25), the measure this decision rests on. It changes the gate's verdict and so the weights the Fast Loop serves, so it ships **off**; it is outside `config_hash` because its effect on predictions goes only through the weights, which `model_version` records.

`ml_direction_classifier_enabled` (no migration) adds a binary variant of the shared model to the weekly Slow Loop (ML-30). Regressing a noisy 12-hour return under an RMSE gate almost never beats zero, while the product communicates a direction and a confidence; the variant learns P(12h return > +dead band) instead, with the label `1` above the band and `0` below minus the band, and drops the rows inside the band as noise. The band is the protocol's `directional_dead_zone` (`evaluation_protocol.toml`, EXP-06; `0` today, so only a return of exactly zero is dropped), never tuned on the results. It trains on the shared model's sample in raw returns (also with `ml_sigma_target_enabled`), with the same walk-forward folds and purge, and its gate is the out-of-sample Brier against the base rate of each fold's training part (always predicting the share of rises), with the margin and the minimum of out-of-sample points of the regression gate (`summarize_direction_folds` in `src/domain/direction_variant.py`). The step summary gets a "Direction classifier (ML-30)" table: status, rows outside and inside the band, out-of-sample points, Brier and log loss of the classifier next to the base rate, and the verdict. A classifier that passes is written to `data/models/price_predictor_direction.ubj` and answers `MLPredictionPort.predict_proba`; the Slow Loop workflow uploads it to the `model-latest` Release, and the Fast Loop reads it only as a shadow challenger with `shadow_predictions_enabled` (ML-33), so the served (champion) regression model and every prediction stay the same. A failing step only logs. Off by default; outside `config_hash`.

`shadow_predictions_enabled` (**requires migration `075`**) runs champion/challenger for the ML leg (ML-33). The shipped model is refit on every row and never re-validated (`METRIC_NOTE`), so the only honest out-of-sample test is live predictions. With the flag, every prediction that passes the volatility gate also asks the challengers listed in `ml_challengers` (at most two, each a `name`, the `path` of its weights and a `kind`: `return` for a regressor of the 12-hour return, `direction` for a classifier of P(return above the dead band), such as the ML-30 variant) for a shadow forecast from the same feature vector and the same σ the champion got, and writes it to `shadow_predictions` next to the champion's own return (the one behind the email), under the id of the saved prediction. Each row carries the sha256 of its weights file as `model_version`, the same hash the recipe records for the champion. The challengers load their own boosters (`load_challenger` in `src/infrastructure/adapters/xgboost_local.py`) and never touch the champion's: the predicted price, the council input, the prompt, the email and the `prediction_logs` row are the same with the flag on or off. A challenger whose weights file is missing, broken or of the other kind is skipped with a log line; one that cannot forecast a cycle (a feature outside the vector, a σ model without σ) drops out of that cycle with a warning; a failed shadow write (for example before the migration) leaves the prediction saved. The weekly Slow Loop then pairs each challenger with the champion on the same settled predictions of the last 90 days and adds a "Champion/challenger (ML-33)" table to its step summary: pairs, the mean loss of both, the relative improvement, the paired z and the verdict (`ReviewChallengersUseCase`; a failed read, for example before the migration, only logs). A regressor is scored by the squared error of the 12-hour return, like the training gate; a direction classifier by the Brier score of "up beyond the protocol's dead band" (`directional_dead_zone`; moves inside the band are left out), with the champion's return read as a hard call (probability 1 or 0 by its sign, 0.5 at zero). The rule (`should_promote` in `src/domain/promotion.py`) is the walk-forward gate applied to live data and fixed in code before the data exists: at least `MIN_OOS_POINTS = 60` pairs, a mean loss at least `MIN_REL_IMPROVEMENT = 2%` lower and a paired z above `PAIRED_Z_CRIT = 2.0`. It only reports: promoting a challenger (serving its weights) stays the owner's decision. The weights come from the same `model-latest` Release as the champion's: the Slow Loop uploads `price_predictor_direction.ubj` when the ML-30 classifier passed its gate (`ml_direction_classifier_enabled`), and the Fast Loop downloads it before the agent when the Release has it (a missing asset only means no challenger). The flag ships **off**: before the migration the table does not exist. It is outside `config_hash`, like `ml_challengers`, because the prediction is the same.

<a id="flag-interval-coverage"></a>

### `interval_coverage_enabled`: the 80% interval and its coverage

`interval_coverage_enabled` (**requires migration `032`**) stores the 80% interval of each prediction and measures it. The interval itself needs no flag and no migration: every cycle that passes the volatility gate computes it in `predict_node` and the email shows it under the expected move ("80% przedział: −2.1% … +2.4% (n=57)", in the HTML and the plain-text email). `src/domain/conformal.py` holds the method. The calibration window is the settled predictions of the same asset class (STOCK, ETF, CRYPTO) from the last 90 days, read once per cycle with `RepositoryPort.get_settled_moves` (a free Supabase read of columns that already exist, zero paid calls), oldest first, capped at the 250 most recent. Settled predictions, not all price snapshots, because only a cycle past the gate gets an interval: calibrating on the same selection of large-move days keeps quiet days from narrowing it. With trained weights the interval is split conformal around the model's return: ŷ ± the finite-sample quantile `ceil((n+1)(1−α))`-th smallest of the window's `|y − ŷ|`, where `ŷ` is the return the stored target implied; on cold start the predictor is 0 and the bounds are the empirical return quantiles of the window, `floor((n+1)α/2)`-th and `ceil((n+1)(1−α/2))`-th smallest, so the interval can be skewed. α = 0.2 (80%). Adaptive conformal inference (ACI, step γ = 0.005) replays the window in time order: each point gets the interval built from the points before it, and a miss lowers α_t (`α_{t+1} = α_t + γ(α − err_t)`), so a run of misses after a volatility shift widens the interval; when α_t falls below what the window can support, the widest finite interval (the window's extreme) is used. With fewer than 20 points in the class the email says "za mało historii (n/20)" instead of a number. Points settled by this cycle's own `reflect` arrive in the next cycle's window. **The coverage guarantee assumes exchangeability of the window and the new prediction, and markets do not satisfy it**: volatility clusters and regimes change, so the nominal 80% is a target, not a promise; ACI mitigates a shift in the distribution but guarantees nothing. That is why the flag exists: it writes `interval_low` and `interval_high` (prices, the same scale as `predicted_target_price`) on every saved prediction with an available interval, and the Track Record compares the realised coverage of settled intervals with the nominal 80% ("Pokrycie przedziałów 80%: zrealizowane 74% (37/50) vs nominalne 80%"). The flag ships **off**: writing the keys before the migration returns `PGRST204` and the whole prediction write fails, and reading the columns returns `400`. It is outside `config_hash`: the interval describes the uncertainty of the forecast, it does not change the trend, the target or the recommendation.

<a id="flag-gate-delta"></a>

### `gate_delta_enabled`: the move that opened the gate

`gate_delta_enabled` (**requires migration `034`**) stores on every saved prediction the price change that opened the volatility gate, `prediction_logs.gate_delta`: the fraction (`0.031` = +3.1%) against the price snapshot of the previous cycle, the same value the gate checked and the LLM saw in its prompt. A cold start without a previous snapshot writes no value. The offline echo test reads it (`uv run python main_tools.py evaluate --echo`, see [running-locally](running-locally.md)): if the LLM trend mostly repeats the sign of that move, a free rule gives the same call at no cost. The migration backfills the history from `price_snapshots`: for each prediction, the newest snapshot of the same symbol taken **strictly before** the prediction, because the gate compared against the latest snapshot at the start of the cycle and the cycle's own snapshot is written after the prediction. It is an approximation: a snapshot written between the start of the cycle and the prediction (an overlapping manual run) would be taken instead, the stored current price is rounded to 4 decimals, and a prediction without an earlier snapshot, or with a snapshot price of 0, stays `NULL`. The flag ships **off**: writing the key before the migration returns `PGRST204` and the whole prediction write fails. It is outside `config_hash`: the delta is recorded, it does not change the forecast. The echo result is printed only by `evaluate`, never in the email or the weekly recap.

### `experiment_arms_enabled`: the arms on the prediction row

`experiment_arms_enabled` (**requires migration `037`**) stores the arms of the experiments active in the cycle on every saved prediction, `prediction_logs.experiment_arms` (`{"EXP-02": "blind"}`); a cycle without an active experiment writes no value, so the column stays `NULL`. The same arms already reach the v2 decision receipt as the optional key `experiment_arms` with `receipts_enabled`, which needs no migration, so `evaluate --experiment` works before `037`: it prints "kolumna experiment_arms niedostępna — uruchom migrację 037; ramiona z kwitu decyzyjnego" and reads the receipt. <a id="flag-invalidation-level"></a>

### `invalidation_level_enabled`: what would change my mind

`invalidation_level_enabled` (ML-27, **requires migration `074`**) adds "what would change my mind" to every prediction: the prediction prompt asks for an `invalidation` field, `{price, reason}`, the price level whose crossing breaks the thesis. The domain checks it while normalising the answer (`src/domain/invalidation.py`): below the current price for BULLISH, above it for BEARISH, either side for SIDEWAYS, never at the price and at most 15% away; a level on the wrong side or further out is dropped with the quality flag `invalidation_out_of_band`, an unreadable one with `invalidation_invalid`, and a missing one is no quality problem. A valid level is saved in `prediction_logs.invalidation_price`, shown under the reasoning in the email ("Teza upada: …" with the reason) and watched by the Shock Watch, which pushes "Teza NVDA unieważniona" once per prediction when the free price crosses it from the side of the entry before the prediction settles (stamped in `invalidation_alerted_at`). It changes the prediction prompt and adds an output field, so the flag is part of the recipe and ships **off** until EXP-02/03 end; with it off the prompt is byte-identical to its golden file. A model can invent "support levels": the band only rejects the implausible ones, it does not make the level meaningful.

<a id="flag-trend-probabilities"></a>

### `trend_probabilities_enabled`: the full distribution of the trend

`trend_probabilities_enabled` (**requires migration `051`**) asks the main LLM for the full distribution of the three trends instead of one trend and one confidence (ML-29). The prediction prompt gains one schema field, `"probabilities": {"BULLISH": float, "BEARISH": float, "SIDEWAYS": float} (suma 1.0)`, and one instruction line (about 20 more output tokens per prediction, zero new calls). `ProbabilityForecast` in `src/domain/forecast.py` normalizes the answer: keys are case-insensitive, a missing class counts as `0`, a negative probability is clamped to `0`, and the rest is divided by the sum, so percentages (`60/25/15`) work like fractions. The trend is the argmax (a tie resolves to `SIDEWAYS`, then `BULLISH`, then `BEARISH`) and `confidence_score` is the largest probability; the LLM's own `trend_direction` is overridden when it disagrees with its distribution (logged at INFO). When the answer has no usable distribution (not an object, a non-numeric or unknown class, or a zero sum), the trend and the confidence come from the old fields as before, and the column stays `NULL`. Saved predictions store the normalized distribution in `prediction_logs.trend_probabilities` (`{"BULLISH": 0.2, "BEARISH": 0.1, "SIDEWAYS": 0.7}`), which proper scoring rules such as the ranked probability score and the three-class Brier score need; no report reads it yet. With the flag off the rendered prompt is byte-for-byte the prompt from before ML-29. The flag is part of `config_hash`: it changes the prompt and the meaning of `confidence_score` (the largest of three probabilities is at least 1/3), so predictions made with it form their own `recipe_version` segment instead of mixing confidence distributions. The flag ships **off**: writing the key before the migration returns `PGRST204` and the whole prediction write fails.

<a id="flag-settled-at-windows"></a>

### `settled_at_windows_enabled`: windows by settlement time

`settled_at_windows_enabled` (**requires migration `029`**) counts the "closed in the window" reads by the moment a prediction was settled instead of the moment it was made. Migration `029` adds `prediction_logs.settled_at`; a trigger stamps it with the database time when `actual_price_after_12h` first goes from `NULL` to a value, and scoring a settled row again does not move it. Before, both windows filtered on `timestamp`: a Friday prediction settled on Monday was already older than 24 hours, so it missed the email's closed-predictions section, and the Sunday recap still saw it open while a week later it was outside the 7-day window. With the flag on, the email lists the predictions settled since the current cycle started, under the heading "Zamknięte predykcje (rozliczone w tym cyklu)", so a settlement shows up in the digest of the cycle that made it; the preheader count, the lead's hit/miss labels and the push digest scorecard read the same rows. The weekly recap reads the predictions settled in the last 7 days. Rows settled before the migration get an approximate `settled_at`: the first price snapshot of the symbol at the settlement price taken at least an hour after the prediction, because the settling cycle writes its snapshot at the price it settled with. Without such a snapshot the backfill falls back to the prediction's own `timestamp`, which is only a lower bound; those rows have `settled_at = timestamp`. The flag ships **off**: before the migration, filtering on the column returns `400`, so the email would lose the section and the recap would be skipped. With the flag off, both reads, the heading and the 24-hour window are exactly as before.

<a id="flag-shock-watch"></a>

### `shock_alerts_enabled`: the Shock Watch

`shock_alerts_enabled` (migration `021`) adds a **fourth entry point**, [`main_watch.py`](../main_watch.py), designed for an hourly cron that runs **24/7 rather than only during NYSE hours** — BTC and ETH trade around the clock. **Status: that cron runs** (resumed on 2026-10-23 after a pause from 2026-10-16); it does not depend on the Fast Loop. Since ALR-02 the watch no longer needs Fast Loop snapshots to see a move: it first reads the **day's change from the same free quote** (`DailyChangePort`: Finnhub `dp`, the move since the previous close, for stocks; CoinGecko's 24-hour change for crypto) and falls back to the Fast Loop snapshot only when that reading is missing, fails, or is not from the run's UTC day. A reading from another UTC day never alerts — on Saturday Finnhub still reports Friday's `dp` with Friday's timestamp `t`, and alerting on it would repeat Friday's alert under a new `alert_date`. Crypto has one more guard: CoinGecko's 24-hour change still contains a move for a day after it happened, so a crypto symbol whose previous alert (`shock_alerts.created_at`) is less than 24 hours old gets no alert from the daily change — otherwise a move alerted at 22:00 UTC would alert again after midnight under the next `alert_date`; stocks keep the UTC-day rule. A fresh reading decides the symbol on its own (no snapshot read, no price fetch), so one run sends at most one alert per symbol, and the push says which reference it used ("od poprzedniego zamknięcia", "w ciągu ostatnich 24 h" or "od ostatniego snapshotu ceny"). The workflow guard (`tests/test_shock_watch_env_wiring.py`) allows the watch cron without the Fast Loop cron as long as `main_watch.py` wires that daily-change source. It answers the one thing a once-daily digest cannot: an -8% move on BTC at 14:00 should not wait until tomorrow morning. Cost is **zero paid API calls** — free price sources (Finnhub / CoinGecko), a Supabase read, and free push channels; no LLM, no Alpha Vantage, no embeddings. Two hard contracts protect the rest of the system. The watch **never calls `save_price_snapshot`**: overwriting the snapshot hourly would make the Fast Loop measure its delta against an hour-old price instead of a cycle-old one, quietly shutting the volatility gate. And a **one-alert-per-symbol-per-day debounce** — enforced both by the domain predicate and by `UNIQUE(symbol, alert_date)` — keeps a chaotic market from training you to ignore the channel. Delivery is **at-least-once** (ALR-14): the push goes out first and the `shock_alerts` row is written after a successful send, so a database failure never swallows an alert. The price is that two overlapping runs, or a failed write, can push the same alert twice; `UNIQUE` rejects the second row, not the second push, and the failed write is logged. The comment in migration `021` ("the watch tries to insert the row before sending") describes the opposite order; the migration is applied and is not edited, so this paragraph and `main_watch.py` are the contract. On the snapshot fallback, a price snapshot older than 30 hours suppresses the alert entirely, because a stale reference point manufactures false alarms. The age is checked **before** the current price is fetched, and a run in which no symbol had a fresh daily change and every snapshot is stale logs a `Shock watch ślepy` WARNING instead of reporting a healthy-looking "0 alerts".

<a id="flag-alpha-fusion"></a>

### `alpha_fusion_enabled`: the alpha sources reach the prediction

`alpha_fusion_enabled` (migration `022`) closes the repo's largest wasted investment. Five alpha sources were fetched, classified against domain thresholds, and then rendered **only into a table**: insiders could be buying by the million and neither the LLM prediction nor the seven XGBoost features would know. Fusion is a weighted sum of the *existing* domain classifications, renormalised over whichever sources are actually present, so a symbol with one available source is not silently penalised. A social snapshot **without sentiment** counts as absent, not as present-neutral: Reddit search returns mention counts only, so that vote could never carry a direction and would merely drag the other sources towards zero with its 0.20 weight. The Reddit adapter also returns no snapshot when its week search fills the whole 100-post page — the count is then a ceiling, and the understated baseline would report a false `SURGING`. The score reaches both the LLM prompt — **with its per-source breakdown**, so the composite stays auditable rather than becoming a black box — and `ml_feature_store`, where it is a **candidate** feature, not a model feature: it is not in `ML_FEATURE_COLUMNS` ([`src/application/ml_features.py`](../src/application/ml_features.py)), so the XGBoost model neither trains nor predicts on it. Enrichment had to move **before** the graph to make that possible; it previously ran after, which is precisely why the signals never reached anything. The paid-call count is unchanged: `enrich` already ran once per symbol, just later. In the view the column is `COALESCE(alpha_fusion_score, 0.0)` so that, once the score is promoted, `dropna` cannot cut the historical rows out of training (a train/serve skew the migration test freezes). Whether the hand-picked weights are signal or noise is not settled yet: the walk-forward "beat the baseline" gate only judges the model's own features, so promoting the score needs an A/B comparison first (EXP-19), not intuition — which is why the flag is off by default in code. Production `config.toml` turns it on.

<a id="flag-attestation"></a>

### `attestation_enabled`: a checkable track record

`attestation_enabled` (**requires migrations `024` and `043`**) is built to make the track record **cryptographically checkable**. At prediction time a SHA-256 commitment over the canonicalised prediction plus a random salt is written to `prediction_logs` and the **hash alone** is appended to a public JSONL file — until the salt is revealed the hash discloses nothing. The hash is published only after the prediction row is saved (WIA-01), so a failed write never leaves a public hash whose salt is not in the database; a second save of the same symbol in the same UTC hour (a LangGraph retry or a re-run, which the `(symbol, timestamp_hour)` upsert overwrites) reuses that row's salt when the prediction is the same, so it gets the same hash and nothing is revealed. When the new prediction differs, the commitment it overwrites is revealed at once: its `commitment`, `salt` and verbatim `payload`, read from the row before the upsert, with `"status": "superseded"`, because after the upsert the database no longer holds them and the published hash could never be revealed; the new prediction gets a fresh salt. The superseded reveal goes out only after the new row is saved (a failed write leaves the old row in place for the sweep), and when the stored hash cannot be read the salt is reused as before (WIA-01). The row also keeps the canonical plaintext exactly as it was hashed, in `commitment_payload` (`TEXT`, migration `043`, WIA-70). Once the prediction settles, a **sweep** reveals every matured commitment (salt and plaintext), whatever its age and whether or not its symbol is still on the watchlist (WIA-03; the read used to stop at 30 days, so older commitments stayed hidden): a row with `commitment_payload` publishes it verbatim as `payload`, so anyone checks SHA-256(`payload` + `salt`) byte for byte without rebuilding it from columns whose types PostgREST converts (a `NUMERIC` comes back as a float); a row without it (written before `043`) is revealed from its columns as before. Before each Fast Loop cycle with the flag on, `attestation_columns_available()` checks that the three commitment columns exist; without them the cycle runs without attestation and logs a `WARNING`, instead of losing every prediction write to `PGRST204`. Once the prediction settles, a **sweep** reveals every matured commitment (salt and plaintext), and `revealed_at` is stamped only once the reveal is *durable* (WIA-15): the sweep after the report only appends to `reveals.jsonl`, and the next Fast Loop run, before its first symbol, stamps exactly the rows whose `commitment_hash` is in the `reveals.jsonl` it checked out of `attestation-log`, i.e. the lines that survived the previous run's push. A cancelled job or a failed push leaves the rows unstamped, so the next sweep reveals them again, and a row whose reveal is already in the ledger is never appended twice; re-runs are idempotent. A miss can never be marked-revealed-but-never-published. The sweep is deliberate rather than a reveal-on-settle hook: predictions for symbols later removed from `config.toml` would otherwise never be revealed, and to a sceptic that looks exactly like hiding losses. **Be honest about what this proves:** git commit dates are forgeable. The claim is *tamper-evidence under branch protection*, not an unforgeable timestamp. **One Merkle root per cycle (WIA-60).** The commitments of a cycle are the leaves of one Merkle tree built as in RFC 9162 §2.1 (`tree: "rfc9162-sha256"`: leaf = SHA-256(`0x00` ‖ the 32 bytes of the commitment), node = SHA-256(`0x01` ‖ left ‖ right), split at the largest power of two below the size; the empty tree hashes nothing), sorted and without duplicates so the same set of predictions gives the same root whatever order the parallel symbols saved them in. After the symbol pass, and also when the pass raised, the Fast Loop appends **one** line per cycle to `commitments.jsonl`: `cycle_id` (`<run id>.<attempt>.<start UTC>`), `committed_at`, `root`, `n_leaves`, `leaves`, `schema_version` (the canonicalisation of the leaves, still `2`) and `tree`, also for a cycle with no prediction. The root is one event to anchor, and `n_leaves` closes the set: no prediction can be added or a loss left out after the line is pushed. The leaves are the same salted hashes the single lines carried, so listing them reveals nothing. A reveal of a leaf carries `inclusion` (`cycle_id`, `root`, `leaf_index`, `tree_size` and the audit `proof`), read from the checked-out ledger, so it can be checked against the root alone; a reveal whose commitment the ledger does not know (the job was cancelled before its cycle's root, or that push failed) carries `"status": "incomplete_cycle"` instead of pretending to be proven. Canonicalisation is frozen by golden tests and carries a `schema_version` from the first commit, because a canonicalisation bug breaks verification of history with no way to repair it retroactively. New commitments use schema `2`. Besides the symbol, trend and prices it binds what the public scorecard shows most (WIA-41): the declared confidence, the horizon (12 hours), the council's `final_recommendation` and `consensus_strength` (`null` without a council), the `recipe_version` and the hash of the evaluation protocol, so none of them can be changed in the database after the fact; fractions are hashed as four-decimal strings, never as floats. Prices are hashed as the four-decimal text of their `DECIMAL(14,4)` columns (WIA-02), rounded half away from zero as Postgres rounds `NUMERIC` (`Money.for_storage()`), and the prediction row stores the same rounded prices, so a commitment never depends on precision the database cannot keep; schema `1` (prices in full Python precision) stays frozen for verifying older commitments. Zero cost — local hashing. **Status: built and wired, not switched on.** The publisher appends to JSONL files, and the ledger's durable home is the orphan branch `attestation-log` (WIA-14). The Fast Loop checks that branch out into the directory of `attestation_commitments_path` and `attestation_reveals_path` before the agent runs, so the append continues the history instead of starting an empty file on a fresh runner. A separate job, `publish-attestation-ledger`, is the only one with `contents: write` and holds no API key: it commits the new lines with `[skip ci]`, runs `git pull --rebase` with up to five retries (two runs that appended to the same file merge by `merge=union`, so no line is lost) and pushes to `attestation-log` and nowhere else, never to `main`. The agent's step ends with exit 1 when every symbol failed, but the commitments of predictions saved before that are already in the database, so the job runs after a failed agent job too. A flag on without the branch fails the Fast Loop in its first step, before any paid call. The pages deploy carries only the scorecard's directory and replaces the whole site, so it cannot keep an append-only ledger. Guards in [`tests/test_workflow_env_wiring.py`](../tests/test_workflow_env_wiring.py) check the wiring (checkout before the agent, the one write-access job without secrets, pushes only to `attestation-log`, retry) and run the push step against a local remote. `config.toml` ships the flag **off** until the owner creates and protects the branch (step 9 of the [resume checklist](resume-checklist.md)); a second guard fails the flag if it is switched on without a `git add` of both ledger files and a `git push` in the agent's job or a job that waits for it (`needs`).

**Where the verifiable track record starts (WIA-27).** The predictions of 2026-07-10 to 2026-08-17 cannot be attested: nothing about them was public before their outcome was known, so a hash computed today would prove nothing about when they were made. The track record is verifiable only from the first push of the commitment ledger onwards. Rows written before that push are never published as attested: they stay in the database and in the email's Track Record as unattested history, and no claim of tamper-evidence covers them.

<a id="flag-attestation-rekor"></a>

### `attestation_rekor_enabled`: an independent clock for the cycle roots

The git ledger proves tamper-evidence under branch protection, not time: commit dates are forgeable, and an OpenTimestamps stamp (WIA-76) confirms time only hours later. WIA-73 (decided 2026-10-24) anchors each cycle root in Sigstore Rekor instead: an append-only public log whose `integratedTime` is set by the log at the moment of the write, signed keyless with the job's GitHub Actions OIDC identity, so the entry is bound to the public workflow run and not to a key someone keeps. Built after the durable ledger (WIA-14/15) and the per-cycle Merkle root (WIA-60), because one root per cycle is one entry to anchor. The client is plain REST plus `cryptography`, which was already installed through `supabase-auth[crypto]`, rather than the `sigstore` package and its own dependency tree; verification of the certificate chain to the Fulcio root and of Rekor's signed checkpoint is left to the standard Sigstore tooling, so `verify-attestation` stays offline. Off by default: Rekor entries are public forever, the service is external, and `id-token: write` on the job that holds the API keys is a security decision the owner takes when switching it on.

<a id="flag-portfolio"></a>

### `portfolio_positions_enabled`, the position currency and the risk flags

`portfolio_positions_enabled` (migration `023`) replaces a fiction. `stress_test` and `portfolio_pnl` computed on **equal weights**: someone holding 40% in NVDA received a VaR calculated as though they held 2.3% of each of 43 tickers. A `positions` table now feeds a `Portfolio` aggregate with real weights (renormalised over the symbols that actually have a current price), unrealised P/L per position, and the exposure of each stock sector from `sectors` (a sector, not a measured correlation cluster) — your three largest positions in one sector are 61% of capital. Until `sectors` filled `peer_groups`, the groups were empty, so neither the warning nor the sizing exposure ever fired. Amounts in PLN come from NBP rates passed to the renderer as **values** (`ReportContext.portfolio_fx`, see `fx_rates_cache_enabled` below), never by injecting a port into the renderer. A **STALE badge is a requirement, not decoration**: the positions table is maintained by hand, and a stale portfolio produces a *false* P/L, which is worse than no section at all. A Supabase error degrades to no section rather than to wrong numbers. A position the cycle could not price (for example a ticker in `symbols_unsupported_price` such as `XDWD.DE`) is never dropped silently: the section lists it under the table as "Bez wyceny w tym cyklu: XDWD.DE, IUSN.DE (≈ X% kosztu)", with its share of the total **cost** basis (`Portfolio.unpriced_symbols` / `unpriced_cost_share`), and the totals are labelled "bez pozycji niewycenionych", because the weights of the priced positions are renormalised without it. A position in a symbol outside the watchlist (`symbols` + `crypto_symbols`) and outside `symbols_unsupported_price` gets a price from the free quote endpoint only (`build_market_port`: Finnhub `/quote` or CoinGecko), fetched sequentially while the report is built and passed as `ReportContext.held_prices`. It never writes a `price_snapshots` row, never enters the graph and never triggers an LLM, Alpha Vantage or embedding call; adding the symbol to `symbols` instead would pay for a full analysis on every move past the volatility gate. A failed quote leaves the position unpriced. Phase 2 is now in: `suggest_band` knows the existing exposure. Suggesting a "full 4-5% position" to someone already holding 40% of their capital in that symbol was advice computed on an empty portfolio. Both `current_weight` and the exposure of the symbol's **sector** can only ever *narrow* the band — three positions in one sector are one position wearing three hats. Monotonicity is the contract: an empty portfolio is absence of information, never a buy signal, so exposure never upgrades a weak signal. Both arguments default to `None`, preserving the pre-phase-2 behaviour exactly. Portfolio risk is the third input. With `portfolio_var_enabled` on and real positions loaded, `main_agent` measures the positions actually held (`PortfolioRiskUseCase.position_risk`): the free `price_snapshots` history of the held symbols only, weighted by each position's market value at its latest snapshot and renormalised over the held symbols that have history. `suggest_band` applies it after the exposure, and each signal is its own step: a 1-day VaR95 of at least 3% (`VAR_TIGHTEN_THRESHOLD`, from 60 returns as in the radar) lowers the band one step, a current drawdown of the portfolio at least 15% below its peak in the 90-day window (`DEEP_DRAWDOWN_THRESHOLD`) forces the starter band, and held hedges that do not move against the rest of the portfolio (hedge effectiveness below 0.3, from 20 paired returns) lower it one step. A hedge is a held instrument typed `INVERSE_EQUITY` or `VOLATILITY` in `risk_symbol_types` (`EQUITY_HEDGE_TYPES`, `src/domain/hedge.py`); a held GLD, EPOL or TBT is an investment, not a hedge of the stock book, and never lowers the band. Like exposure, risk can only narrow the band. With the flag off or without positions the band is unchanged; the radar's VaR, computed on equal watchlist weights, never sizes anything. The global hit rate stays the track-record input. The flag stays outside `config_hash`: the band is rendered after the prediction and changes no stored forecast.

**Position currency and purchase date (migration `035`, no flag since PORT-23).** Each position carries its currency and its real purchase date. Migration `035` adds `positions.currency` (ISO 4217, `NOT NULL DEFAULT 'USD'`, three capital letters enforced by a check) and `positions.purchase_date` (`DATE`, `NULL` = unknown). It backfills the currency of the rows that exist when the column is added from the ticker suffix: `.DE`, `.AS`, `.PA`, `.MI`, `.MC` → `EUR`, `.L` → `GBP`, anything else → `USD`. London quotes are often in pence (GBX) and some `.L` ETFs trade in USD; the migration converts nothing, so correct such a row with the import below. A rerun of the migration does not overwrite a currency set later. Existing rows keep `purchase_date = NULL`: `as_of` is the date the table was last updated, not a purchase date, and the adapter never uses it as one. `SupabasePositionsAdapter` always reads both columns (a row without them reads as USD with an unknown date) and `uv run python main_tools.py import-positions --csv <file> --apply` always writes them (see [running-locally](running-locally.md)); the import returns `PGRST204` and leaves the old portfolio in place when the migration has not been applied. Production has had the migration and the switch on since 2026-10-23, so the switch (`positions_currency_enabled`) and the old `as_of` mapping were removed. The currency changes the report, not the forecast.

The 💼 section's P/L in złoty (PORT-11) values the cost at the NBP rate of the purchase date and the current value at the current rate, then splits the result into the instrument and the currency effect: `P/L zł` = quantity × current price × current rate − quantity × purchase price × purchase-date rate, of which `w tym kurs` = quantity × purchase price × (current rate − purchase-date rate), and the instrument part = quantity × (current price − purchase price) × current rate; the two add up to the P/L. Buying 10 shares at 100 USD with USD/PLN at 4,00 and holding them at 100 USD with USD/PLN at 4,40 is +400 zł, all of it currency. This is an economic result at the NBP rate of the purchase date, not a tax base: Polish income tax (PIT, art. 11a) uses the NBP rate of the last business day before the transaction. Each position uses the rates of its own currency (`Portfolio.pln_pnl`, `src/domain/portfolio.py`); a PLN position has no currency effect. With `nbp_enabled`, `main_agent` collects the rates while the report is built (`collect_pln_rates`, `src/application/portfolio_fx.py`): the current rate of each foreign currency for today in Warsaw and the rate of each (currency, purchase date) pair, from the NBP table A endpoint `/api/exchangerates/rates/a/{code}/{date}/`. A day without a table (weekend, holiday, before the table is published around noon) returns 404 and the adapter steps back day by day to the previous business day, at most 10 days (`MAX_LOOKBACK_DAYS`); any other error gives no rate and stops further NBP calls for the rest of the cycle, because with NBP down every call is a timeout with retries and dozens of purchase dates would exceed the job's time limit. These calls are free (NBP needs no key), outside the graph and the volatility gate. A position without a purchase date (every row that had no `purchase_date` when migration `035` ran, because `as_of` is not a purchase date) says `kurs z dnia zakupu nieznany` in the `w tym kurs` cell and `—` in `P/L zł`, instead of a P/L computed with the current rate on both sides, which would hide the currency effect; a missing NBP rate for the purchase date says `brak kursu NBP z dnia zakupu`, a missing current rate `brak kursu XXX/PLN`. The totals line names the current rates it used (`W PLN (kursy NBP: EUR 4,2710 · USD 3,6820)`), sums the value of every position with a current rate and the P/L and its currency part of the complete positions only, and lists the others (`bez P/L w zł: AMD, NVDA`). When the rate collection fails, the section falls back to the current USD/PLN and EUR/PLN of Risk Watch without purchase-date rates. Position amounts are shown in the position's currency; when the priced positions hold different currencies the native totals line says so instead of adding dollars to euros. The whole portfolio is measured in one currency, złoty, whenever rates are known: the weights in the 💼 section and in the lead (`AAPL (50% portfela)`), the sector exposure of the concentration warning and of the sizing band, the symbol weight the sizing band sees, the unpriced positions' share of the cost and the change since the previous email all use `Portfolio.pln_prices` (price × current NBP rate of the position's currency) instead of adding dollars to euros; `main_agent` passes the same rates to `PortfolioRiskUseCase.position_risk`, so the VaR, drawdown and hedge weights of the sizing band are in złoty too. A position whose currency has no rate (or a symbol held in two currencies) drops out of all of them and the section says so under the table: `Bez kursu NBP: VUSA.L — poza wagami i sumami w zł`; it is never treated as USD. Returns stay in the quote currency, so the currency move is in the P/L split but not in the VaR. Without any rate (`nbp_enabled` off) the old native amounts remain, which is only right for a single-currency portfolio. GBX risk: migration `035` maps `.L` tickers to `GBP`, but London quotes are often in pence; if the price source returns pence for a position stored as `GBP`, every złoty amount and weight of that position is 100 times too large, so check `.L` positions and set their currency explicitly with the import. Other subscribers (`subscriptions_enabled`) never receive the rates, like the rest of the portfolio. `fx_rates_cache_enabled` (**requires migration `036`**) adds a read-through cache of past-day rates in the `fx_rates` table (key `currency`, `on_date`; `effective_date` is the NBP table the rate came from), so a purchase-date rate is fetched from NBP once. Only days before today in Warsaw are cached, because today's rate before publication is yesterday's. A cache read or write error is logged and the rate comes straight from NBP. The flag ships **off**: before the migration the table does not exist. Both flags are outside `config_hash`.

`portfolio_var_enabled`, `stress_test_enabled` and `hedge_effectiveness_enabled` add VaR/CVaR, a beta-based stress test and hedge effectiveness to the 🎯 Portfolio Radar and Risk Watch sections, all computed from free `price_snapshots` history (zero paid calls). With real positions, `portfolio_var_enabled` also lets the risk of the held portfolio narrow the sizing band (see above). Series of different symbols are paired by **UTC day** (`align_by_utc_day`, `src/domain/correlation.py`): snapshots written in one cycle differ by seconds, so the exact-timestamp intersection used to be empty and the radar, VaR, stress test and hedges silently disappeared. When a day has several snapshots the latest one wins, and only days present in every series are kept. An hourly bucket would split one cycle across two hours. Minimum samples (`src/domain/risk_sample.py`) keep a handful of points from posing as risk statistics: VaR/CVaR needs `MIN_VAR_OBSERVATIONS = 60` daily returns, and correlations, clusters and the stress-test betas need `MIN_PAIRED_RETURNS = 20` paired returns. Below that the statistic is not computed and the section says "za mało historii (n/60)" (or `n/20`) in both the HTML and the plain-text email instead of going blank or printing a VaR that is just the worst day of the sample. The radar reads a 90-day window (`PRICE_HISTORY_DAYS`), roughly 63 sessions, so VaR can appear at all; `get_price_history` reads it page by page, because PostgREST silently caps a SELECT at about 1000 rows; until the loop has collected that history (or it is backfilled) the section honestly reports the gap.

<a id="flag-public-scorecard"></a>

### `public_scorecard_enabled`: the one artefact for a stranger

`public_scorecard_enabled` renders the one artefact that can earn a stranger's trust: a landing page carrying **aggregates only** — number of settled predictions, the directional hit rate, Brier score, ECE, the reliability curve as a div-sparkline, and the equity curve. The numbers are computed so that they mean something:

- **One definition of hit rate.** The headline is the *directional* hit rate from `directional_hit_rate` (`src/domain/equity_curve.py`): SIDEWAYS calls place no bet and stay out of the denominator; their count gets its own card. With no directional calls the card shows "—" instead of borrowing the equity curve's win rate.
- **Uncertainty.** Next to the rate: a 95% Wilson interval (`src/domain/statistics.py`) computed on the **effective sample size** `n_eff = n / (1 + (m̄ − 1)·ICC)` (`src/domain/significance.py`). Predictions of one cycle (UTC day of `prediction_logs.timestamp`) move together, so 412 calls can be worth ~61 independent ones; the page prints "n=412, n_eff≈61". With at least 20 cycles a cycle-level block bootstrap adds a second interval; below that the page says the bootstrap was skipped, and below `n_eff = 5` it says the interval is very wide.
- **Naive baselines.** "Always BULLISH / BEARISH / SIDEWAYS" hit rates computed on the **same** directional predictions (after the volatility gate, not on every market day) — `naive_baselines` in `src/domain/track_record.py`.
- **Significance.** An exact one-sided binomial test (normal approximation above n = 1000) against the stronger of the two directional baselines, run on `n_eff`, with a Polish verdict such as "nieodróżnialne od rzutu monetą (p=0.41, n=37, n_eff≈12)". `benjamini_hochberg` (FDR, q = 0.10) corrects tables of many comparisons: the `evaluate --by` segments and the email's council ranking (WIA-22, see [report-email](report-email.md)).
- **Required sample (DOC-16).** The methodology section says how many settled directional predictions, in `n_eff`, it takes to tell a 55% hit rate from a coin flip with a one-sided test at α = 0.05 and 80% power: ~617 (`required_n` in `src/domain/significance.py`, normal approximation). With a window it adds the window's `n_eff` and, at the window's pace, the date the sample would suffice (`sample_reached_on`); a window with no directional prediction says `brak napływu danych` instead of a date, which is what a paused Fast Loop gets.
- **Probability scores.** Brier score, the climatological Brier (always forecasting the base rate), the Brier Skill Score, log loss and the Murphy decomposition (reliability, resolution, uncertainty) lead the calibration block (`probability_scores` in `src/domain/calibration_curve.py`). ECE stays as a secondary number, because a constant "55%" forecast at a 55% hit rate has ECE = 0 and no skill at all. Each reliability bucket shows its `n`. The curve, ECE and scores cover directional predictions only; the private Track Record lists SIDEWAYS calls separately with their `n` and Brier score (WIA-39), since that sample is small. ECE itself is computed on 10 equal-count buckets (`reliability_curve(..., strategy="equal_mass")`, quantile edges, WIA-58), because confidences cluster in 0.6–0.85 and 10 equal-width buckets leave two or three non-empty; the diagram keeps the equal-width buckets. Next to it the page prints a 95% interval from a bootstrap that resamples whole cycles (UTC days, at least 20, otherwise it says the bootstrap was skipped), `n` and `n_eff`, and the bias-corrected ECE (`debiased_ece`: the observed ECE minus the mean ECE of 200 seeded Bernoulli simulations of perfectly calibrated outcomes for the same confidences; a small sample of a perfectly calibrated forecast still has an ECE of several points), e.g. "ECE = 7.0% [3.0%; 12.0%], n=412, n_eff≈61 (kubełki równoliczne; po korekcie obciążenia 5.0%)".
- **Equity curve.** One point per cycle, equal weight per prediction within a cycle, SIDEWAYS held as cash (`paper_portfolio_curve`), net of the one-way trading cost charged on each change of a symbol's position (`src/domain/trading_costs.py`); the heading says "paper-PnL (koszt 10 bps)" with the decimal point, and the assumptions name the crypto cost. Next to it the page compares the agent with two buy&hold benchmarks that pay the same cost (WIA-21, `src/domain/benchmark.py`): the **basket** (every predicted symbol held long in the same windows, equal weight, entry cost only) and **IVV** (held long in the prediction windows, one point per agent cycle), as "agent +1.2% · koszyk +3.4% · S&P 500 +2.1%", plus the excess return over the basket and the **market-relative hit rate**: a directional call is a hit when its sign matches the sign of the symbol's return minus IVV's return in the same window, so an always-BULLISH agent in a bull market no longer scores ~55% for free; predictions of IVV itself stay in both curves but out of this hit rate, since their excess return over IVV is zero by definition. The sparkline gets a second row for the basket. The basket is an aggregate and the page names the index "S&P 500" instead of its ticker, so no watchlist symbol reaches the page — IVV is on the watchlist, so the invariant holds without exception; the private email says "IVV". **Timestamp convention:** IVV is read from the free `price_snapshots` (no paid call) and its window uses the same cycle snapshots as the prediction: the start is the IVV snapshot of the same cycle (same UTC day, the one nearest to the prediction's `timestamp`, since IVV may be written minutes before or after the symbol), the end is the first IVV snapshot at least `reflection_min_age_hours` later, which is the cycle in which `reflect_node` settles the prediction. The 05:30 UTC snapshot is the previous session's close, so both sides measure close(D−1) → close(D); calendar trading dates are never used. A missing IVV snapshot in a prediction's cycle drops that prediction from the market-relative hit rate; a cycle with no IVV window at all makes the IVV curve "brak danych benchmarku" rather than a curve with a hole. If IVV misses the settlement cycle, its window runs to the next IVV snapshot. The read covers `track_record_days + 1` days, because the start snapshot of the oldest cycle can be written just before the prediction window's cutoff. The old curve compounded parallel trades serially on 100% of capital; the page marks the methodology change of 2026-10-18.
- **Survivorship.** The methodology section says that the watchlist was hand-picked (2026-06) with knowledge of the companies' earlier rallies, so a long bias on it is not skill, and points at the naive "always up" baseline on the same predictions. The sentence names no symbol, so the anti-PII invariant holds.
- **Window.** The page states its window and generation date — "Okno: ostatnie 30 dni (2026-09-18 – 2026-10-18)" — from `track_record_days`.

<a id="flag-batch-diagnosis"></a>

### `batch_diagnosis_enabled`: one diagnosis call a week instead of one per miss

`reflect` pays for a mistake diagnosis on every wrong prediction past the volatility gate, and the diagnosis backfill (WIA-53) pays once more for each miss the gate skipped. EXP-17 is the cheapest form of self-correction: `reflect` leaves a placeholder and the Slow Loop diagnoses the whole week in one call, under the weekly ceiling `slow_loop_max_paid_llm_calls_per_week` (FIN-30), so the cost no longer grows with the number of misses. The price is latency: a lesson reaches the prediction prompt up to a week later, which changes what the prompt sees, so the flag is part of the recipe (`config_hash`) and waits until EXP-02/03 end (after 2027-01-29). The batch prompt lives in its own module, not in `prompts.py`, so building it did not change `prompt_sha256` of the running recipe.

<a id="flag-diagnosis-judge"></a>

### `diagnosis_judge_enabled`: a rubric judge for the lessons

The diagnoses of wrong predictions come back into later prompts as lessons (reflection and the RAG analogues), so a fluent but empty diagnosis would poison them without anyone noticing. EXP-10 grades a random weekly sample of at most 10 with three yes/no criteria — a factor present in the saved news or prices, a falsifiable claim, not a platitude — and keeps a diagnosis below 2 of 3 out of the lessons and the RAG analogues, while its text stays in `rejected_diagnosis` (migration `078`), so a rejection can be undone. It runs in the Slow Loop's weekly LLM ceiling (FIN-30), last in the order. An LLM judging an LLM shares its bias, so the score means something only after the owner has compared it with 20 of their own grades; until then, and until EXP-02/03 end, the flag stays off.

<a id="flag-weekly-recap"></a>

### `weekly_recap_enabled`: the Sunday recap

`weekly_recap_enabled` costs exactly **one LLM call per week** — not per symbol, not per cycle, enforced by a test — and, like the diagnosis backfill, it runs outside the volatility gate under the Slow Loop's weekly ceiling `slow_loop_max_paid_llm_calls_per_week` (FIN-30), where it has the first share. The Slow Loop already ran every Sunday and sent the user nothing. It now composes a story: prediction of the week (the directional hit closest to its price target; a week with no directional hit shows the miss closest to target instead, titled "Najbliżej celu (kierunek chybiony)"), miss of the week (the mirror rule: the directional miss farthest from its target; a week with no directional miss shows the hit farthest from target instead, titled "Najdalej od celu (kierunek trafiony)") with the lesson `reflect_node` drew from it, the council's **vindicated dissenter** ("Soros was right while everyone said BUY"), the Brier score of the week's confidences next to the climatological Brier and the Brier Skill Score (WIA-36, the same `probability_scores` as the Track Record: a constant "55%" at a 55% hit rate has ECE = 0 but BSS = 0), and the week-over-week ECE delta as a secondary number. Each hero shows its direction verdict (✅ / ❌) and its price-target error (`1 − accuracy_score`, as a share of the entry price); `accuracy_score` measures closeness to the target, not directional accuracy, so neither the email nor the narrative prompt calls it "trafność". The direction verdict, which also drives hero selection and the recap's ECE, is the `is_trend_correct` that `reflect_node` stored (with the ±2.5% SIDEWAYS band for crypto), the same value the daily email uses; only a row without it is re-scored from its prices. That re-scoring and the "vindicated dissenter" check (did the market go UP, DOWN or stay FLAT) use the asset-class band `reflect_node` uses: ±2.5% for symbols listed in `crypto_symbols`, ±0.5% for everything else, so a +1.5% day on BTC counts as FLAT and vindicates a HOLD dissenter. A hard sample-size rule lives in the domain: **below five closed predictions no recap is built and no email goes out**, because a thin week would otherwise manufacture drama out of noise. If the LLM call fails the deterministic recap is still sent, without the narrative. A failure to *build* the LLM adapter (for example a missing SDK or `ANTHROPIC_API_KEY`) falls back the same way: the step gets an adapter that fails on every call, so the recap still goes out without the narrative and the calibration judge still stores its arithmetic. Insight text reaches the prompt through `fence_untrusted`, since `correction_insights` derives indirectly from news headlines.

<a id="flag-owner-bot"></a>

### `telegram_bot_enabled` and `symbol_mutes_enabled`: the owner's bot

Every channel was one-way: to ask "why NVDA?" between emails, the owner had to wait for the next email or read Supabase. The bot (MAIL-48, decision 2026-10-24: the push channel is Telegram and the owner creates the bot) turns the digest into something to come back to without a server of its own: a GitHub Actions cron polls `getUpdates` every 15 minutes, which also bounds the latency at roughly a quarter of an hour plus the cron's usual delay. A webhook would need a public endpoint (a Supabase Edge Function, a new runtime), so polling was chosen. The chat id allowlist is the security boundary: without it anyone who finds the bot would read the portfolio. Commands are free reads, never an LLM call.

The mutes (MAIL-45, decision 2026-10-23, option b) answer "I just sold it, stop analysing it" without a deploy, but the database holds **only** mutes: symbols are added solely through `config.toml`, so the watchlist keeps one source of truth and the track-record universe still follows git. A mute decides whether a symbol enters the graph, not how it is predicted, so both flags sit outside `config_hash`. The muted symbol keeps its price snapshot, so the first cycle after the mute measures its move from a fresh reference instead of from the day of the mute.
