# How it works

The pipeline, the data it runs on, and every signal it emits. Start at [the README](../README.md) for what this project is.

## How it works

```
Finnhub (US prices) ──► check_price ──► reflect ──► fetch_fundamentals ──► [Δ ≥ threshold?]
                         (+ snapshot     (Self-        (AlphaVantage           ├── no ──► ignore ──┐
                          to DB)          Reflection)   OVERVIEW+EARNINGS       │                   │
                                                        slow loop only)         └── yes ──► sentiment │
                                                                                            → news    │
                                                                                            → predict │
                                                                                            → council │  ← 7 investor personas
                                                                                            → save ───┤
                                                                                                      │
                          ┌───────────────────────────────────────────────────────────────────────────┘
                          ▼
                 accuracy_stats + resolved_predictions
                          ▼
                 HTML report (inline charts) ──► Resend.com email
```

1. **Fetch price + snapshot** — `FinnhubAdapter` pulls the current quote for each US ticker. `check_price_node` saves a **price snapshot in every cycle** (`price_snapshots` table) so the next cycle always has a reference point — this breaks the cold-start deadlock. Free tier is US-only; dotted tickers (`CSPX.L`, `BAS.DE`) get a 403 and are handled gracefully.
2. **Self-Reflection (runs every cycle, before the volatility gate)** — `reflect_node` reads the last unverified prediction. Rows saved before the LLM answer was normalised (step 6) may hold a lower-case, `NULL` or invalid `predicted_trend`; they are read with the same rule (`normalize_trend` in `src/domain/prediction.py`), so one old row cannot block the oldest-first queue. It computes two independent domain metrics and persists both: `accuracy_score` (how close the price landed to the numeric target — feeds XGBoost training) and `is_trend_correct` (whether the directional call matched reality — feeds the report's hit-rate). If the prediction was directionally wrong, the LLM diagnoses why ("I ignored hawkish Fed signals"). The diagnosis prompt carries that prediction's own inputs read back from `prediction_logs`: the entry price, the target, each saved headline and the original reasoning. The headlines and the reasoning are untrusted text, so both go through one `fence_untrusted` block; when a row has no saved headlines, the prompt says so instead of showing an empty block. The insight is injected into the next prediction's prompt as `<reflection_context>`. The **cheap bookkeeping** (`accuracy_score` / `is_trend_correct` / persisting the outcome) runs every cycle regardless of volatility, so every prediction is scored on the **next cycle**; the **paid `analyze_mistake` LLM diagnosis** is now gated by the same volatility decision as the prediction pipeline (on a flat, below-threshold cycle it records the outcome with a "diagnosis skipped (not retried)" note instead of spending an LLM call — a FinOps bound on backward-looking spend; the prediction is closed in that cycle, so nothing runs the diagnosis later). That note, the "correct prediction" note written for hits and the "diagnosis deferred" text that older rows still carry are placeholders, not lessons: `is_substantive_insight` (`src/domain/prediction.py`) keeps them out of the lessons panel, the "lesson" of a RAG analog, the report's "why" line and the weekly recap. **Prediction horizon, honestly:** the loop runs at most once per trading day (not every 12h despite the legacy `*_12h` names; with the cron paused, only as often as you dispatch it manually), so a prediction is resolved ~24h later on weekdays and ~72h later across a weekend. The email's predictions section says which session that is: `Horyzont prognozy: następny cykl · najbliższe zamknięcie NYSE: pt 27.11 13:00 ET (skrócona sesja)` names the first NYSE close after the cycle started, from the session calendar in `src/domain/market_calendar.py` (NYSE holidays and 1:00 p.m. ET early closes for 2026–2028, so Thanksgiving and weekends are skipped). A `reflection_min_age_hours` guard (config, default `6`) skips predictions too fresh to score fairly — so an overlapping manual `workflow_dispatch` can't prematurely close a prediction made minutes earlier and pollute the accuracy signal. A `reflection_max_age_hours` bound (config, default `96`) skips predictions too old to score fairly: after a pause in the schedule, a prediction from weeks ago is not scored against today's price; it stays unresolved and stays out of the hit rate and `ml_feature_store`.
3. **Fundamentals (slow loop refreshes, fast loop reads cache)** — `fetch_fundamentals_node` runs after `reflect` and before the volatility gate. The `FundamentalsPort` is implemented by `AlphaVantageFundamentalsAdapter` (2 API requests per stock symbol: `OVERVIEW` + `EARNINGS`) wrapped in `CachedFundamentalsAdapter` (decorator pattern). In the **slow loop**, real API calls populate the `fundamentals_cache` Supabase table. In the **fast loop**, a `NullFundamentalsAdapter` delegate skips API calls and reads from cache only. A cached row counts as fresh for `FUNDAMENTALS_CACHE_TTL_HOURS = 144` (6 days): long enough for the Fast Loop to see it most of the week, short enough that the next weekly Slow Loop always finds it stale and refreshes it. ETF symbols (configured via `SYMBOLS_ETF`) always skip fetching — they have no meaningful per-share EPS/P/E. The domain evaluates a deterministic `ValuationVerdict` (`UNDERVALUED / FAIR / OVERVALUED / UNKNOWN`) based primarily on PEG ratio, with PE/growth qualifiers; ETFs always get `UNKNOWN`. The verdict is surfaced to the Council prompt as a `Valuation snapshot` block and rendered as a dedicated **Wycena fundamentalna** section in the email report.
4. **Volatility gate** — `Asset.evaluate_volatility(delta, threshold)` lives in the pure domain (Hexagonal core). Δ < 2% → `ignore`, no paid APIs touched. **Domain decides, graph executes.** A reference price older than `REFERENCE_MAX_AGE_HOURS = 96` (`src/domain/asset.py`) is not the previous cycle but the state before a pause in the schedule: a move measured from it is many days of drift and would open the gate for every symbol at once. `AnalyzeMarketUseCase` reads the reference's timestamp (`get_last_price_snapshot`, a free read) and `is_reference_stale` decides against the cycle start; a stale reference closes the gate whatever the move (`evaluate_volatility(..., reference_stale=True)`), the paid mistake diagnosis in `reflect` included. The cycle only saves today's price as the new reference (re-baseline, `SkipReason.STALE_REFERENCE`, zero LLM, Alpha Vantage and embedding calls), and predictions resume on the next cycle. A cold start (no reference at all) is unchanged, and a failed timestamp read leaves the gate as it was before the rule. With `feature_snapshots_enabled` (migration `031`) both terminal nodes, `ignore` included, also write a point-in-time feature vector to `feature_snapshots`, so training data is no longer limited to the cycles that passed the gate ([configuration](configuration.md)).
5. **News + Sentiment** — `AlphaVantageClient` makes one request per ticker, rotating N API keys when one exhausts its 25 req/day quota. A `relevance ≥ 0.5` filter strips noise **before** anything reaches the LLM. Per ticker it returns a multi-feature dict: `av_sentiment_score`, `av_relevance_avg`, `news_volume_24h`, `high_relevance_count`, `av_sentiment_label`. **The feed is bounded to the last 24 hours:** the Fast Loop sends `time_from = now − 24h` (plus `sort=LATEST`) on the same single request per ticker, and the client re-applies the same bound to each article's `time_published` as a second safeguard (an article without a parsable timestamp is dropped). Without that bound AV returned the 50 latest articles of any age, so `news_volume_24h` meant "relevant articles among the 50 latest" — a few hours for NVDA, months for a rarely covered ETF — and the same stale article fed the sentiment, the prompt and the `LOW_SIGNAL` risk flag cycle after cycle. The count is still capped by `limit=50` per request, so a ticker with more than 50 articles in a day saturates. The feature keeps its name (ML contract), but rows logged before this change carry the old, unbounded meaning. `prediction_logs.feature_set_version` (migration `027`) separates them: `1` = the unbounded feed, `2` = the 24-hour window (`FEATURE_SET_VERSION`); the Fast Loop stamps it behind `feature_set_version_enabled`, and the Slow Loop trains on the current version only behind `feature_set_filter_enabled` (see [configuration](configuration.md)).
6. **LLM (cross-validation)** — **Claude Sonnet 4.6** (default; or OpenAI GPT when `LLM_PROVIDER=openai`) receives pre-computed AV sentiment + headlines + reflection context + fundamentals valuation snapshot. The first five headlines reach the prompt as a list inside the untrusted-data fence, each capped at 300 characters on its own. They used to be joined into one string, and the fence's per-item cap cut off everything after roughly the third headline; rows logged before this change were predicted from fewer headlines, so the `av_llm_agreement` feature may shift — worth keeping in mind at the next retrain. The council sees the same five titles, and the saved `news_summary` keeps its joined `a | b` form. It returns structured JSON: `trend_direction`, `confidence_score`, **`av_agreement`** (whether it agrees with AV — anything below 0.3 flags potential manipulation), `target_price_12h`, `reasoning`. The answer is normalised before anything reads it, so the council, the saved row and the report see the same values: `trend_direction` is stripped and upper-cased; a value outside `BULLISH` / `BEARISH` / `SIDEWAYS` is stored as `SIDEWAYS` with the `trend_direction_invalid` data-quality flag (a missing one as `SIDEWAYS` without a flag, never `NULL`); `confidence_score` and `av_agreement` outside [0, 1] (a model drifting to a 0–100 scale answers `85`) are clamped by the domain's `clamp_unit` and flagged `confidence_score_out_of_range` / `av_llm_agreement_out_of_range`. Clamping keeps the bound, not a rescale: `85` is stored as `1.0`.
7. **ML hard prediction (local XGBoost)** — the weights are a local `.ubj` file (`data/models/price_predictor.ubj`, Local-First AI) holding **one shared model for every symbol**: the features are dimensionless (returns, scores, counts), so rows of different tickers pool into one training sample. The file exists only after the Slow Loop has shipped a candidate that beats the naive baseline (step 10); until then this step is the cold-start baseline described at the end of this item. Consumes 7 features: `price_delta`, `av_sentiment_score`, `av_relevance_avg`, `news_volume_24h`, `high_relevance_count`, `llm_trend_signal`, `av_llm_agreement`. **The model predicts a 12h _return_, not an absolute price** — `predict_node` reconstructs the target price as `current_price × (1 + return)`. This makes RMSE measure the accuracy of the *move* (not the price level, which used to dominate and let a "echo the last price" model win), and the persistence baseline becomes a clean "return = 0". The `price_delta` feature uses the **same reference in training and inference** — the price of the *previous logged prediction* (view's `LAG(price_at_prediction)` ↔ `RepositoryPort.get_last_prediction_price`), not the per-cycle snapshot that drives the volatility gate (avoids train/serve skew). On cold start (no trained weights yet) it falls back to a "no change" (= return 0) baseline instead of crashing — consistent with the new target. The graph state carries `ml_cold_start`, so the council prompt says there is no ML target and the report labels the forecast `— (ML: cold-start)` rather than presenting the baseline as a model forecast. Each prediction also gets an 80% interval for the return until it is settled (`src/domain/conformal.py`: split conformal with adaptive conformal inference, calibrated on settled predictions of the same asset class; on cold start the predictor is 0 and the interval comes from empirical return quantiles). The email shows it as "80% przedział: -2,1% … +2,4% (n=57)"; the coverage guarantee assumes exchangeability, which markets do not satisfy ([configuration](configuration.md), `interval_coverage_enabled`).
8. **Advisory Council** — after `predict_node`, 7 legendary investor personas (Buffett, Graham, Lynch, Dalio, Soros, Wood, Marks) each independently analyse the same data via parallel LLM calls (one worker per investor). The personas are **data, not code** — one JSON file per investor in [`data/council_personas/`](../data/council_personas/), schema `{"name": str, "style": str}`. Adding / removing a council member = adding / removing a file (bounded by a `COUNCIL_MAX_PERSONAS = 12` cap — extra persona files beyond the cap are dropped with a WARNING, so the per-cycle LLM cost can't silently scale without limit). Loader (`src/infrastructure/persona_loader.py`) validates schema and uniqueness at startup; CLI walidator `uv run python -m src.tools.validate_personas` plus a pre-commit hook catch typos before runtime. A final "chairman" call writes the human-readable `summary` + `dissenting_views`, but the decision scalars — `final_recommendation` and `consensus_strength` — are computed **deterministically in the domain from the actual investor votes** (confidence-weighted), not taken from the chairman's self-reported number; if the chairman call fails, the verdict still reflects the real votes instead of silently defaulting to HOLD. Two volatility gates: the main one (`volatility_threshold`, default 2%) decides whether to run the prediction pipeline at all; the **council-specific gate** (`council_volatility_threshold`, default 3%) further filters out medium-Δ cycles where the 8 LLM calls would mostly return HOLD — set it to `0.0` to disable. Stored as JSONB in `prediction_logs.council_verdict` (legacy blob) **and** as one row per investor in `council_votes` (structured audit trail — query "how did Soros vote on NVDA in the last month" without parsing JSON). Rendered as a styled table in the email report. That audit trail is also what makes the personas **accountable**: the `persona_accuracy_stats` RPC (migration 018) joins settled predictions back onto each investor's votes, and the report renders a **credibility leaderboard** — "Buffett — 68% (95% CI 47–84%) (22 głosy)"; the Wilson interval shows how often the gap between personas is still noise. The ranking rule lives in the domain (`rank_personas`, `src/domain/persona_track_record.py`): a `min_votes = 5` threshold drops personas whose sample is too small to mean anything, so a single lucky call can't top the board. Sample size is always printed next to the percentage. Zero paid calls — it is computed entirely from votes already in the database, and the section suppresses itself when no persona clears the threshold. Failures are not dressed up as votes: a persona whose LLM call fails is dropped instead of counted as HOLD; if no persona answers, the adapter raises `CouncilUnavailableError` and the symbol simply has no verdict (nothing is written to `council_votes`); the 60 s round budget is a real wall-clock limit, late calls finish in the background and are only logged as `paid_discarded`; and when the main analysis LLM failed, the council is skipped rather than fed a placeholder `SIDEWAYS 50%`.
9. **Persist + RAG** — `SupabaseRepository` writes the full record to `prediction_logs`. The news summary is embedded (OpenAI `text-embedding-3-small` → 1536-dim `pgvector`) **once per cycle in `predict_node`** and reused at save time. That embedding is **actually consumed**: before the LLM call, `predict_node` runs a pgvector similarity search (`match_news_embeddings` RPC, migration `011`) to pull the most similar *past* situations and their real outcomes (trend, hit/miss, the correction insight) into the prompt as `<similar_past_situations>`. Analogs are stored text (headlines and an LLM-written lesson), so a prompt injection saved in one cycle could resurface in a later one; they reach the prompt inside the same untrusted-data fence as the news (label `ANALOGS`), one analog per item capped at 900 characters, with the source symbol, outcome and lesson ahead of the headlines so the cap can only trim headlines. RAG is fully graceful — if the RPC/pgvector is unavailable, retrieval is skipped and the prediction still runs.
10. **Slow Loop (weekly cycle)** — `main_trainer.py` trains **one shared XGBoost model** (`TrainModelUseCase.run_pooled`) on the resolved predictions of every symbol in `symbols + crypto_symbols` (rows with a realized `target_return` in the `ml_feature_store` view), pooled into one sample. The view leaves out two kinds of settled rows (migration `026`): `llm_analysis_failed`, the neutral "SIDEWAYS 50%" placeholder saved when the main LLM call failed (its `llm_trend_signal` and `av_llm_agreement` are a fallback, not a signal), and `av_keys_exhausted`, a cycle where every Alpha Vantage key was spent (its news and sentiment features are "no data" zeros, not a quiet day). Rows flagged only `price_delta_no_prior_prediction` (a symbol's first prediction) stay: the other features are real, and without an earlier settled prediction their `price_delta` is NULL in the view, so `dropna` drops them anyway. The filter is applied after the `LAG` window, so `price_prev_12h` is still computed over every settled prediction, the same reference inference uses (the price of the last logged prediction, whatever its flags); filtering before the window would shift that reference and reintroduce train/serve skew. Measured on production on 2026-10-18: 288 settled rows, 45 `av_keys_exhausted`, 38 `price_delta_no_prior_prediction`, 21 `llm_analysis_failed`; the filter keeps about 225. Training one model per symbol made every symbol overwrite the same weights file, and a single ticker needs months to collect 50 settled predictions. The pooled rows are sorted by global time, and each walk-forward fold drops from its training set the rows whose 12h label matures after the fold's validation starts (`purged_train_end` with `LABEL_HORIZON` in `src/domain/backtest.py`): otherwise a training row of one symbol would carry the market move that a validation row of another symbol, a minute later, is asked to predict. The pooled sample needs at least `MIN_SAMPLES_FOR_TRAINING = 50` valid rows. With `feature_set_filter_enabled` only rows of the current feature-set version count (step 5, migration `027`); when that cut leaves fewer than 50, the shared model is skipped with `n_samples` and `feature_set_version` in the result and a warning in the log, never silently. Each symbol is still evaluated on its own walk-forward (`TrainModelUseCase.run`, status `evaluated_passed_gate` or `evaluated_failed_gate`), with the same label-horizon purge applied on that symbol's row timestamps, and that evaluation never writes weights; the report's model card takes its verdict and its RMSE metrics only from the shared model's `ALL` row (a skipped shared run shows no metrics rather than a per-symbol evaluation's RMSE) and lists these evaluations on a separate line. The workflow commits the weights file only when the shared candidate passes the walk-forward gate below — a run that ships nothing commits nothing — and the commit step runs on `!cancelled()`, so a file that was written still gets committed when one evaluation failed and the job exits 1. Skipped results carry `n_samples`, so the scorecard row shows how far the sample is from the minimum. The view owns the single source of truth for `price_delta` (NaN-guarded) and the `target_return` label — the trainer no longer recomputes them. Validation is **walk-forward** (expanding-window folds, not one noisy 20% split): the ship/skip gate decides on the *average* across folds, and the rule lives in the domain (`beats_baseline` / `summarize_folds` in `src/domain/backtest.py`), which the adapter applies before writing weights. A candidate ships only if it cuts RMSE by at least `MIN_REL_IMPROVEMENT = 2%` relative to the **strongest** of three baselines (a margin fixed before looking at results, so noise does not pass as a better model) on at least `MIN_OOS_POINTS = 60` out-of-sample points summed over the folds; with four folds that takes at least 75 samples. The baselines are the zero return ("price unchanged"), the mean drift (the mean target of the fold's training part, predicted as a constant) and the LLM alone (`llm_trend_signal` times the mean absolute target of the fold's training part). Both new baselines take their scale from the training part only, never from the validation block. XGBoost receives `llm_trend_signal` as a feature, so a candidate that beats the zero return but not the rescaled LLM direction only re-learns the LLM at a higher cost, and the hybrid adds nothing; the gate rejects it (`strongest_baseline` / `summarize_folds` in `src/domain/backtest.py`). The offline backtest harness (`main_backtest.py`) reports the same verdict and purges the label horizon the same way, from the row timestamps. The result reports `candidate_holdout_rmse` next to `baseline_rmse` (zero return), `drift_baseline_rmse` and `llm_baseline_rmse`, `candidate_holdout_directional_hit_rate`, `n_folds`, and per-feature distribution stats for drift visibility — keys are explicitly *candidate* metrics because the shipped model is refit on all data and not re-validated. Also runs a fundamentals refresh step using `AlphaVantageFundamentalsAdapter` to repopulate `fundamentals_cache` — which needs the real `ALPHA_VANTAGE_API_KEYS` secret in the workflow, not a placeholder.
11. **Deliver** — Polish-language HTML report via Resend. **Every chart is inline HTML** — no `<img>`, no external host. Gmail and Outlook block remote images by default, which used to punch holes through the middle of the report, and the old `quickchart.io` URLs carried the portfolio's deltas and sentiment scores to a third party on every send. Bars are div-based (the `_render_sparkline_html` technique), the scatter is a quadrant table, and each bar keeps a minimum width plus its printed value so a -0.5% move can never look like a -8% one. The report opens with a **5-second lead**: the cycle's strongest signal ("NVDA -4,2%, rada PODZIELONA") rendered above the fold and reused as the email **subject line**, so the digest wins the inbox before it is opened. The lead's ranking lives in the domain (`src/domain/digest_lead.py`) and is deliberately *not* delegated to an LLM: a CRITICAL quota alert always outranks the biggest price move, and additive (not multiplicative) scoring means a symbol without a council verdict still scores. With a real portfolio (`portfolio_positions_enabled`) the lead knows what you hold: right below a CRITICAL quota alert comes a council verdict against one of your positions ("⚠️ Sygnał przeciw Twojej pozycji: rada SPRZEDAJ na NVDA (24% portfela) -4,2%": the council says SELL on a position worth ≥ 10% of the portfolio, `POSITION_LEAD_MIN_WEIGHT`), then a move of such a position past the volatility gate ("💼 NVDA (24% portfela) -4,2%", ranked by weight × |Δ|), and only then the previous tiers (split council, strong consensus, closed prediction). The subject line inherits it, because the subject and the email body share one `build_cycle_lead`. Without positions the lead is exactly what it was. On a brand-new deployment the first email is instead a **"Dzien 1" onboarding section** — "building a baseline for N instruments, first predictions tomorrow" plus the portfolio's sector breakdown — with its own welcome subject, replacing what used to be a wall of "Pominiete". The distinction is load-bearing: `SkipReason` separates a genuine cold start (no previous price) from a symbol filtered by the volatility gate and from a ticker the price adapter cannot serve, so a mass source outage can never be dressed up as a friendly first run. Below it, in a "Na dziś" zone (portfolio, changes since yesterday, signals, predictions, crypto) followed by a "Zaplecze" back-office zone behind a separator ([report-email.md](report-email.md)): 2 charts (Δ per cycle + forecast), correlation scatter plot, trade signals sorted by `confidence × |Δ|`, risk signals with severity badges, day-over-day diff, a council credibility leaderboard, and clickable news headlines. Two sections (council + fundamentals valuation) render via Jinja2 templates in `src/application/templates/` — autoescape on, the rest of the report still uses f-string composition in `report_builder.py` (incremental migration). The council template surfaces domain-level signals via `CouncilVerdict.is_split_decision()` (⚠️ PODZIELONA RADA badge), `has_strong_consensus()` (SILNY KONSENSUS badge), and `vote_distribution()` (BUY/SELL/HOLD count).

**Experiments in the loop (EXP-05).** A change to a prompt is tested as an A/B experiment rather than before/after, because a before/after comparison mixes the change with what the market did. Each symbol and day (UTC) gets an arm from sha256(`id|symbol|day`) modulo the number of arms: deterministic and stateless, so a re-run lands in the same arm and both arms see the same days and the same market. The first arm is the status quo; the other arms are treatments known to the code, and at most one enabled experiment may change a given prompt part at a time. The arm is stored with the prediction (decision receipt, and `experiment_arms` after migration `037`), and `main_tools.py evaluate --experiment` reports the difference per metric with `n` and `n_eff` per arm and a block-bootstrap interval over days, because predictions of one day are correlated. Experiments add no paid calls. Two are defined and inactive until the Fast Loop resumes: EXP-02, a council that does not see the main LLM's trend and confidence, and EXP-03, a prediction prompt without the lessons from `reflect` and the RAG analogs (that arm still embeds the news at save time, so the analog corpus has no gap). Definitions, rules and metrics are in [configuration](configuration.md#experiments).

All HTTP adapters retry transient failures (429 / 5xx) with exponential backoff, honouring a server's `Retry-After` up to 10 s (the header can ask for hours; the job has 15 minutes), and a single per-symbol error never aborts the whole cycle. POST requests are retried only where a retry cannot duplicate a message: Resend gets an `Idempotency-Key` per email, while Telegram and Slack, which have no such key, are not retried at all.

Sector mix: 🤖 AI / semis (NVDA, AMD, TSM, ASML, ASMIY, MU, QCOM, INTC, SNDK) · ☁️ cloud / software (MSFT, ORCL, NET, SAP, PLTR, IBM, TEAM, FROG, SNOW, DDOG) · 🔐 cybersecurity (CRWD, PANW, OKTA, S, SAIL) · 📱 big tech (AAPL, AMZN, GOOGL, META) · 🖥️ hardware (DELL, SSNLF) · 🚗 mobility (TSLA, UBER) · 🏭 industrial / pharma (SIEGY, NVO) · 💰 financials (BLK) · 📊 ETFs (VT, QUAL, IHI, VB, EWY, IVV, XDWD.DE, IUSN.DE).

Configurable via `SYMBOLS` in `.env` (CSV).

The list was picked by hand (2026-06) with knowledge of how these companies had already risen, so it carries survivorship bias: a long bias on it is not skill. The track record and the public scorecard therefore show the naive "always BULLISH" baseline on the same predictions, and the recipe of every prediction records a `universe_version` (sha256 of the sorted `symbols` + `crypto_symbols`) so that a changed watchlist starts a new segment ([configuration.md](configuration.md), `recipe_version_enabled`).

## Crypto basket (separate price source, separate threshold)

Crypto tickers live in their **own pool** — `CRYPTO_SYMBOLS=BTC,ETH` — and are routed to a different price adapter (`CoinGeckoAdapter`, not Finnhub). The graph itself doesn't know — `RoutingMarketDataPort` picks the right adapter per symbol behind the `MarketDataPort` interface.

Why a separate pool:

- **Different volatility profile** — BTC natively moves 3–5% per day. The equity threshold (2%) would make every crypto cycle pass the volatility gate, burning 8 LLM calls (7-persona council + chairman) on routine noise. `CRYPTO_VOLATILITY_THRESHOLD=0.05` (5%) keeps the gate meaningful: full pipeline only runs when the move is actually a signal.
- **Different ticker format on the news side** — Alpha Vantage `NEWS_SENTIMENT` requires the `CRYPTO:` prefix (`CRYPTO:BTC`, `CRYPTO:ETH`). `AlphaVantageClient` translates `BTC ↔ CRYPTO:BTC` internally so the rest of the system stays clean.
- **No fundamentals** — same model as ETFs: `AssetType.CRYPTO` ⇒ `evaluate_valuation` short-circuits to `ValuationVerdict.UNKNOWN`, no AlphaVantage `OVERVIEW` / `EARNINGS` requests wasted.

**Different sideways band** — `SIDEWAYS_TOLERANCE` is ±0.5%, a sensible "no move" band for a stock. Against BTC's 3–5% daily volatility it would call almost every day a move, so a `SIDEWAYS` prediction on crypto was scored wrong nearly every time. `CRYPTO_SIDEWAYS_TOLERANCE` (±2.5%) is used instead when the asset is crypto. This is a measurement correction, not a loosened grade.

**Crypto is in the training sample** — the Slow Loop pools `symbols + crypto_symbols`, deduplicated, into the shared model and evaluates each of them on its own. It previously trained only `symbols`, so BTC and ETH were never even attempted. Crypto and equity rows now share one model, so their regimes mix; whether the shared model still beats the baseline is left to the walk-forward gate.

Everything else (predict, news, sentiment, advisory council, prediction logs, self-reflection) works identically to equities — crypto goes through the same `AnalyzeMarketUseCase`.

## Quota monitoring (no silent exhaustion)

Every adapter that has a paid / metered quota writes a `QuotaAlert` to a shared `QuotaMonitor` when something looks bad:

| Adapter | What it emits |
|---|---|
| `AlphaVantageClient` | `CRITICAL` when all `ALPHA_VANTAGE_API_KEYS` have hit the daily 25 req/day cap — feed is partial. |
| `OpenAIAdapter` | `WARNING` when a 429 / 5xx / connection error was retried but eventually succeeded (you're at the TPM edge). `CRITICAL` when retries are exhausted and the call failed. Retries happen only in the adapter (the SDK's own are off) and one wait is capped at 20 s. Source field includes the model: `OpenAI (gpt-5-mini)`. |
| `AnthropicAdapter` (default main LLM) | Same retry/backoff as OpenAI on 429 / 5xx / 529 (Overloaded) / connection errors. `WARNING` after a successful retry, `CRITICAL` when retries are exhausted. Source field includes the model: `Anthropic (claude-sonnet-4-6)`. |
| `FinnhubAdapter` | `CRITICAL` on 429 (free tier 60 req/min hit). |
| `ResendNotifier` | `CRITICAL` on 429 (free 100 mails/day), any other 4xx, any 5xx and a network error or timeout — email was not delivered. The alert appears in the **next** report once delivery recovers, and the push digest says the mail did not arrive. |

All alerts from the current cycle are persisted to the `quota_alerts` table (migration `010_quota_alerts.sql`) — including the ones raised while the report itself is being sent. The report builder pulls **the last week (7 × 24 + 3 h)** of alerts, so a Sunday Slow Loop alert still reaches Monday's mail, and renders them as a coloured banner at the **very top** of the e-mail (above the NYSE session line). Severity drives the banner colour and ordering — `CRITICAL` rows come first.

The alert's `message` and `action` are written in Polish, because they are email content: the banner (`🔴 KRYTYCZNY` / `⚠️ OSTRZEŻENIE`), the lead and the subject show them as they are, and so does the `quota_alerts` row they come back from. Each adapter logs the same event in English (`Resend returned 429 — …`), so the run logs keep the English diagnosis; a network failure of the Telegram or Slack push logs only the exception type, since its text carries the bot token or webhook URL and the run logs are public.

If anything `CRITICAL` is in the current cycle, the e-mail subject is prefixed with `⚠️ [QUOTA] ` so the alert is visible directly in the inbox, before opening.

This means: **no exhausted limit, blocked email, or rate-limited API call can silently disappear into the logs**. If the agent saw it, you see it.

## Risk Watch (separate macro pass)

Beyond the per-symbol prediction loop, the agent runs a **separate Risk Watch use case** (`MonitorMacroRiskUseCase`) over proxy instruments that signal *risk-off* conditions. These tickers are tracked but **never enter the prediction pipeline** — their semantics are inverted (a *rise* in `SH` means S&P 500 is *falling*, which is a warning).

```text
EPOL                                # iShares MSCI Poland — sovereign proxy, decline = capital flight from PL
SH,PSQ,RWM,EUM,SQQQ                 # inverse equity (SPY, QQQ, Dow, EM, 3× QQQ)
TBT                                 # inverse long-Treasuries — proxy for rising yields
GLD                                 # gold — classic safe haven
VIXY,UVXY                           # short-term VIX futures — explicit volatility hedge
```

Each instrument is tagged with a `MacroRiskInstrumentType` via `RISK_SYMBOL_TYPES`. The domain (`MacroRiskSignal.evaluate_alert`) maps price change to one of `NORMAL / ELEVATED / CRITICAL` — for `SOVEREIGN_PROXY` the sign is inverted so a *falling* EPOL triggers the alert.

When `NBP_ENABLED=true`, the `NbpClient` adapter (implements `MacroIndicatorsPort`) pulls a 30-day EUR/PLN and USD/PLN window from `api.nbp.pl` (free, no key). `PolishMacroSnapshot.evaluate_stress_level` raises ELEVATED / CRITICAL when the złoty weakens > 2% / > 5% over the window — early warning for PL fiscal stress visible in FX before it shows up in the rating.

Output lands in the e-mail as a dedicated **🚨 Risk Watch** section (signals table + FX block + overall alert level). A per-symbol fetch failure (e.g. Finnhub 403 on a delisted ticker) is logged and skipped — Risk Watch never breaks the main report.

## Risk signals (three types)

`detect_risk_signals(results)` flags anomalies and renders them in the report with a colour-coded severity badge:

| Type | Trigger | Meaning |
|---|---|---|
| 🚨 **DIVERGENCE** | `\|delta\| > 2%` & sentiment opposes the price direction | Possible correction / pump / unusual market dynamics |
| 🚨 **AV_LLM_CONFLICT** | `av_agreement < 0.3` | LLM disagrees with AV — potential fake news / manipulation |
| ⚠️ **LOW_SIGNAL** | `news_volume < 3` | Decision built on a tiny news sample — low confidence |

Each signal lands in a dedicated section in the email with a red/yellow accent stripe.

## Trade signals (top BUY / SELL)

`build_trade_signals(results)` sorts saved predictions by **signal strength = `confidence × |expected_change| × 100`**. Top 5 surface in the email:

```
🟢 BUY      TSM   confidence 92%  forecast +5.05%  #1 · move 5.1% × confidence 92%
🔴 SELL     SAP   confidence 71%  forecast -4.24%  #2 · move 4.2% × confidence 71%
🟢 BUY      NVDA  confidence 85%  forecast +2.95%  #3 · move 3.0% × confidence 85%
🟡 OBSERVE  ORCL  confidence 45%  forecast +0.39%  #4 · move 0.4% × confidence 45%
```

Gives an immediate actionable view without digging through the table. Each card shows its rank and the two factors of its strength rather than the bare product. With `calibrated_confidence_enabled` the ranking runs on the calibrated confidence, so the card shows both values and the sample size of the calibration bucket, e.g. `pewność 85% → 58% po kalibracji (n kubełka: 40)`, and the strength factor reads "calibrated confidence"; `n kubełka: 0` means no bucket matched and no correction was applied. Small buckets swing, which is why n is shown.

**On ML cold start** (no trained XGBoost weights, `SymbolResult.ml_cold_start`) the target equals the current price, so `|expected_change|` is 0 and the formula above would zero every signal and leave the list in processing order. Strength is then the confidence alone — calibrated by its bucket's historical hit rate when `calibrated_confidence_enabled` has a sample — the card shows `— (ML: cold-start)` instead of a forecast, and the section says the ranking is by confidence. The two strengths are on different scales, so model-backed signals always rank ahead of cold-start ones. The forecast chart leaves cold-start symbols out and disappears when every symbol is cold-start.
